# ADR-0011: 台账是账本——条目生成时固化归属，历史口径不 join 当前

**状态**: ✅ 已实施（2026-06-19：C2 字段与新建条目 stamp、C3 历史聚合改读、C4 存量回填均已落）
**决策日期**: 2026-06-16
**相关需求**: REQ-RNT-006（台账自动化）、REQ-RNT-005（合同更正与作废留痕）、REQ-ANA-001（经营分析与导出）、REQ-AST-002（资产关系可追踪）、PRD §3.2（关键报表口径一致性）、§6.3（盈亏沿归属链汇总）

---

## 背景

`ContractLedgerEntry`（domain-model §4.14）只带 `contract_id`，**不带任何 `project_id` / `owner_party_id` / `asset_ids` 归属快照**。要把一条台账算到哪个项目/产权方头上，系统现场 join：条目 → 合同 → 合同组（`project_id` / `owner_party_id` / `asset_ids`）→ 资产 → 项目；而这些归属字段都是**可被覆盖的当前值**，合同组/资产可被 re-org 到别的项目（ADR-0010 已确认「项目是资产的业务管理归集、可调整」）。

后果：**历史财务口径被现状改写**。例：2025-03 资产 X 在甲项目、台账记 10 万；2025-06 把 X 挪到乙项目；此后翻「甲项目 2025-03 收入」得到 0，那 10 万跑到乙项目名下——甲项目的历史账面凭空消失。

根因是**把台账的性质搞错了**。台账每条钉在账期 `year_month` 上、`paid`/`partial` 条目被冻结只读（ADR-0008、§4.14「历史台账只读」）——这些只有**账本（book of record）** 才成立。台账是逐期累加、过往不可变的**历史记录**；「当前欠多少、现在归谁」是从账本 + 当前主数据派生的**实时投影**，是另一回事，不能把账本当实时列表来 join。

## 决策

**确立台账的账本语义，并让条目自带归属：**

1. **台账 = 账本（历史记录）**：每条 `ContractLedgerEntry` 是绑定账期的不可变财务事实；实时情况（当前欠款、出租率、当前归属）是另算的派生投影，不等于账本本身。
2. **条目生成时固化归属快照**：在生成（及重算新建未收条目）时，把该条目解析出的归属上下文——`project_id`、`owner_party_id`、`operator_party_id`、`asset_ids`(集合)——**写死在条目上**，之后 re-org 不回写。固化的 `project_id` 是**该条目按自身叶子合同/资产解析出的唯一项目**：承租模式合同组锁单项目，固化项目即组项目；代理模式代理合同可跨项目，但每条台账仍落唯一项目，固化按条目自身的直租/资产解析，**不取「伞」的项目**（见 ADR-0012），保证固化项目无歧义。
3. **历史/分析口径读条目固化值，不 join 当前**：项目/产权方维度的收入、成本、收缴率等历史口径，一律按条目自带的归属快照聚合；禁止再 join 合同组/资产的当前 `project_id` / `owner_party_id` 回算历史。
4. **金额仍是合同级，不按资产分摊**：固化 `asset_ids` 只表达「这条账当时对应哪些资产」（支撑「该资产的台账历史」检索），金额不拆到单资产，沿用 §6 合同级口径。**固化的 `asset_ids` 取生成该条目的那份 `Contract.asset_ids`（逐合同具体覆盖），不取整组 `ContractGroup.asset_ids`**——否则「资产 A 的台账历史」会混入同组但该合同未覆盖的账。`Contract.asset_ids` 留空表示「覆盖本合同关系全部资产（整租）」，此时固化回退到生成时刻的 `ContractGroup.asset_ids`（见 ADR-0012 子集与整租语义）。固化的 `project_id` 仍唯一（合同经其单项目合同组归属，ADR-0012）。
5. **当前归属可变、历史事实不可变，分层**：合同组的当前 `project_id` / `owner_party_id` 照常可随 re-org 演进；每条台账固化各自生成时点的归属，互不影响。`ServiceFeeLedger` 同理（可继承来源租金台账的固化归属）。

## 被否决的方案

| 方案 | 否决原因 |
|------|----------|
| 维持现状：条目只带 `contract_id`，历史口径 join 当前归属 | 把账本当实时列表读，re-org 静默改写历史财务口径，正是 §3.2「关键报表口径一致性」最难查的违反（同一张去年报表这月和下月跑出来不一样） |
| 建「资产-项目/资产-产权方」归属历史时间线表，回放历史 | 救不了——台账仍 join 合同组当前归属，绕不过；且是为还没出现的回放需求建时间线，与已删的覆盖率口径、配对表同构的过度建模 |
| 合同组一旦有台账就冻结其 `project_id` / `owner_party_id` 不许改 | 太刚——几乎每个活跃合同组都有台账，等于禁止一切 re-org；不如把「当前归属可变」与「历史事实不可变」分层到两处承载 |

## 关键冻结决策

1. **台账是历史账本，不是实时情况列表**——实时投影另算。
2. **历史财务口径只认条目固化归属**，不 join 当前。
3. **金额不分摊到资产**，固化 `asset_ids` 仅作归属与检索，不改 §6 合同级口径。

## 影响

工程项：

- **后端**：`ContractLedgerEntry` 增固化归属列（`project_id` / `owner_party_id` / `operator_party_id` / `asset_ids`），生成与重算新建条目时写入；`ServiceFeeLedger` 同步继承。**2026-06-18 已实施 C2**：新增列、迁移、激活生成/重算新建条目 stamp、服务费继承来源台账固化值。**2026-06-19 已实施 C3/C4**：项目/产权方维度的统计、分析、收缴率聚合改读固化值，不 join 当前合同组/资产归属；新增存量回填迁移按当前关联回填 `attributed_*`（回填时点 = 当时归属的近似），并在回填后断言不得残留空归属。
  - **固化 stamp 必须落在共享写方法 `ledger_service_v2.recalculate_ledger` 与 `service_fee_ledger_service.sync_contract_group` 内**，使三个建条目入口——激活生成、合同更正重算（ADR-0008）、补偿任务（`ledger_compensation_service.run`，仅委托 `recalculate_ledger`/`sync_contract_group`，非独立写路径）——自动一致写入；**切忌只在「激活生成」处加 stamp 而漏共享重算路径**，否则重算/补偿补出的条目归属为 NULL，击穿历史聚合。
  - **补偿任务补出的历史月份条目盖「当前归属」**（无历史归属时间线可查，对齐本 ADR「不建归属时间线表」）——补偿是缺口补齐非历史重建，此近似与存量回填同质，可接受。
- **domain-model**：§4.14 ContractLedgerEntry 增固化归属字段并标注账本语义；§4.15 ServiceFeeLedger 同步（本次随手落字段说明）。
- **PRD**：REQ-RNT-006 明文「台账是账本，条目固化归属、历史口径不随 re-org 改写」（本次随手落）。
- **CONTEXT.md**：增「台账（账本语义·归属固化）」词条（本次随手落）。
- **traceability**：REQ-RNT-006 / REQ-ANA-001 记代码收口缺口。
