# ADR-0005: 删除产权证 `is_verified` 核验状态及未核验风险

**状态**: 🟡 已决策，待实施（2026-06-11）
**决策日期**: 2026-06-11
**实施日期**: 待定
**相关需求**: REQ-AST-005（口径调整）、REQ-AST-003 风险摘要（口径调整）

---

## 背景

产权证（`PropertyCertificate`）带一个 `is_verified` 布尔「核验状态」，文档（domain-model §4.20/§4.5.1/§5.3、PRD REQ-AST-005、CONTEXT「产权证核验状态」）围绕它写了大量约束：只能由有产权证编辑权限的用户核对原件后手工切换、上传/解析/确认不得自动置真、不保存核验人/核验时间、未核验时生成 `warning` 级数据质量风险但不阻断保存等。

代码审查（2026-06-11）发现它名实严重不符：

- **后端零消费**：`is_verified` 只在导入时被写成 `False`（`property_certificate/service.py:340`），**没有任何业务逻辑读取它**——不卡保存、不进统计、不参与计算。
- **唯一「消费者」从未实现**：domain-model §4.5.1 把「未核验」列为 `property_certificate_data_quality` 风险的触发源之一，但全局搜索 `property_certificate_data_quality` 及未核验风险计算**零命中**——这条风险根本没建。
- **前端只是孤立徽标**：产权证详情页一个「已审核/待审核」彩色标签 + 一个手动切换按钮，纯展示，不驱动任何下游。
- **本就无追责**：已决定不存 `verified_by`/`verified_at`。于是它是一个**匿名、不可审计、又卡不住任何事**的手工勾——谁有编辑权限谁都能点，点完唯一作用是（本应）消除一条其实没建的 warning。

业务判断（yellowUp）：「有人核过原件」要有意义，前提是能追责（记谁/何时）；既然为了轻量已砍掉追责，这个勾就两头不靠——想当真信号缺追责，想保持轻又零消费。**砍。**

## 决策

1. **删除 `is_verified` 字段**：从 `PropertyCertificate` 模型、schema、前端徽标与切换按钮一并移除；写删列迁移。
2. **删除「未核验」数据质量风险触发（触发 a）**：`property_certificate_data_quality` 风险**只保留两个客观触发**——(b) 证照信息不完整（证载面积/期限/限制等关键字段缺失，按补录完整性提示口径）、(c) 产权证权利人与关联资产当前主产权主体不一致。二者均由数据实时派生、无需手工勾，是真正有用的质量信号。
3. **正式保存硬门槛不变**：证号全局唯一且非空、至少一个既有资产关联、至少一份附件、权利人引用已审核 Party；本就不含核验状态，删 `is_verified` 不影响。
4. **清理文档**：从 PRD REQ-AST-005/§4.1/§9、domain-model §4.20/§4.5.1/§5.3、CONTEXT（删除「产权证核验状态」词条、删「产权证管理」词条中核验相关句）、api-contract、requirements-trace 删除核验相关表述。

## 被否决的方案

| 方案 | 否决原因 |
|------|----------|
| 保留 `is_verified` 现状 | 后端零消费、唯一消费者（未核验风险）从未实现，是管理摆设 |
| 给 `is_verified` 补 `verified_by`/`verified_at` 让其成为真信号 | 与「产权证主数据不存核验人/时间」的既有轻量决定冲突；为一个无人消费的勾加追责字段不划算 |
| 留作纯展示徽标、仅删未建的风险 | 仍要前后端维护一个零消费字段；既然零消费，不如删净（删而非冻，对齐 ADR-0002 减法原则） |

## 关键冻结决策

1. **产权证 MVP 不做核验状态**：无 `is_verified`、无核验动作、无核验人/时间。
2. **产权证质量风险只剩客观两类**：信息不完整、权利人与资产主产权主体不一致；均数据实时派生，不能手工关闭，只能改源数据消除。
3. **核验若将来要做**：属 vNext，且须一并设计追责（核验人/时间）与消费场景，不重蹈「孤立勾」覆辙。
