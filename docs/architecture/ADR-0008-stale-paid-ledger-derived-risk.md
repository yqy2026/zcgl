# ADR-0008: 合同更正后陈旧已收台账改为派生风险，删除「孤儿响应值」式标记

**状态**: ✅ 已实施（2026-06-15）
**决策日期**: 2026-06-15
**相关需求**: REQ-RNT-005（合同更正与作废留痕）、REQ-PRJ-003（项目风险摘要）、REQ-ANA-001（实收与收缴率口径可信）

---

## 背景

REQ-RNT-005 规定：合同更正触发台账重算时，已收/部分已收（`paid`/`partial`）条目系统不自动改写或作废，「自动跳过并**标记需人工处理**」，以免破坏实收与收缴率口径。

代码核对（2026-06-15）发现「标记」名实严重不符：

- **后端只有临时返回值**：`ledger_service_v2.py` 重算把跳过条目塞进 `skipped_entries` 列表（带 `reason: paid_or_partial_entry_requires_manual_resolution`），作为重算函数返回值经 `LedgerRecalculateSkippedEntry` schema 出到 HTTP 响应体。
- **零持久化**：没有任何台账字段记录「这条已收条目已与更正后的合同条款不一致」。
- **前端零渲染**：`skipped_entries` 全前端零引用——连这个返回值都不显示给用户。

后果比单纯的「死能力」更危险：这是**财务数据已经不一致，而系统假装提醒过了**。已收条目带着旧的 `amount_due` 静默留在账上，而它正是实收与收缴率统计的事实来源，直接侵蚀 G3 经营统计口径与 §8「关键操作必须审计」。

根因与已删的 `is_verified`（ADR-0005）、手工 `overdue`（ADR-0007）同构：一个本应长期可见的信号，被实现成无人消费、无处归宿的孤儿。

## 决策

**已收台账陈旧是客观会发生的财务事实，信号必须有持久归宿；但归宿是派生风险，不是手工标记位。**

1. **不引入手工标记字段**：不加 `needs_manual_review` 之类布尔列——那是 `is_verified`/手工 `overdue` 的覆辙（靠录入纪律维护、没人保证维护对、消费方各自为政）。
2. **持久派生风险 `ledger_stale_after_correction`**：当 `paid`/`partial` 台账条目的 `amount_due` 或 `due_date` 与当前合同条款重算出的目标值不一致时，由数据实时派生为风险，挂在合同关系与项目风险摘要；人工对账修正条目后自然消除，不能手工关闭、忽略或标记已处理（口径同逾期派生与产权证 `warning` 风险）。
3. **重算结果当场可见**：修前端缺口——合同更正/重算结果页当场列出本次被跳过的条目（条目、原因），用户即时可见，不依赖事后再去翻风险。
4. **`skipped_entries` 返回值保留**：作为重算结果即时展示的数据源，但不再是「标记」的唯一载体。

## 被否决的方案

| 方案 | 否决原因 |
|------|----------|
| 维持现状（仅 HTTP 返回值，前端不显示） | 财务数据不一致却无任何持久信号，等于没提醒；REQ-RNT-005「标记」沦为空话 |
| 加 `needs_manual_review` 布尔标记位 | 与 ADR-0005/0007 同构的反模式——手工维护的状态位无人保证维护对，且更正后条目是否仍不一致应由数据决定而非人脑记忆 |
| 仅修前端当场展示、不做持久信号 | 用户一旦划走即无第二次提醒，陈旧已收条目仍静默留存；财务一致性的容错门槛要求有持久、自愈的信号 |
| 把 PRD「标记」措辞降级为「返回」、不收口 | 等于承认系统不管财务不一致，违背 G3 与 §8 |

## 关键冻结决策

1. **陈旧已收台账信号 = 派生风险，非手工标记位**：`ledger_stale_after_correction` 由数据实时派生、自愈、不可手工关闭。
2. **两条提醒机制并存**：重算结果当场展示（即时）+ 持久派生风险（事后兜底）。
3. **不做自动红冲、不自动改写已收条目**：MVP 无冲销机制（属财务总账，Out of Scope）；陈旧条目由人工在台账上对账修正，修正即消除风险。
