## 决策更新（2026-06-10，同日）

本 ADR 的核心结论**不变**：资产删除路由审批流、只保留 `review_status` 两步生命周期。但**下文中「硬约束 审核人 ≠ 提交人」这一点已被推翻**，以本节为准：

- **取消职责互斥**：资产确认 `pending → approved` **只按复核权限门控，不再要求审核人 ≠ 提交人**。任何持复核权限者均可确认，**包括提交人本人**；同一人有权限可一人走完 `draft → pending → approved` 两步。
- **理由**：这是**内部运营工具**，多为小团队、甚至一个数据范围只有一个操作员；硬约束「审核人 ≠ 提交人」会在单人场景**死锁**（录完无人可批，资产永久卡 `pending`）。「第二双眼睛」对「资产台账完整率 ≥ 98%」的边际价值，低于「录入/确认别被卡死」的实际价值。与同期 MVP 减法主线一致。
- **导入连带**：导入资产统一落 `draft`，支持**批量提交 / 批量审核**；取消互斥后，一个管理员即可批量提交再批量确认，无需「初始化导入 vs 日常导入」拆分。
- **vNext**：职责互斥（审核人≠提交人、可配置互斥矩阵）整体推迟到 vNext「可配置职责分离体系」，MVP 不做任何职责互斥。
- **本节推翻**：下文「决策」第 3 点、「被否决的方案」中『单人自确认』一行（现已部分采纳——单人在 `review_status` 生命周期内自确认是允许的，但仍须经 `pending` 中转，非 `draft` 直连 `approved`）、「关键冻结决策」第 3 点。其余结论（删审批流、两步生命周期、锁编辑、反审闭环）保持有效。

## 背景

资产域同时存在两套互不相关的"审批"机制：

1. **`Asset.review_status`**（`draft / pending / approved / reversed`）——直接由 `asset_service.py` 驱动的轻量审核标记，语义是「资产数据是否已被确认」，可反审核再重审。
2. **`ApprovalInstance` / `ApprovalTaskSnapshot` / `ApprovalActionLog`**（REQ-APR-001「资产审批流第一阶段」）——一整套路由审批流程引擎，动作 `start / approve / reject / withdraw`，接入 `notification_service` 发审批待办通知。

两者的问题：

- **真相源不清**：`asset_service.approve_asset` 直接翻 `review_status`，完全不碰 `ApprovalInstance`；一个资产可以 `review_status=approved` 而审批实例仍 `pending`，PRD 从无一句要求二者同步。
- **反审核无处安放**：`review_status` 支持 `reversed`，但 `ApprovalActionLog.action` 没有 reverse 动作，反审核只能游离于审批审计链外。
- **粒度名实不符**：审批流被描述为"针对变更请求"，但 `ApprovalInstance.business_id = asset_id`、`business_type` 固定 `asset`、待办快照是**全资产快照而非 diff**，模型里根本没有"变更请求"这个对象。
- **冗余**：两套机制管的其实是同一件事（这个资产数据能否进入下一步），重复建设。

## 决策

**资产只保留 `review_status` 两步确认，彻底删除路由审批流。**

1. **保留 REQ-AST-003，移除 REQ-APR-001**。资产的管控由 `review_status` 承担，不再有独立的路由审批。
2. **两步复核**：制单人提交 `draft → pending`，审核人确认 `pending → approved`。砍掉 `ApprovalInstance` 的待办分配、时间线、通知、可撤回等流程引擎外壳，只保留 `review_status` 字段上的两步控制。
3. **硬约束 `审核人 ≠ 提交人`**（资产层面的基础职责互斥），现在就上。vNext「职责分离」(本文档第 277 行 PRD)保留给更广的可配置互斥体系（提权审核/业务审核隔离），不与此处冲突。
4. **彻底删除而非冻结**：`ApprovalInstance` 三表、相关代码及 `notification_service` 的审批通知一并拆除，并写删表迁移。

## 被否决的方案

| 方案 | 否决原因 |
|------|----------|
| 保留对象级审批流（REQ-APR-001 留在 MVP） | 与 `review_status` 重复管控同一件事；审批靶子会动（全量快照 + 不锁编辑）；模型撑不起"变更级"承诺 |
| 升级为变更级审批（新增"变更请求"对象 + diff 快照） | MVP 无此需求，属流程引擎二期能力；改动大、需新表 |
| 仿 `Ownership` 冻结代码骨架、入口下线 | `ApprovalInstance` 接入了 `notification_service`（外部副作用），半死不活会继续发通知；接了副作用的死代码应拆净，区别于纯静态骨架 |
| 单人自确认（`draft → approved` 直连） | 失去第二双眼睛，对"资产台账完整率 ≥ 98%"无质量保障 |

## 关键冻结决策

1. **资产无路由审批**：MVP 资产域不存在审批实例、待办、时间线概念。
2. **删除原则**：接入外部副作用（通知）的死代码彻底删除；纯静态骨架（如 `Ownership`）可冻结保留。两者处理不同是有意为之，不是不一致。
3. **基础互斥现在上**：`审核人 ≠ 提交人` 是 MVP 硬校验，不推迟到 vNext。
4. **变更级审批归 vNext**：出租/出售/调价分别路由审批，若将来需要，重建于流程引擎能力之上。
