# ADR-0020: 主体历史身份稳定性——MVP 不合并主体 + 合同对手方名称定稿固化快照

**状态**: 🟡 已决策，待实施（2026-06-19）
**决策日期**: 2026-06-19
**相关需求**: REQ-PTY-001（Party 单一主档管理，含「去重」）、REQ-CUS-002（客户统计双指标）、PRD §6.1（客户定义与名称快照）、§3.2（关键报表口径一致性）

---

## 背景

PRD §6.1 两条承诺：

1. 客户列表以**主体为唯一行**，客户双指标按 **Party live 去重**（不像台账那样固化归属）。
2. 历史合同**保留签署时主体名称快照，不因主档后续变更而追溯覆盖**。

grill（2026-06-19）核对模型后发现两处未兑现：

- **「去重」语义未定，且无 merge 支撑**：REQ-PTY-001 列「去重」，但 domain-model §4.18 Party / api-contract 既无合并字段也无合并端点，只有「同类型内 `code` 唯一」。「去重」到底是建档查重还是合并已存在主体，没写死。若支持 merge：客户双指标按 Party live 去重，把客户 A 并进 B 会**回溯改变历史客户主体数**，正撞 §3.2 口径一致性——这与台账固化归属（ADR-0011）刻意冻结历史的取向相反。
- **§6.1 名称快照无字段承载**：§4.7 Contract 只有 `lessor_party_id` / `lessee_party_id`（外键、跟主档 live 变名），无名称快照列。唯一沾边的 §4.8 `LeaseContractDetail.tenant_name`（选填、冗余展示）只覆盖承租/下游，委托/直租没有。即 Party 改名后历史委托/直租合同显示名会**跟着变**，直接违反 §6.1「不追溯覆盖」。一个没字段兑现的产品承诺。

## 决策

**主体的当前身份可变（主档 live），历史引用的身份事实冻结——分层承载，与 ADR-0011 台账固化同一哲学。**

1. **「去重」= 建档查重提示，MVP 不做主体合并**：创建/导入 Party 时按名称/统一社会信用代码等做重复提示，防重复建档；**不提供合并已存在主体的能力**。合并归 vNext（届时须先设计「合并是否回溯改写历史客户口径」）。客户双指标的 Party ID 轴因此稳定，历史口径不漂移。
2. **合同对手方名称定稿固化快照**：§4.7 Contract 增 `lessor_name_snapshot` / `lessee_name_snapshot`，在合同**定稿（补录即生效 / `finalize_correction`）时**从当时主档名写入、之后**不随主档改名回写**，覆盖全部合同类型（上游/下游/委托/直租）。这是 §6.1「签署时名称快照」的唯一权威承载；`LeaseContractDetail.tenant_name` 退为展示冗余、从快照同步，不另立真相轴。客户**列表**仍显示当前主档名（Party.name live），**历史合同详情**显示快照名——§6.1 两句话各自落到对应字段。

## 被否决的方案

| 方案 | 否决原因 |
|------|----------|
| MVP 支持主体合并 | 客户双指标 live 去重，合并回溯改写历史客户主体数，撞 §3.2；与 ADR-0011 固化历史取向相反；MVP 无 merge 端点/字段，属新建能力非收口 |
| 不加快照字段、§6.1 弱化为「展示当前主档名」 | §6.1 明文「不因主档变更追溯覆盖」是真实业务诉求（历史合同要还原签署时对手方），弱化等于砍需求；而固化快照成本只是两列 + 定稿时写一次，与台账固化同质，划算 |
| 快照只放 `LeaseContractDetail.tenant_name` | 只覆盖承租/下游，委托/直租漏；且与 Contract 外键两套名来源易漂移 |

## 关键冻结决策

1. **MVP 不合并主体**（去重 = 建档查重），合并归 vNext。
2. **合同对手方名称定稿固化**于 Contract，覆盖全类型，不随主档改名回写。
3. **当前身份（主档 live）与历史引用身份（快照冻结）分层**，同 ADR-0011。

## 影响

待实施的工程项：

- **后端**：Party 创建/导入加重复查重提示（不引入合并）；Contract 已增 `lessor_name_snapshot` / `lessee_name_snapshot` 列与迁移，定稿/补录生效与 `finalize_correction` 时写入快照、改名不回写；存量合同回填快照（按当前主档名一次性快照）；`LeaseContractDetail.tenant_name` 已改从快照同步。
- **domain-model**：§4.7 Contract 增两列快照；§4.18 Party 顺修 `review_status` 枚举 `reversed → rejected`（抄串 Asset，CONTEXT「轻量提交标记」/§6 状态表均为 `rejected`，Party 驳回后保留 `rejected` 态，可编辑后重新提审，不提供反审闭环）。
- **PRD**：§6.1 引用快照字段；REQ-PTY-001 注明「去重 = 建档查重、MVP 不合并」；§10 vNext 增「主体合并（含历史口径回溯策略）」。
- **api-contract**：§4.18 Party `review_status` 同修 `rejected`；§4.7 Contract 暴露快照字段只读。
- **CONTEXT.md**：增「主体历史身份（不合并 + 名称快照固化）」词条（本次随手落）。
- **traceability**：REQ-PTY-001 / REQ-CUS-002 记代码收口缺口。
