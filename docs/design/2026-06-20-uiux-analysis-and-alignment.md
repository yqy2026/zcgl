## 第二部分 · 诊断（按严重度排序）

| 编号 | 问题 | 性质 | 严重度 |
|---|---|---|---|
| G1 | **设计 ⟂ MVP 范围错位**：role-dashboard 画了 MVP 不做的产品 | 范围 | 🔴 高 |
| G2 | **画像借自通用物管，非本系统真实用户轴** | 根问题 | 🔴 高 |
| G3 | IA 仍是模块形；任务/角色视角只停在首页提案、未落地 | IA | 🟡 中 |
| G4 | 缺核心任务流程（journey）文档 | 完整性 | 🟡 中 |
| G5 | 设计资产无 scope 治理，已随减法漂移 | 治理 | 🟡 中 |

### G1 — 设计 ⟂ MVP 范围错位（最该先修）

`role-based-dashboard-redesign.md` 画的是**一个完整物业管理套件**，但当前 MVP 是**精简的资产/合同/台账/口径内核**。具体错位：

- **引用已删端点**：§5.1 列 `GET /api/v1/approval/pending`——审批流已删（ADR-0002、原 REQ-APR-001 移除），资产只剩 `review_status` 两步确认。
- **招商工作台（Phase 3）整块超范围**：空置资源 / 意向客户 / 招商漏斗 / 报价 / 签约——MVP 无「招商/意向/推盘」概念，§4.2 也无此范围；其新 API `dashboard/vacant-assets`、`lease-pipeline` 不存在、未规划。
- **物业运维工作台（Phase 4）整块超范围**：工单 / 巡检 / 派单维修 / 设备异常 / 入驻退租验收——MVP §4.2 明确不做催缴，更无工单/巡检模型；其新 API `dashboard/work-orders`、`move-in-out` 同样是空中楼阁。
- **时间线**：该设计 2026-06-03 早于后续多轮激进 MVP 减法（删审批流、删催缴、删覆盖配对、产权证去 `is_verified` 等），故**整体偏大、偏旧**。

→ 4 个工作台里**只有「领导」和「资产管理」对应系统真实能力**；招商、物业是为不存在的功能设计的。

### G2 — 画像借自通用物管，非本系统真实用户轴（最深）

设计的 4 画像「领导 / 资产管理 / 招商 / 物业运维」是**通用物业公司的组织架构**，不是从**本系统的用户结构**派生的。本系统真实的用户轴（PRD §5「角色-绑定-视图三维正交」）是：

- **绑定轴**：产权方绑定用户 vs 运营方绑定用户——这是数据范围的根，决定「能看哪批数据」。**产权方视角**（只看自己资产 + 代理服务费 + 直租，owner 口径）与**运营方视角**（管项目/补录/台账，manager 口径）是两类**根本不同**的用户体验，而 role-dashboard **完全没有「产权方」这个画像**。
- **RBAC 动作轴**：操作（补录/维护）、复核（资产/Party 两步审核）、管理（admin）、权限管理（`perm_admin` 不可见业务数据）。
- **视图轴**：分析/大屏的 owner / manager 口径隔离。

→ 真实画像应是 **(运营方 / 产权方) × (操作 / 复核 / 管理 / 权限)**，而非套用「招商/物业」。**「产权方对接人」工作台的缺失，是比「物业工单」更该补的**——因为它是系统真实服务、且数据隔离要求最强的一类用户。

### G3 — IA 仍是模块形，任务视角只停在首页

- role-dashboard §3.1/§6.1 明确「**主导航保持不变**」，只改工作台首页按角色渲染。
- 即首页之外，所有操作仍走模块导航；「任务/待办视角」只是个落地页装饰，未触及 IA。
- 且 §5.3 自承当前 `DashboardPage` 仍是通用资产统计看板——**连首页改造也未落地**，是提案态。

### G4 — 缺核心任务流程（journey）文档

project-main-axis 是**屏级** mockup（4 张静态画面），但没有**端到端任务流**。系统最核心的几条链路从未被画成 flow：

1. **合同补录链路**：扫描件上传 → OCR/AI 解析 → 逐字段人工确认（候选/低置信/来源）→ 写入合同 → 生成台账。（这正是 PRD §3.2 新增的「核心经营链路真实可用」使用信号。）
2. **实收登记 → 收缴率/逾期派生**：台账条目登记 `paid_amount` → 收缴率/逾期/风险实时派生。
3. **风险处置（非工单）**：风险摘要 → 下钻 → 修正源数据 → 风险自然消除（无关闭按钮——派生不可手工关闭，UX 必须体现「改源头而非点已处理」）。

这三条是「用户实际怎么干活」的骨架，比单屏更能暴露 UX 是否顺。

### G5 — 设计资产无 scope 治理，已随减法漂移

PRD/spec 有 `make docs-lint` 守卫防漂移；**设计资产没有任何防线**。结果 role-dashboard 漂成了「超 MVP 范围」而无人发现。设计稿需要一条「**设计 ⟂ 当前 MVP 范围**」的对齐纪律（哪怕是人工 checklist）。

## 第三部分 · 解决方案

### S0 · 原则

1. **设计从「MVP 范围 + 真实用户轴」派生**，不套用通用物管模板。
2. **不超 MVP 范围**：设计只画系统真做的功能；vNext 功能显式标注、不混入当前设计。
3. **单一真相**：UI 口径引用 PRD/domain-model，不在设计稿里重新定义业务口径（同 PRD 收口纪律）。
4. **IA 渐进**：不推翻已建模块导航；用「任务化工作台 + 跨模块任务流」补任务视角，低风险增量。

### S1 · 重定义画像（取代 role-dashboard §2）

按系统真实用户轴定义 **4 个 MVP 画像**（招商/物业移出）：

| 画像 | 绑定 × RBAC | 核心关注 | 典型任务 | 是否 MVP |
|---|---|---|---|---|
| **运营操作员** | 运营方 × 操作 | 待补录合同、待生成台账、待登记实收、到期/逾期提醒 | 补录链路、实收登记、台账维护 | ✅ 主用户 |
| **运营管理/领导** | 运营方 × 管理 | 经营大盘、收入拆分、收缴率/出租率、高风险项目 | 看大盘 → 下钻 → 问原因 | ✅ |
| **产权方对接人** | 产权方 × 操作/查看 | **仅自己产权范围**：自有资产、代理服务费收入、直租情况、产权证 | 查看 owner 口径数据、产权证维护 | ✅ **新增（原设计缺失）** |
| **复核人** | 任意 × 复核 | 待审资产、待审 Party | 两步确认 / 反审核 | ✅ |
| ~~招商~~ / ~~物业运维~~ | — | 意向/漏斗 / 工单/巡检 | — | ❌ vNext（无功能支撑） |

> `perm_admin`（权限管理员）不进业务工作台——其工作台只有用户/角色/字典/审计，且**强制不可见业务数据**（ADR-0009）。

### S2 · 收口 role-dashboard 设计

- **标注过时**：在 `role-based-dashboard-redesign.md` 顶部加「⚠️ 部分过时，以 2026-06-20 对齐方案为准」。
- **删/降级超范围内容**：招商（Phase 3）、物业（Phase 4）两个工作台及其 5 个新 API（`work-orders`/`move-in-out`/`lease-pipeline`/`vacant-assets` 及 Phase 1 的 `dashboard/summary` 中物业相关聚合）整体移入 **vNext 设计候选**，不进当前实施。
- **修 stale 引用**：`approval/pending` → 资产/Party 的 `review_status` 待办来源（`GET /api/v1/assets?review_status=pending`、Party 同理）。
- **保留可用部分**：领导 + 资产工作台骨架（§3.3 布局规范、KpiCard/TodoItem/ProjectSummaryCard 组件）有效，纳入 S3。

### S3 · 任务化工作台（落地 G3，仅 MVP 画像）

保持主导航不变；把 `DashboardPage` 改为**按 S1 画像渲染的任务化工作台**：

| 画像 | 工作台内容（只用现有 API） |
|---|---|
| 运营操作员 | KPI（在管项目/资产、本月收缴率、逾期金额）+ 待办（待补录、待登记实收、到期/逾期提醒）+ 快捷入口（项目→补录、财务→实收） |
| 运营管理 | KPI（总收入=自营+代理、收缴率、出租率、高风险项目数）+ 高风险下钻 + 收入趋势 + 项目总览 |
| 产权方对接人 | **owner 口径**KPI（自有资产、代理服务费收入、直租应收）+ 我的产权证（数据质量风险）+ 我的项目；**严格按绑定数据范围过滤** |
| 复核人 | 待审资产 / 待审 Party 列表 + 一键进入审核 |

- **数据**：复用 `analytics/comprehensive`、`projects/{id}/risks`、`ledger-summary`、`contract-groups`、`assets?review_status=`、产权证接口。**唯一建议新增** `GET /api/v1/dashboard/summary`（按当前用户绑定+角色聚合 KPI/待办/风险，减并发）——这是 role-dashboard 唯一仍成立的 P0 新 API。
- **角色判定**：按用户 RBAC 角色 + 绑定类型派生工作台；多角色/多绑定提供顶部「视角切换」（运营/产权方切换天然对应 owner/manager 口径，与 §5 视图轴一致）。

### S4 · 文档化 3 条核心任务流（落地 G4）

新增 `docs/design/flows/`，把 G4 三条链路画成 flow（泳道/步骤图，标注每步的页面、API、校验门、错误分支）：

1. `flow-contract-intake.md`：补录链路（含 OCR 确认页的逐字段/低置信/候选不自动绑定 UX）。
2. `flow-ledger-settlement.md`：实收登记 → 收缴率/逾期派生。
3. `flow-risk-remediation.md`：风险下钻 → 改源数据 → 派生消除（**强调无「标记已处理」按钮**，UX 引导改源头）。

这三条同时就是 PRD「用户层」（P6/B）最小可用版本——不必另写大 PRD。

### S5 · 设计治理（落地 G5）

- `docs/design/README.md` 增一条治理规则：**设计稿必须标注「对齐的 MVP 范围基线日期」**；功能超出当前 PRD §4 In Scope 的，必须显式标 `vNext`。
- 设计稿引用业务口径时只能引 PRD/domain-model 锚点，不自行定义（防口径双源）。
- （可选）评审 checklist：新设计稿过一遍「是否引用已删能力 / 是否超 §4 范围 / 口径是否单源」。

### 验收标准

1. role-dashboard 文档无「已删能力」引用、超范围内容已标 vNext。
2. 4 个 MVP 画像各有工作台，**产权方工作台严格只见其绑定数据范围**（§8 验证：构造跨产权方数据，确认不泄漏）。
3. 工作台 KPI/口径与 domain-model §6 一致（不另立口径）。
4. 3 条核心任务流有 flow 文档，覆盖页面/API/校验门/错误分支。
5. 待办可点击直达处理页。
6. 设计稿带 MVP 范围基线日期标注。

## 第四部分 · 与既有工作的关系

- **承接 PRD P6/B**：上轮认定 PRD 是工程件、缺用户层。本方案的 S1（画像）+ S4（任务流）就是**最小可用的用户层**——不必另写大 PRD，把它们作为 PRD 的用户视角补充即可。
- **与减法纪律一致**：U1 的「砍招商/物业到 vNext」是设计侧的 MVP 减法，与 PRD 多轮减法同源。
- **与单一真相一致**：S0/S5 让设计稿引用而非复制业务口径，复用 PRD/domain-model 收口的成果。
- **不与并行代码收口冲突**：U1/U2 纯设计文档；U3+ 才动前端，且只在工作台层、不改已建模块页面。
