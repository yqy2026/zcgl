# 土地物业资产运营管理系统 PRD

## 1. 文档定位

本文档描述土地物业资产运营管理系统的产品目标态，是**产品、研发与验收**的产品需求基线（工程口径）。业务与设计在评审环节参与，但日常以派生摘要 / 视图为入口，不直接消费本文档的字段级口径。

本文档只回答“产品要做什么、为什么做、做到什么算完成”。字段、状态机、API 契约、代码实现证据、历史决策过程分别由其他文档承载。

| `docs/specs/api-contract.md` | API、权限和请求契约 |

## 2. 背景与问题

土地/物业资产运营当前存在资产台账分散、合同与协议链路割裂、证照与主体信息分散、统计口径不统一等问题。现实经营同时包含承租转租模式与代理运营模式，跨产权方、运营方、终端租户的业务关系复杂，依赖人工台账和线下口径容易造成漏记、重复统计和权限风险。

系统目标是建设统一资产运营平台，以项目为普通运营用户的默认主工作对象，同时保留资产、合同与协议、经营台账、主体客户、经营分析等全局直接入口，支撑项目内经营闭环和跨项目整体查看。

## 3. 产品目标

### 3.1 MVP 一票否决目标

| 目标 | 验收含义 |
|---|---|
| 资产清晰可见 | 资产页和项目页可展示资产基本信息、租赁情况、客户摘要 |
| 项目合同与协议可用 | 承租转租与代理运营都可在项目下表达，且同一合同/协议经营事项内模式不混用 |
| 合同/协议补录和经营台账可追踪 | 盖章扫描件上传、必要经营字段补录、经营台账生成、轻量收付流水和更正均有留痕 |
| 经营统计口径可用 | 支持终端租户收缴、运营方收入、运营方成本、服务费结算、经营结果和客户双指标 |

### 3.2 上线后三个月成功指标

| 指标 | 目标值 | 认定规则 |
|---|---|---|
| 关键报表口径一致性问题 | <= 2 个/月 | 口径类缺陷以 issue 标签（`口径问题`）登记，按「确认为真实口径不一致的缺陷数」逐月计数，由产品负责人月度复盘认定；纯人工流程，不建系统功能或报表 |
| 核心经营链路真实可用 | 上线后首月达成 | 真实业务数据可端到端完成「扫描件上传 → 人工确认补录 → 台账生成 → 实收登记」核心链路（**二元达成**，不设比率 / 数量阈值以免凑数）；由产品负责人按真实使用抽验认定，不新建埋点系统。区别于 §3.1/§9 的**放量前**验收门槛——本指标确认**上线后真实生产数据**确有走通 |

> 原「资产台账完整率 >= 98%」与「核心流程平均处理时长下降 >= 40%」已删除：前者无口径定义，与已删的台账覆盖率同构（数据完整性由导入模板校验、资产两步确认、补录完整性提示机制保障，不靠事后指标）；后者无线下基线，不可证伪。MVP 的核心成功标准是 §3.1 一票否决目标与 §9 验收门槛。

## 5. 角色、权限与数据范围

系统采用角色、绑定、视图三维正交模型。

| 维度 | 解决的问题 | 规则 |
|---|---|---|
| 角色 | 用户能做什么操作 | 基于 RBAC 与 ABAC 控制按钮和接口级动作 |
| 绑定 | 用户能看哪批数据 | 基于用户绑定的产权方或运营方主体自动过滤 |
| 视图 | 同一数据用什么经营口径解读 | 仅分析和大屏使用 owner / manager 口径 |

核心规则：

- 用户权限 = 角色可执行动作与主体绑定数据范围的交集。
- 多角色权限默认取允许权限并集；如命中显式拒绝授权或拒绝数据策略，则拒绝优先。
- 权限管理员（`perm_admin`）只可管理用户、角色、权限配置、字典与审计，不可查看业务数据。该隔离是**强约束而非默认**：`perm_admin` 不得授予任何带业务数据范围的角色（业务角色），含授予自己；业务角色只能由 `admin`/`system_admin` 授予。授予前按角色业务数据能力分类校验，违规授予应被拒绝（见 ADR-0009）。此为静态角色授予边界，不是职责互斥矩阵，与「MVP 不做职责互斥」不冲突。
- 多绑定用户在常规列表中展示数据并集，并按业务实体主键去重。
- 普通运营用户默认从项目进入日常工作，但资产、合同与协议、主体客户、经营台账、经营分析必须保留同级直接入口，用于跨项目查询、专项维护和整体视角。
- 分析和大屏不能混合产权方口径与运营方口径，必须按视图口径展示。
- 管理员和审计类用户可按授权查看全量数据。

## 6. 核心业务口径

### 6.1 客户定义

客户不是固定身份，而是合同对方主体。同一主体可在不同合同中扮演不同角色。

客户列表以主体为唯一行（按 Party live 去重），显示**当前主档名**并通过角色标签展示其在合同中的角色。历史合同详情则显示**签署时主体名称快照**（Contract `lessor_name_snapshot` / `lessee_name_snapshot`，定稿时固化、不因主档后续改名而追溯覆盖，见 ADR-0020）。Party「去重」指**建档时查重提示**（防重复建档），MVP **不做主体合并**——合并会回溯改写历史客户主体数/合同数口径，撞 §3.2，归 vNext（见 ADR-0020）。

### 6.2 经营模式

系统支持两种经营模式：

| 模式 | 结构 | 运营方收入口径 |
|---|---|---|
| 承租转租 | 运营方从产权方承租，再向终端租户转租 | 转租租金收入 |
| 代理运营 | 产权方与终端租户直租，运营方提供代理管理 | 代理服务费收入；代理直租租金不计入运营方收入 |

单条合同/协议经营事项只能对应一种经营模式，不允许在同一事项内混用承租转租和代理运营。一个项目可以同时承载承租转租和代理运营，但展示和统计必须按模式分区。

合同/协议记录**锁单项目**（承租转租/代理运营一律如此），其覆盖资产同属该项目。代理运营的**委托协议**（产权方↔运营方）可覆盖多个项目（直租/承租/转租合同恒单项目），但**跨项目落在盖章扫描件层**：同一份委托协议扫描件只上传一次，在覆盖的每个项目下各建一条合同/协议记录共享引用该扫描件，不创建跨项目的用户侧合同对象、不让内部合同组跨项目；每条租金、成本或服务费台账仍落唯一项目（见 ADR-0012、ADR-0011）。

### 6.3 合同与协议类型

| 类型 | 所属模式 | 含义 | 经营影响 |
|---|---|---|---|
| 承租合同 | 承租转租 | 产权方与运营方之间的上游承租合同 | 运营方成本 |
| 转租合同 | 承租转租 | 运营方与终端租户之间的下游转租合同 | 终端租户收缴 + 运营方收入 |
| 委托协议 | 代理运营 | 产权方与运营方之间的委托管理协议 | 服务费比例与结算规则 |
| 直租合同 | 代理运营 | 产权方与终端租户之间的直租合同 | 终端租户收缴 + 服务费计算基数 |

用户侧统一展示为“合同与协议”，不展示“合同关系”作为页面对象名。内部可保留合同组、合同关联或其他聚合模型承载技术实现，但产品界面和验收表达以承租合同、转租合同、委托协议、直租合同为准。

承租合同、转租合同、委托协议、直租合同是**经营影响方向标记**：转租合同租金计入终端租户收缴和运营方收入，承租合同租金计入运营方成本，直租合同租金计入终端租户收缴并作为代理服务费计算基数，委托协议提供服务费比例和结算规则。系统不做合同对合同的逐对配对，也不做“主合同覆盖”判定。经营结果沿“合同/协议 → 资产 → 项目”归属链汇总，当前成本和收益只在项目级呈现，不分摊到资产级。

MVP 全部合同按实际资料到达顺序补录、补录即生效（不做提审 / 审核 / 反审核，见 §4.2、ADR-0013），每份合同必须保留至少一份盖章扫描件作为事实底座。扫描件解析辅助补录、字段来源与附件管理遵循 §6.5。

### 6.4 到期后新签

MVP 不提供“续签”业务能力。合同期满后如继续合作，按新合同/协议补录流程重新创建合同/协议记录，历史合同/协议保留扫描件和补录字段用于查询与审计。

### 6.5 扫描件解析与附件通用规则

合同与产权证的扫描件解析辅助补录、附件管理遵循同一套产品规则（字段级机制、枚举与阈值见 `docs/specs/domain-model.md` §2「字段来源」「扫描件解析确认」与 §4.20~§4.23，本节只述产品意图）：

- **扫描件是事实底座**：合同补录必须保留至少一份盖章扫描件，产权证必须保留至少一份附件，删到最后一份被阻止。
- **解析只辅助、人工定夺**：OCR/AI 预填字段必须由用户逐项确认或修正后才写入；低置信字段必须逐项处理（确认候选值、修正为手工值，或非必填字段显式留空），不得静默落库；解析失败、超时或低置信不阻断完全手工补录。
- **不自动绑定、不自动覆盖**：解析出的主体 / 权利人 / 资产仅作候选推荐，必须用户显式选择已审核 Party 或既有资产后才写入；与已保存字段冲突时默认保留旧值、仅作差异提示，不自动覆盖。
- **不在确认动作里造主数据**：未匹配已审核 Party 只提示先创建并审核，未匹配既有资产只提示先维护资产主档，确认动作内不直接创建 Party 或 Asset，产权证不得保存为无资产关联的孤立证照。
- **解析会话即用即弃**：仅临时工作区，不存草稿、不可稍后继续，确认 / 取消 / 失败后不留档；长期事实以主数据、附件和字段来源快照为准，不记解析工具、模型、置信度、页码或截图等元信息。
- **建议补全不阻断**：确认页可列少量建议补全的非必填经营关键字段（合同限签订日期、付款周期、备注类；产权证限证载面积、期限、限制信息），不填不阻断保存，仅形成补录完整性提示。
- **附件能力轻量**：附件支持轻量在线预览（跟随查看权限、不单独记日志）；下载是独立资料外流动作，校验独立下载权限并记轻量下载日志；同名或哈希疑似重复只提示、不阻断。MVP 不做批量解析、批量确认、附件版本管理或打包下载。
- **来源可追溯不喧宾夺主**：保存时记字段来源快照（手工录入 / 解析确认 / 解析修正），仅在编辑或补录来源上下文按需查看，业务详情主视图不默认展示。

该规则适用于 REQ-AST-005、REQ-RNT-003 与 REQ-DOC-001。

### 6.6 经营款项与账期归属

经营台账不是财务总账，MVP 只做运营侧应收/应付、实收/实付、未收/未付、轻量收付流水和经营统计，不做会计收入确认、开票、税票、支付通道、银行对账或独立现金流分析。

经营台账按四类业务视图组织：

| 视图 | 业务含义 | 包含款项 | 是否产生逾期 |
|---|---|---|---|
| 终端租户收缴 | 终端租户租金收缴完成情况 | 承租转租下游租金；代理直租租金 | 是 |
| 运营方收入 | 运营方自身经营收入 | 承租转租下游租金收入；代理服务费收入 | 否 |
| 运营方成本 | 运营方承租成本 | 承租转租上游租金成本 | 否 |
| 服务费结算 | 产权方向运营方支付代理服务费 | 代理服务费应收、实收、未收 | 否 |

关键口径：

- 代理直租租金必须进入终端租户收缴，因为运营方需要管理和跟进终端租户付款；但代理直租租金不是运营方收入，只作为代理服务费计算基数。
- 运营方收入必须拆分为承租转租租金收入和代理服务费收入。
- 运营方成本只覆盖承租转租上游租金成本，记录应付、实付、未付，不做逾期口径，不产生逾期通知。
- 代理服务费应收 = 代理直租租金实收 × 委托协议服务费比例。当前业务中服务费比例存在历史差异：当前合同 30%，更早合同 20%。
- 服务费按租金账期月份 / 项目 / 委托协议 / 产权方汇总生成，不逐笔生成；服务费比例和服务费归属月份均按租金账期，不按实际收款月份。
- 直租合同必须明确关联一份委托协议。系统可按同项目、同产权方、同运营方、账期落在委托协议有效期内自动推荐，但用户必须确认；若命中多份或未命中，必须人工选择或补齐委托协议。
- 每条可计算服务费的租金账期必须命中单一委托协议比例。若账期跨比例区间，系统提示拆分账期，不做自动按天拆分。
- 已生成服务费应收后的租金实收更正，不得静默覆盖既有服务费应收；具体采用调整项、作废重算或其他更正机制，后续在领域模型阶段确认。

MVP 应支持轻量收付流水，而不是只修改累计实收 / 实付金额。适用范围包括终端租户租金收缴流水、代理服务费收款流水和承租上游成本付款流水。流水至少记录发生日期、金额、登记人、备注和可选凭证附件；实收 / 实付由流水汇总派生。一笔收款可人工分摊到多个账期，系统校验分摊金额合计；凭证附件可选，不上传不阻断登记。

经营分析和项目详情汇总指标默认按租金账期归属；流水保留实际发生日期。经营台账默认按账期月份筛选，同时支持收付发生日期筛选。筛选 2025-12 时，分母为 2025-12 账期应收租金，分子为这些 2025-12 账期截至当前已登记实收的金额，不管实际收款发生在 2025-12 还是 2026-01。

逾期只属于终端租户租金收缴。终端租户未收清且账期到期后，系统自动派生逾期金额、收缴率、风险、筛选和通知；用户不得人工直接翻改逾期事实。为了适配未接财务系统的运营跟进，MVP 允许维护轻量跟进状态（待跟进、已联系、承诺付款、争议中、线下已收待登记、暂缓跟进），但跟进状态不改变逾期金额、收缴率或实收金额。

项目经营结果默认看已登记实收 / 实付，时间归属仍按账期口径：`经营净流入（已登记实收实付） = 运营方收入实收 - 运营方成本实付`。同时提供应收应付口径切换：`账面经营差额（应收应付） = 运营方收入应收 - 运营方成本应付`。界面应避免使用“利润”作为 MVP 核心指标名，避免引入会计利润口径。

| 安全 | PII 字段必须加密，状态变更请求必须防 CSRF，关键操作必须审计 |
| 权限 | 所有业务查询必须按主体绑定过滤，未授权对象不可见 |
| 性能 | 常规列表 P95 <= 800ms，统计和搜索 P95 <= 2s |
| 并发 | Asset 使用乐观锁（`version_id_col`），并发冲突返回明确错误；台账等高并发批量写路径由幂等保证（见下「幂等」行），不另加乐观锁。MVP 不再用「核心实体」这种无边界表述 |
| 幂等 | 批量台账更新、补偿任务、审批回调等关键写操作必须幂等 |
| 可维护性 | API 统一版本化，路由层和业务层分离 |
| 兼容性 | MVP 支持 Chrome 最新两个大版本和 Edge 最新版 |

## 9. 验收标准

MVP 放量前必须同时满足：

| 门槛 | 标准 |
|---|---|
| G1 | 资产页和项目页能清晰展示资产信息、合同与协议租赁情况、客户摘要和项目经营摘要 |
| G2 | 合同与协议能力可用，支持承租转租、代理运营、盖章扫描件解析预填、人工确认补录和经营台账维护 |
| G3 | 经营统计口径可用，支持终端租户收缴、运营方收入、运营方成本、服务费结算、经营结果、客户主体数和客户合同数 |

建议验收覆盖：

- 创建资产重名拦截。
- 面积不一致拦截。
- 资产已关联合同时删除拦截。
- 资产详情按承租合同、转租合同、委托协议、直租合同展示租赁情况。
- 项目必须绑定运营管理方。
- 多绑定用户常规列表展示并集去重数据。
- 合同/协议经营事项模式校验阻止承租转租和代理运营混用。
- 合同/协议上传盖章扫描件后解析预填关键字段，人工确认补录租金或服务费条款后生成经营台账。
- 产权证上传扫描件后解析预填证号、权利人、坐落、面积、期限和限制信息，人工确认后写入资产详情内产权证。
- 产权证证号正式保存必填且全局唯一；重复证号提示维护既有产权证、经用户显式确认后追加资产关联，不自动绑定（见 REQ-AST-005、§6.5）。
- 同一本产权证关联多个资产时不区分主资产和附属资产；展示可按资产名称或编码排序，风险按每个关联资产独立判断。
- 产权证权利人与关联资产当前主产权主体不一致时，对对应资产生成 `warning` 级数据质量风险提示，只在资产详情产权证区域、产权证详情/编辑页和项目风险摘要展示，不阻断保存；该风险不能手工关闭、忽略或标记已处理，只能通过修正源数据自然消除。
- 保存合同补录至少保留一份盖章扫描件；保存产权证满足 5 项硬门槛（证号唯一非空、≥1 既有资产、≥1 附件、权利人已审核 Party、坐落/地址非空）；附件类型/大小、上传不自动解析、轻量预览、下载独立权限、资产与附件 ≥1 下限、疑似重复只提示等行为见 §6.5、domain-model §4.22。
- 产权证 MVP 不做核验状态（`is_verified` 已删，见 ADR-0005）；产权证数据质量风险只剩客观两类——证照信息不完整、权利人与关联资产当前主产权主体不一致，均不阻断资产维护、合同补录、台账生成或经营统计。
- 扫描件解析确认全流程符合 §6.5 与 domain-model §2/§4.23：低置信字段逐项处理后才可保存、来源缺失阻断确认、候选不自动绑定或覆盖、解析会话不留档、失败/超时/低置信可重试或完全手工补录、未匹配已审核 Party 或既有资产只提示不在确认动作中创建、确认后不长期保存页码/片段等来源证据。
- 合同/协议补录更正后旧经营台账按规则重算或作废；已有收付流水的条目不静默改写，留待人工处理。
- 项目详情展示当前账期终端租户收缴、运营方收入、运营方成本和经营结果，且默认按租金账期归属。
- 全局经营台账可跨项目筛选终端租户逾期租金；逾期只由终端租户租金收缴产生。
- 代理直租租户登记实收租金后，该金额进入终端租户收缴，但不进入运营方租金收入。
- 月度服务费结算按代理直租租金实收、租金账期和委托协议历史比例生成服务费应收。
- 租户补缴历史账期租金时，收缴率和服务费归属回补到租金账期，流水保留实际收款日期。
- 承租转租上游租金生成运营方成本，记录应付、实付、未付，但不产生逾期提醒。
- 一笔租户收款可分摊到多个账期，实收由流水汇总派生。
- 终端租户未收清且账期到期后自动派生逾期；用户只能维护跟进状态，不能手工改逾期事实。
- 客户双指标正确去重展示。
- 多绑定用户以 `scope_mode=all` 访问任一暴露客户双指标的端点时，客户双指标不在混合视图下计算：综合分析端点硬拒绝并要求选视图；项目分析端点靶向抑制客户双指标（置空 + 标记），其余分析摘要照常返回。
- 搜索结果不返回未授权对象。
- 权限管理员（`perm_admin`）尝试给任意用户（含自己）授予业务角色被拒绝；业务角色授予仅 `admin`/`system_admin` 可执行，拒绝与成功授予均落审计。
- 合同/协议到期与终端租户租金逾期通知只发给数据范围内可见该对象的用户；逾期通知按终端租户收缴派生口径触发，不依赖人工翻态；运营方成本未付和服务费未收不发逾期通知；通知无处理闭环，只有已读/未读。
- 产权证风险不进入全局搜索，不单独建立风险处置流程，不提供关闭、忽略或已处理状态。

## 10. vNext 候选能力

| 能力 | 说明 |
|---|---|
| 错误恢复模块正式化 | 将错误恢复从工程能力提升为正式产品能力 |
| 系统设置模块稳定化 | 将系统设置纳入稳定功能范围 |
| 集团汇总视图 | 支持集团总部汇总查看所有产权方和运营方数据 |
| 高级多角色冲突策略配置 | 支持更复杂、可配置的多角色冲突解释，不改变 MVP 显式拒绝优先语义 |
| 合同审批与状态流转 | 如未来需要对合同做路由审批——联审、反审核、制审分离、提审/审核门控生效——另行补齐合同审批基线；**MVP 已保留补录即生效的最小合同生命周期（到期/终止/纠错草稿），本项仅指 BPM 路由审批流**（见 ADR-0013） |
| 资产变更级审批 | 如未来需要对资产具体变更（出租、出售、调价）分别路由审批，重建审批流引擎并升级为变更级；MVP 资产只做 `review_status` 两步确认 |
| 可配置职责分离体系 | 提权审核与业务审核隔离、可配置互斥范围与冲突矩阵；**MVP 不做职责互斥**（资产确认只按复核权限门控，不限制审核人 ≠ 提交人），如将来需要由 vNext 引入可配置互斥体系 |
| 权属方管理 | 如需恢复旧独立 Ownership 管理模块，补齐与 Party 产权方角色的边界后再纳入正式基线 |
| 扫描件批量解析 | 如后续补录量证明必要，再设计批量上传、批量解析进度和批量任务治理；不得绕开单条人工确认规则 |
| 风险标签规则自动标注 | 从人工标注升级为规则自动加人工补充 |
| 主体合并 | 合并重复 Party，须先定义合并是否回溯改写历史客户主体数/合同数口径；MVP 只做建档查重、不合并（见 ADR-0020） |
