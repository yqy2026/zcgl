| 迁移 | 只迁移有效合同、未结账款、保证金和必要主数据；期初由业务与财务共同确认并锁定 |

## 2. 背景与问题

土地/物业资产运营当前存在资产台账分散、合同与协议链路割裂、证照与主体信息分散、统计口径不统一等问题。现实经营同时包含承租转租模式与代理运营模式，跨产权方、运营方、终端租户的业务关系复杂，依赖人工台账和线下口径容易造成漏记、重复统计和权限风险。

系统目标是建设统一资产运营平台，以项目为普通运营用户的默认主工作对象，同时保留资产、合同与协议、经营台账、主体客户、经营分析等全局直接入口，支撑项目内经营闭环和跨项目整体查看。

## 3. 产品目标

### 3.1 MVP 一票否决目标

| 目标 | 验收含义 |
|---|---|
| 资产、空间与权属清晰 | Asset、Space、登记单元、产权和出租授权职责分开，出租与占用判断不再依赖资产备注或合同自由文本 |
| 承租转租链真实可用 | 从租赁意向、条件审议、外部审批证据、签署生效、账单与收付、催收直至退场结算可端到端完成 |
| 委托代理链真实可用 | 产权方可完成终端合同与到账确认，双方盖章对账单确定代理费应收；凭票请款和先收款后按约定开票均可流转，开票和服务费实收独立留痕 |
| 金额与历史可信 | 结算项、发票、银行原始行、经营收付、开票分摊、收付分配、保证金、调整和核销分层记录，历史不被当前主数据或合同修改静默重写 |
| 权限和责任可追溯 | 运营方、产权方、财务和复核人员只在职责范围内操作，关键确认实行制审分离并保留证据 |

### 3.2 上线后三个月成功指标

| 指标 | 目标值 | 认定规则 |
|---|---|---|
| 关键报表口径一致性问题 | <= 2 个/月 | 口径类缺陷以 issue 标签（`口径问题`）登记，按确认的真实口径不一致缺陷逐月计数，由产品负责人月度复盘认定 |
| 承租转租核心链路真实可用 | 上线后首月达成 | 真实业务数据可完成“意向 → 条件审议 → 外部审批证据 → 签署生效 → 账单 → 收付分配 → 催收/退场”的二元验收，不以凑数量替代闭环 |

| 范围 | 说明 |
|---|---|
| 本系统合同或通用 BPM | 合同在既有外部合同审批系统审批；本系统只记录绑定版本的审批结果与证据，不复制第二套流程 |

| 用户侧物理删除 | 合同、账款、收付、审批和结算等关键事实只允许作废、反向调整或新增版本 |

## 5. 角色、权限与数据范围

系统采用角色、有效主体范围、视图三维正交模型。

| 维度 | 解决的问题 | 规则 |
|---|---|---|
| 角色 | 用户能做什么操作 | 基于 RBAC 与 ABAC 控制按钮和接口级动作 |
| 有效主体范围 | 用户能看哪批数据 | 显式用户绑定优先；确实没有当前有效绑定记录时，回退到所属内部组织直接或继承的默认主体与视角 |
| 视图 | 同一数据用什么经营口径解读 | 仅分析和大屏使用公开 `view_mode=owner|manager|all`；`scope_mode` 只作为服务端解析结果 |

核心规则：

- 用户权限 = 角色可执行动作与唯一范围解析器得到的有效主体范围的交集。
- 多角色权限默认取允许权限并集；如命中显式拒绝授权或拒绝数据策略，则拒绝优先。
- 权限管理员（`perm_admin`）只可管理用户、角色、权限配置、字典与审计，不可查看业务数据。该隔离是**强约束而非默认**：`perm_admin` 不得授予任何带业务数据范围的角色（业务角色），含授予自己；业务角色只能由 `admin`/`system_admin` 授予。授予前按角色业务数据能力分类校验，违规授予应被拒绝（见 ADR-0009）。此为静态角色授予边界，不是职责互斥矩阵，与「MVP 不做职责互斥」不冲突。
- 当前存在有效显式绑定时，全部有效绑定构成完整范围，常规列表按业务实体主键去重；组织默认范围不与显式绑定合并。
- 仅当用户没有当前生效的显式绑定记录时才回退组织默认范围。范围缺失或配置失效必须失败关闭并返回明确 403，不得伪装为空列表。
- 只有当前有效分配内建 `admin` 或 `system_admin` 角色的用户不受主体范围限制；`perm_admin` 与其他管理角色仍需有效主体范围，且 `perm_admin` 始终不得读取业务数据。
- 省略 `view_mode` 时，范围只有一种视角则自动采用；同时含 owner/manager 时解析为内部 `scope_mode=all`，不得从绑定顺序或展示偏好猜选。需要单一视角的分析端点要求用户明确选择。
- 普通运营用户默认从项目进入日常工作，但资产、合同与协议、主体客户、经营台账、经营分析必须保留同级直接入口，用于跨项目查询、专项维护和整体视角。
- 客户主体数/客户合同数等客户双指标必须使用 owner 或 manager 单一视角；其他分析字段可在 `all` 混合范围下按端点明确的抑制契约展示，不得把混合口径伪装成单一视角。
- 内建 `admin`、`system_admin` 仍受动作权限和显式 deny 约束；审计类用户不因角色名称自动获得主体全量范围。

## 6. 核心业务口径

### 6.1 客户定义

客户不是固定身份，而是合同对方主体。同一主体可在不同合同中扮演不同角色。

客户列表以主体为唯一行（按 Party live 去重），显示**当前主档名**并通过角色标签展示其在合同中的角色。历史合同详情则显示**签署时主体名称快照**（Contract `lessor_name_snapshot` / `lessee_name_snapshot`，定稿时固化、不因主档后续改名而追溯覆盖，见 ADR-0020）。Party「去重」指**建档时查重提示**（防重复建档），MVP **不做主体合并**——合并会回溯改写历史客户主体数/合同数口径，撞 §3.2，归 vNext（见 ADR-0020）。

Organization 与 Party 是两条正交身份轴：Organization 只表达内部公司、部门和项目组层级，Party 只表达可独立承担产权、运营、签约或租赁角色的法人主体或自然人。部门和项目组不创建 Party；公司同时具有内部组织身份和业务主体身份时，分别建档并由 Organization 显式关联已审核、启用的法人 Party。关联为空时继承最近有效上级的默认主体与 owner/manager 视角；无来源或直接关系失效时失败关闭，不按名称、编码或外部引用自动关联。详见 ADR-0022。

### 6.1.1 主体业务角色切片

主体中心以 Party 主档为唯一行，支持“全部、产权方、运营方、终端租户”四种当前业务角色切片。角色由查询时的当前有效资产、项目和合同/协议关系派生，不写入 Party 主档；同一 Party 可同时出现在多个角色切片，但在“全部”列表只出现一行并展示全部角色标签。

产权方取当前有效资产的产权方，运营方取当前有效项目的运营方，终端租户取当前有效下游转租合同或直租合同的承租方。仅有历史合同的 Party 不进入当前终端租户切片，历史角色继续通过客户档案的历史签约呈现。`customer_type` 是内部/外部展示标签，用户主体绑定是数据范围，两者都不是业务角色；本期不引入客户等级、评分、自动分群或 Party 角色缓存。
### 6.2 经营模式、签署文书与项目记录

系统支持两种经营模式，并在同一套界面中用模式标签和筛选明确区分：

| 模式 | 法律关系 | 运营方经营收入 | 合同审批责任 |
|---|---|---|---|
| 承租转租 | 运营方先向产权方承租，再以出租方身份与终端租户签转租合同 | 下游转租租金收入 | 运营方使用自己的外部合同审批系统完成下游合同审批 |
| 委托代理 | 产权方直接与终端租户签直租合同，运营方依据委托协议提供招商和运营服务 | 经双方盖章对账确认的代理服务费 | 产权方使用自己的外部合同审批系统完成终端合同审批 |

一份双方实际签署或盖章的法律文书只建立一个“签署文书”身份和一条法律版本链，可关联多个项目经营记录。法律条款、签署文件和版本由各项目共享，项目账单、收付、催收、结算和利润历史保持独立。不得把同一份协议按项目复制成多份法律合同，也不得把多个项目的账款混成一套台账。

Project 只表达日常运营责任。同一 Space 同一时点只归一个 Project；产权、物业、改造、消防或专项任务责任另行记录，不因项目归属自动推导。

### 6.2.1 租赁意向、底价和竞争洽谈

- 潜在承租人通过租赁意向书或运营人员代录形成租赁意向，记录拟租 Space、租期、租金、递增、免租期、保证金和其他条件。
- 运营方对意向作接受、还价或拒绝的正式条件决议；该决议是内部经营判断，不包装为独立 Quote 合同对象。
- 多个意向方可以针对同一 Space 同时洽谈，系统不锁定 Space。只有已经生效的终端合同形成排他占用，并由数据库约束和事务校验阻止 Space、期间和用途冲突。
- 有效底价必须包含适用 Space/项目、有效期、计价口径、依据文件、出租方式和审批/备案证据。缺少有效底价时可继续接洽和登记意向，但不得进入合同生效。
- 低于有效底价的条件必须关联本案专项例外审批及证据；一般性授权或口头说明不能替代。

### 6.3 合同类型、授权与生效

| 类型 | 所属模式 | 经营影响 |
|---|---|---|
| 上游承租合同 | 承租转租 | 运营方租金成本及转租授权来源 |
| 下游转租合同 | 承租转租 | 终端租户应收与运营方租金收入 |
| 委托代理协议 | 委托代理 | 运营权限、责任边界和代理费结算规则 |
| 终端直租合同 | 委托代理 | 产权方对终端租户应收及代理费试算来源 |

合同方向只说明谁收、谁付和经营影响，不能替代出租授权。终端合同生效前必须验证授权对 Space、期间、用途和是否允许转租的覆盖，并冻结当时的授权版本、证据和验证结果。承租转租模式已有有效上游转租授权时，产权方无需逐份确认下游合同；委托代理模式的终端合同由产权方确认。

产权、授权资料由运营方依据产权方提供的材料录入，实行提交人与复核人分离，提交人不得自审。复核只证明材料已按职责检查，不把运营方变成产权真实性的担保人。

所有合同继续在现有独立合同审批系统完成审批，本系统不建设合同 BPM。每次生效必须保存外部审批系统、审批单号、结果、完成时间、审批证据、对应合同版本、文件哈希和确认人。任一方均可上传外部审批证据，由承担该次审批责任的组织确认；最终签署或盖章文件也可由任一方上传，由合同出租方确认其为生效版本。

合同生效至少同时满足：

1. 适用且已确认的外部审批结果绑定当前合同版本。
2. 最终签署或盖章文件齐备并经出租方确认。
3. 有效底价及低价例外审批满足适用规则。
4. 出租授权覆盖 Space、期间和用途，且授权快照已冻结。
5. 漏水修复、消防、腾退等生效前置条件已经完成，或由运营方授权人员记录原因、人员、时间和附件后明确豁免。
6. 约定以实际交付日为起租日时，双方签署或盖章的交接记录已经确认实际交付；固定起租日合同的迟延交付不自动顺延计费。

豁免前置事项不得暗中修改租金、租期、免租期等核心合同条件；核心条件变化必须重新走外部审批并形成新版本。

合同生效检查遵循“机器检查确定性事实、人工处理真实例外”的原则：

- 空间排斥、租期覆盖、金额公式、授权期限等可确定计算的条件由系统自动检查，不要求用户对通过字段逐项点击确认。
- 检查结果必须区分通过、警告、阻断、无法判定、不适用和已批准例外。通过项默认折叠但保留规则版本、检查时间和可展开证据；警告、阻断和无法判定项优先展示。
- 行内只能修正有权限编辑的事实源、绑定已经批准的例外，或发起例外审批。例外保存范围、原因、批准人、证据和有效期；合同核心字段、内容哈希、规则或例外状态变化后必须重新检查。

### 6.4 变更、续租、终止与退出

- 商业变更以补充协议或其他有效文件形成新版本，从约定生效日影响后续账单；已形成的历史账单不回写，追溯差额通过独立调整单处理。
- 续租必须新建与原合同关联的新合同或协议，不覆盖原合同。新合同重新校验外部审批、底价、授权、Space 冲突和交付条件。
- 提前终止必须有关联的终止协议或有效通知，并保存适用的外部审批记录；不得仅靠用户改状态结束法律关系。
- 到期或终止后进入“待退场结算”，完成交还、费用、保证金、损坏赔偿和双方书面结算后关闭。
- 提供“到期台账”支撑国企年度预算与工作计划编制：合同列表支持按到期年份筛选，经营看板提供“未来 12 个月到期”口径（名单、户数、面积、当前续租状态）。台账只聚合既有事实，不折算预测租金、不做预算控制；“按当前合同的租金规模”合计为待业务确认口径，采用时必须标注“按当前合同租金计，不含递增与空置假设，非收入预测”。
- 到期前 180/90 天自动生成“启动续租或退场准备”内部任务（提前量可配置），使年度工作计划在系统内以任务队列承载。
- 存在未清欠费时可将债务转入催收账户及新催收案件后关闭合同经营关系；合同关闭不抹除债务。

### 6.5 文档解析与附件规则

- 有效电子签署原件、纸质原件扫描件和普通附件必须区分类型。系统保存的扫描件不自动替代线下纸质原件，也不因上传而自行取得法律效力。
- 合同、协议、终止文件、交接记录和双方盖章对账单必须关联其业务对象与版本，不使用散落附件代替结构化确认。
- OCR/AI 仅提供候选值；用户逐项确认或修正后才写入，不自动绑定 Party、Space、Asset 或合同，不自动覆盖已保存事实。
- 解析失败、超时或低置信不阻断手工录入；解析会话是临时工作区，确认、取消或失败后不作为长期事实保存。
- 附件删除、替换和下载受权限控制并留痕；关键业务对象必须保留其生效依据和历史版本，不能删除到证据断链。

### 6.6 账单、收付、保证金、代理费与催收

经营系统记录运营侧权利义务和现金事实，不冒充财务总账。关键对象分层如下：

| 对象 | 事实含义 |
|---|---|
| 结算项 | 按合同条款、保证金义务或盖章对账单形成的最小应收/应付义务，固化项目、合同、主体和适用 Space 范围；合同和对账单只作聚合入口，不保存可覆盖底层事实的累计开票或实收状态 |
| 发票 | 独立的开具、红冲或作废税票事实，不等于应收成立、付款许可或实际收付 |
| 开票分摊 | 将发票行金额关联到一个或多个结算项的覆盖关系，不改变结算项未结金额 |
| 银行原始行 | 从银行 Excel/CSV 导入的不可改写外部证据，未经有效收付分配不改变结算项 |
| 经营收付流水 | 已确认资金性质、付款/收款主体和经营归属的现金事实 |
| 收付分配 | 将一笔经营收付拆分关联到一个或多个结算项、项目或合同的复核结果 |
| 未分配预收余额 | 由已确认到账金额减去有效收付分配派生的余额，不是可独立调节的事实源 |
| 调整、退款、核销、非现金抵扣 | 经批准并有证据的独立事实，不伪装成普通收款或付款 |

核心规则：

- 租金支持月、季、年及约定周期，付款日规则、免租期、递增、保证金公式结构化保存，并提供月度账单预览。单价和总价都保存，同时明确合同控制口径；登记面积、测量面积和计费面积分开，主数据面积变化不自动改合同。
- 下游租金收款与上游租金付款是两条独立链，不做净额结算。代理直租租金属于产权方资金，不计入运营方租金收入。
- 银行导入、规则匹配、批量复核入账和批量撤销均按稳定幂等键执行。虚拟子账号唯一、备案账号唯一，或合同号/附言、币种、金额和账期共同唯一等确定性规则，可以自动认领 Party 并在结算项唯一、金额守恒、未命中风险条件时形成待复核拟分配；户名和金额相同不得单独触发自动分配。
- 高置信唯一匹配进入财务批量复核，复核生效后才形成有效收付分配；无附言、多候选、差额、代付、超额、币种不一致或超过金额阈值的流水进入人工异常池。人工拟分配的提交人不得复核自己的结果；规则版本、候选集合、命中解释、操作与撤销链必须审计。
- “已到账待核销”要求付款 Party 已唯一确定且不减少结算项未结金额。只有唯一结算项或明确金额守恒的结算项集合可在限定 SLA 内暂停对应自动催缴升级；Party-only 或多候选只显示到账提示，不暂停催缴。SLA 超时恢复提醒并升级内部异常任务，复核生效的收付分配才派生“已核销”。
- 一笔款可拆到多个结算项、项目和合同。第三方代付需保留关系说明和证据；超额款或尚无结算项的款项保留为未分配收款事实，未分配预收余额由到账金额减有效分配派生，不强行冲销未来结算项。
- 发票行与结算项、经营收付与结算项分别允许多对多分摊或分配。发票与资金按真实发生顺序独立登记，支持凭票请款和先预收后按约定开票；二者不得直接互相核销。
- 保证金从应收、收取、持有、补足到退还、抵扣、没收和差额结清全程留痕。退款、核销和非现金抵扣需要审批及证据，并实行关键现金操作制审分离。
- 委托代理模式由产权方逐笔确认终端租金到账。系统依据委托协议试算服务费，双方确认系统版本并上传双方盖章对账单后，才形成该结算期服务费应收；发票与服务费实际到账分别登记，任何一方都不作为另一方的全局时序前置。
- 争议、承诺付款、暂缓跟进和法务处理不删除或改小欠费。滞纳金在取得合同和事实依据并确认前只作试算，不作为正式应收。
- 每个 `Party × Project` 形成一个持续欠费账户，可包含多个独立催收案件；每次新的欠费周期建立新案件，已关闭案件不得重开。系统自动生成内部催收任务，首期不自动对外发送短信、微信或邮件。
- 日常催收由运营方负责。承租转租模式由运营方决定法务升级；委托代理模式的重大法务行动由产权方批准。法务案件与催收案件关联，但不能替代催收和账款事实。
- 项目经营结果同时提供权责发生和现金口径，只纳入可直接归属的收入与成本；共享成本首期不分摊，不强制把合同金额分配到单个 Space。

| REQ-SCH-002 | 搜索结果组织与排序 | 支持全部视图和分组视图，按相关度和业务置顶排序。**业务置顶** = 查询命中业务编码（资产/项目编码、合同号/协议号）精确或前缀匹配的结果，优先于纯文本相关度；排序键为「业务编码命中 → 文本相关度 → 标题」 |
| REQ-SCH-003 | 搜索权限过滤 | 未授权对象不返回，搜索结果使用统一解析器得到的有效主体范围过滤 |

产权证管理是资产详情内能力，不作为 MVP 全局搜索对象；用户通过资产搜索和资产详情进入产权证信息。产权证相关数据质量风险只在资产详情产权证区域、产权证详情/编辑页和项目风险摘要展示，不进入全局搜索结果。

### 7.6 认证与授权域

| 编号 | 需求 | 验收标准 |
|---|---|---|
| REQ-AUTH-001 | 会话安全与统一鉴权 | 登录、刷新、退出闭环，关键写操作必须鉴权；角色授予受授予边界约束——`perm_admin` 不得授予业务角色（含授予自己），业务角色仅 `admin`/`system_admin` 可授予，违规授予被拒并审计（见 ADR-0009） |
| REQ-AUTH-002 | 数据范围上下文自动注入 | 查询、统计、搜索、通知和分析统一调用单一主体范围解析器：仅当前有效分配内建 `admin`/`system_admin` 角色的用户不受主体范围限制；当前生效时间窗内的显式 `UserPartyBinding` 完整取代组织默认范围；确实没有当前生效记录时，回退到所属 Organization 直接或最近有效祖先的 Party + owner/manager 视角。无范围、组织链失效、Party 失效或当前绑定目标失效分别返回稳定 403 原因码，不得返回成功空列表；双视角解析为内部 `scope_mode=all`，分析仍按公开 `view_mode` 隔离（ADR-0022） |
| REQ-AUTH-003 | ABAC 数据策略引擎 | 支持策略包、角色绑定、拒绝优先、缓存失效和日志模式 |

### 7.7 文档与分析域

| 编号 | 需求 | 验收标准 |
|---|---|---|
| REQ-DOC-001 | 扫描件解析辅助补录 | 支持合同和产权证单件扫描件上传、OCR/AI 抽取、字段置信度展示、确认页轻量来源证据、候选匹配、低置信高亮与逐项处理、人工确认、字段来源快照、重试与超时处理；MVP 不提供「一键采用全部高置信无冲突字段」或批量采纳，所有候选按字段逐项确认或修正。解析确认与附件的通用产品规则遵循 §6.5；字段级机制（字段来源枚举、解析会话临时不留档、候选不自动绑定 / 覆盖、建议补全不阻断）见 `docs/specs/domain-model.md` §2、§4.22、§4.23 |
| REQ-ANA-001 | 经营分析与导出 | 支持终端租户收缴、运营方收入、运营方成本、经营结果、客户双指标、项目维度和经营模式分区、结果导出和口径版本标记；经营分析默认按租金账期归属，实际收付日期仅用于经营台账筛选、流水查询、审计和导出；**客户双指标受单视图口径约束，无论在哪个端点暴露都不得在内部 `scope_mode=all` 下计算**——公开请求只使用 `view_mode`，双视角省略参数或显式 `view_mode=all` 均得到混合范围；综合分析端点对混合范围硬拒绝并要求先选 owner/manager，项目分析等「客户双指标仅为载荷一部分」的端点只置空客户双指标并标记「需选视图」，其余分析照常渲染 |

### 7.8 主体域

| 编号 | 需求 | 验收标准 |
|---|---|---|
| REQ-PTY-001 | Party 单一主档管理 | Party 类型只允许法人主体 `legal_entity` 和自然人 `individual`；内部编码由系统并发安全生成且创建后不可变，分别使用 `LE-000001` / `NP-000001`。法人统一标识类型限 `unified_social_credit_code|legal_registration_number|foreign_registration_number`，按（类型，规范化值）唯一；自然人限 `national_id|passport`，加密、脱敏并按（类型，不可逆指纹）唯一。草稿可缺标识，提审前必须成对且格式正确。支持新增、编辑、查询、建档查重和两步审核；已审核 Party 禁止硬删除，只能携带绑定操作者/提议/状态版本的短期预览凭证和原因执行停用/重新启用，状态漂移时拒绝。MVP 不做主体合并，不保留 `PartyHierarchy`（ADR-0020、ADR-0022） |
| REQ-PTY-003 | 主体业务角色切片 | 主体列表支持按产权方、运营方、终端租户进行服务端筛选和分页，并在同一 Party 行展示全部当前角色标签；角色只从当前有效资产、项目和合同/协议关系派生，历史合同不进入当前切片。查询必须沿用 Party 数据范围，`customer_type` 与用户主体绑定不得充当角色筛选；不增加独立 Customer 主档、客户等级或持久化角色缓存。 |
| REQ-PTY-002 | Party 数据来源与创建路径 | 初始化导入和业务过程只创建法人主体或自然人，主体编码由系统生成，正式统一标识进入专用字段；合同补录、产权证权利人、组织代表主体和用户显式范围只能引用符合各场景约束的已审核 Party，其中新增业务引用和授权要求 Party 同时启用。扫描件解析确认不得直接创建 Party；Organization-Party 批量匹配不得按名称、编码或 `external_ref` 自动生效，必须人工确认 Party ID（ADR-0022） |

> 资产审批流（原 REQ-APR-001）已移除：资产只做 `review_status` 两步确认（见 REQ-AST-003），不建路由审批流。详见 `docs/architecture/ADR-0002-asset-review-no-approval-workflow.md`。

### 7.9 系统管理域

| 编号 | 需求 | 验收标准 |
|---|---|---|
| REQ-SYS-001 | 用户与角色管理 | 支持用户 CRUD、批量启停用、自定义角色和多角色分配；以创建后不可变的 `account_type=human|service|system` 明确账号分类。每个启用 human 用户必须且只能通过 `organization_id` 归属一个启用 Organization，完整祖先链也必须启用；service/system 必须无组织且不继承默认范围。human 用户调动只走 `user:manage_party_scope` 控制的影响预览/专用动作，普通资料更新不得修改 `organization_id`；跨部门能力由角色提供，跨 Party 范围由显式用户绑定提供（ADR-0022） |
| REQ-SYS-002 | 组织架构与主体范围管理 | Organization 只维护内部层级，并以成对可空的 `represented_party_id` + `represented_party_perspective(owner|manager)` 直接代表至多一个已审核启用法人 Party；空值继承最近有效上级，直接配置覆盖继承，失效直接关系阻断上溯。组织页面是该关系唯一写入口，主体详情只读反查代表组织；用户显式绑定只允许 owner/manager、优先于组织默认范围，不保留 headquarters、`is_primary` 或 Party 下级自动展开。组织关系、范围变化移动、用户调动和用户绑定均需专用权限；预览返回绑定操作者、完整提议和相关版本的短期凭证，提交携带凭证、原因和幂等键并重新校验，状态漂移返回 409；写入记录前后值并立即失效缓存，批量操作事务内全成全败（ADR-0022） |
| REQ-SYS-003 | 数据字典管理 | 支持字典分类、字典项 CRUD，业务表单选项来自字典服务 |

> 工具页说明（非 REQ）：数据模板管理（`/system/templates`，菜单挂资产资源）：资产导入模板下载入口，支撑 REQ-AST-001 导入模板校验；仅展示真实可下载模板，不展示假统计与已退休条目。

## 9. 验收标准

v4.0 按纵向链路分阶段验收，承租转租通过后再交付委托代理；不得以零散页面或字段完成替代业务闭环。

| 门槛 | 标准 |
|---|---|
| G1 | Asset、Space、登记单元、产权、出租授权和 Project 责任边界可辨识，历史版本可追溯 |
| G2 | 承租转租从意向、底价/例外、外部审批、授权验证、风险优先生效检查、签署生效到结算项、开票/收付、催收和退场结算端到端可用 |
| G3 | 委托代理从终端合同确认、产权方逐笔确认租金到账、双方盖章对账到服务费应收端到端可用，开票轨和收款轨可按任一真实发生顺序独立闭环 |
| G4 | 结算项、发票、开票分摊、银行原始行、经营收付、收付分配、保证金、调整和核销各自只有一个事实来源，历史不被静默重写 |
| G5 | 合同变更、续租、终止、交接、退出和欠费转催收均追加留痕，不能靠覆盖原合同或手改状态完成 |
| G6 | 运营方、产权方、财务和复核人员权限符合职责；提交人不得复核自己的权属/授权资料，关键现金操作制审分离；自动匹配规则可版本化、可解释、可撤销并保留审计 |
| G7 | 迁移范围只含有效合同、未结账款、保证金和必要主数据，期初余额经业务与财务共同确认并锁定，修正只走调整 |

至少覆盖以下业务场景：

- 同一签署文书关联两个项目，法律版本共享而账单、收付和催收独立。
- 同一 Space 同期只归一个 Project；临时多 Space 组合不生成永久空间边界。
- 同一 Space 可有多个并行意向，但两个生效终端合同不得发生期间和用途冲突。
- 缺有效底价可登记意向但不能使合同生效；低于底价且无专项例外审批同样被阻断。
- 下游转租合同的 Space、期间或用途超出上游授权时阻断生效；有效授权下不要求产权方逐份确认。
- 外部审批证据未绑定当前合同版本，或最终盖章文件未经出租方确认时，合同不能生效。
- 生效前置事项未完成且未合规豁免时阻断；确定性通过项无需人工打勾，缺少输入显示无法判定，合同核心字段变化或例外到期后原结果失效。
- 虚拟子账号唯一匹配自动完成主体认领和拟分配并进入财务批量复核；同额多候选、无附言、差额、代付和超额款进入人工异常池。
- 已到账待核销只有在唯一结算项或明确金额守恒的结算项集合下，才在限定 SLA 内暂停对应自动催缴且不减少应收；Party-only 或多候选不暂停，SLA 超时恢复提醒，复核生效后才派生已核销。
- 一笔收款可拆到多个结算项、项目或合同，超额或尚无结算项的部分进入未分配预收余额，第三方代付保留证据。
- 产权方逐笔确认直租到账后系统可试算代理费，但没有双方盖章对账单不得形成正式服务费应收。
- 国企/外企租户凭票请款时先开票后分次付款；大宗租赁先预收年租后按账期开票，两种时序均可流转。
- 一票多结算项、多票一结算项、一款多结算项，以及红冲、退款均保持金额守恒和原事实可追溯；发票、服务费应收和服务费实收不能互相代替。
- 争议或暂缓跟进不删除欠费；同一欠费账户可建立新催收案件，已关闭案件不得重开。
- 续租建立新关联合同；变更不回写历史账单；终止后先退场结算，欠费转催收后可关闭合同。
- 产权方不能编辑运营方数据，也不能查看运营方内部成本和完整利润。
