# R1：第五轮毁灭性评审（首席架构师）

## 第一部分：顶层重构蓝图

### 1.1 一句话点破本质

> 这个系统的商业与物理本质只有一句话：**把每一平方米空间的权利（凭什么租）、承诺（租给谁收多少）、现金（钱到没到）、现场（能不能用）四件事钉在同一条不可篡改的链上——其余一切数字都是这四件事的投影。**

方案 §1.3 的"一句话定位"已经说对了这句话。**骨架没有错，错在给骨架穿了三件盔甲，又给两扇门装了错误的门轴。**

### 1.2 核心架构全景图（原子实体关系与数据流向）

```text
                        ┌─────────────────────────────────────┐
                        │     SPACE 空间本体（唯一物理名词）        │
                        │   地块 / 楼 / 层 / 房 · 五维状态全派生    │
                        │   （合同承诺×实际占有×权属合规×行政×现场） │
                        └────────┬──────────────────┬─────────┘
              RIGHT 凭什么租      │                  │  MOTION·现场 现在能不能用
     ┌────────────────────────────┴───┐   ┌─────────┴────────────────┐
     │ 权利事实链（只追加修订）            │   │ 巡查 · 问题工单 · 现场限制  │
     │ 产权/经营权 → 转租许可 → 委托代理   │   │ 实际交还 · 新租交付          │
     │ 签约时冻结 → 不可变授权快照         │   │ （现场事实，只追加）          │
     └────────────────┬───────────────┘   └─────────┬────────────────┘
                      │ 签约冻结授权                     │ 改写"现场可运营"维度
                      ▼                                ▼
     ┌───────────────────────────────────────────────────────────┐
     │  MOTION·商业主链（现金 = 这条链的计量结果）                     │
     │  锁定 → 签约 Agreement → 账单 Obligation                     │
     │       → 现金 Flow → 核销 Allocation → 押金/坏账终局            │
     └───────────────────────────┬───────────────────────────────┘
                                 ▼  只许派生，禁止手写
        可租集合 · 即将释放 · 空置时长 · 欠费账龄 · 收缴率 · 盘活漏斗 · 租金滚存(缺)

     ─────────── 镜头层（不是本体，不许与门平级抢点击）───────────
     资产 Asset = 空间的核算镜头（权属+面积+底价聚合）
     项目 Project = 空间的经营镜头（上下文容器）
```

**判词**：方案的四条事实轴（§1.3）与三原子完全同构——Space=物理轴、Right=授权轴、Motion=商业链+物业处置轴，且 §2.1 的"Space/Asset 最终裁决"已把 Asset/Project 正确降为镜头。本体论层面这个方案是对的，五轮评审没有白费。

## 第二部分：四大基础维度评审

### 维度一：名词命名与核心概念

**🛑 当前致命缺陷**

1. **"台账"一词双义**：§3.4:271 与 §4.3:365 裁"台账保留'账本集合'义"（账单域），§4.2:334 又立"资产 › 台账"菜单节点（资产登记册义）——v3.10 堵了"资产›资产台账"自嵌套，却在"台账"上开了第二个洞。
2. **"当前可交付 / 未来供给"是四字造词税**：方案被迫立三条词汇纪律看守"房源"（§3.4:281）——当一个概念需要三条规则约束它的名字，说明词没选对。一线招商的母语是"哪些能租、哪些快到期"。
3. **收付页四 tab 混了两条分类轴**（§5.5:532）：方向轴（终端收缴=收、上游付款=付）× 对象轴（租金/服务费/押金）。铁证：押金收款在全 §5.5 无任何落点，服务费（对象）却与收/付（方向）平级成 tab。v3.12 刚把四 tab 定为 P0 修法——修反了：那是岗位落地页问题，不该用导航结构来解。
4. **与对照参考冲突未裁决**：市场报告确认全行业通行词是"房源、账单、收款、核销、催缴"（明源云链路）；"往来方"保得住（往来单位系通行财务语），"当前可交付"必须回填市场语。
5. **细节自伤**：§5.3:465 要求资产级展示"最长空置叶子并标注 `space_id`"——把内部稳定 ID 摆上界面（R2 分级：违神不违形，§4.3 红线字面不含详情字段，修法仍对）。

**💡 第一性原理重构**：名词系统只需三层——本体词（空间）、权利词（产权/经营权/转租许可/委托代理）、动线词（租、收、修、交）。统计口径词只许出现在数字旁边，不许进导航。大前提：**用户脑中没有"状态分类学"，只有问句；词汇必须贴着问句走，分类学留在后端。**

**🛠️ 落地提案（终审名词对照表）**

| 现用词（出处 §） | 终裁词 | 所在层 | 裁决理由 |
|---|---|---|---|
| 当前可交付（§2.1 公式词） | **可租** | 操作层 | 贴一线问句；六项合取派生公式不动，只换皮；顺带消解"可交付"一词双职（现场可运营四值之一 §2.1:154 vs 聚合词） |
| 未来供给（§2.1） | **即将释放** | 操作层 | 招商原话；"供给"是宏观经济学词 |
| 收付 › 服务费（一级 tab，§5.5） | **收款 › 类型筛选"服务费"** | 操作层 | 岗位默认视图 ≠ 导航结构 |
| 台账的"账本集合义"（§3.4:271） | **废除**，全站只留"资产台账"一个义 | 操作层 | 一词·一义·一层，方案自己的纪律 |
| 资产 / 空间 / 项目 | 空间=本体；资产=**核算镜头**；项目=**经营镜头** | 概念层 | 与 §2.1 裁决一致，"镜头"隐喻写进 PRODUCT.md 词表 |

### 维度二：前端信息架构

**🛑 当前致命缺陷**

1. **"四扇门"问题**：资产域四个兄弟节点——空间/台账/项目总览/产权证（§4.2）——是按对象类型切的，但它们是同一批空间的四个镜头（拓扑/核算/经营/权利证件）。用户问"城东园区 3 号楼怎么样"，得先想清楚今天该走哪扇门。这是"数据库表画菜单"的残余形态。
2. **生命周期轴只在叶子成立，组合层没有一张图**：盘活漏斗要等满一个滚动年数据才点亮（§2.2 灰显），**只读租控图连做都没做**——旧系统复核 §3.4 浏览器实测证明"房间租控图"是真实业务，市场矩阵确认房源状态可视化是全行业标配。方案只砍了"图编辑"（§5.3:488，砍得对），却把只读图也一并埋了（砍过头）。
3. **决策层驾驶舱有历史、没未来**：§5.1 组合驾驶舱全是向后看指标；未来义务确定性生成（§8.3），却没有任何前向应收视图（租金滚存）——这是数据模型白送的能力。
4. **待处理是 11+ 类例外的平铺队列**（§5.1:419）：无分组无默认排序——首屏认知过载，这是 IA 问题不是列表问题。

**💡 第一性原理重构**：双轴 = 纵轴空间拓扑（在哪里）× 横轴生命周期（处于哪一态、在现金哪一环）。任何入口只有两种合法形态：**选空间看横轴**（详情页），或**选横轴切空间**（队列/看板/租控图）。镜头可以有，但**镜头不许与门平级竞争用户的第一次点击**。

**🛠️ 落地提案**

- 资产域：空间是主门（正确）；台账/产权证/项目总览保留为镜头门；中期演进给空间页增"核算/权属镜头切换"，本期不动结构。
- 空间页增**只读租控图视图**：楼×层色块矩阵，色=现场可运营四值主标签，点格直达 Space 详情锚区。零编辑、零新事实表，纯派生。
- 工作台待处理**按业务入口域分组**，组内按金额×期限排序。
- 组合驾驶舱增**租金滚存卡**：未来 12 月应收 × 模式 × 项目（已确定义务 + 临期释放预测）。这是经营应收读模型，不是 §12:1435-36 排除的财务现金流分析，不碰总账边界。

## R3.1 B4.4 认错（结构性不自洽，非判断失误）

- **R2 论证 1 成立且致命**：幂等身份 `(purpose, agreement_id, space_id, agreement_version)` 下，"幂等新建一次交还检查"根本不成立——**R1 要保留的"幂等新建"，其唯一实现载体正是要删的 successor 机制**。要么重定义链身份、要么允许多链并存并引入"哪条链权威"新问题，都比现状糟。
- **R2 论证 2 成立**："省三类唯一约束"是虚账——链根唯一约束服务幂等创建（保留方）、predecessor 唯一后继服务 rejected 路径（未提议删）；过期专属成本=一个字段+一条命令。
- **R2 论证 3 成立，根因认领**：R1 把"证据时效控制"误分类为"防御机械"。accepted review 与交还事实之间的停滞缺口里，空间处于法律占有悬置、物理无人看守状态；旧证据喂 `DepositOffset` 是承租户争议和国企审计的真实风险面。**证据新鲜度不是盔甲厚度，是另一类东西。**
- 折中采纳：两路 successor 合并为一条命令、两个前置分支（latest review rejected ∨ accepted 且过有效期 ∧ 无交还/交付事实）。
- **R2 自身未钉死的补遗①**：R2 说"政策有效期是 B0 政策矩阵的一个常数"，但 §11.3 B0-B 签字清单（限制级别/自处理自验收/critical finding 政策；续租文书样本）**没有 review 有效期**——v3.13 必须显式补进 B0-B，否则该常数无人签字。

## R3.2 两条降级接受

- **并发门**：R1 预先让渡了"用户功能面砍不出 50%"，但"盔甲的 50%"剩余主张在切片协议下同样消解——R2 的批评落在 R1 **框架与内容之间的差额**上，成立。保留 R2 两条底线：§13.3 各门标注归属切片；约束随 migration 落地、分期只分验收时点（R1 原措辞"不变量可排到首笔真实数据落地后分期实施"确有"表先建、约束后补"误读风险，R2 钉法是对 R1 措辞缺陷的修复）。

## R3.4 三处小反击（不影响结论）

1. **"别再动第五轮 vs v3.13 矛盾"是表面矛盾**：R1 结尾的 v3.13 提议本就以自己清单为范围，与 R2 化解方式（"把它自己的清单当作唯一收口范围"）同途。

# §5 教训记录（防下一轮翻烧饼）

1. **删防御机制前先查它的实现载体**：B4.4 案的教训——提议"幂等新建"时必须先确认幂等身份定义，否则删的正是自己要保留的东西的载体。
2. **证据时效 ≠ 防御机械**：涉及法律事实（交还/交付/押金抵扣）的 freshness 控制是实体风险控制，不是盔甲厚度；砍"防御"先分类它保护的是数值一致性还是法律争议面。
3. **清单呈现形态 ≠ 交付承诺**：切片协议已分布的验收门，读作"首批全量交付"会得出虚假的削减空间。
4. **表面矛盾先查双方本意**："别再动"与"v3.13"若范围一致即同义，勿以修辞差异立指控。
5. **收口清单须全量核对来源评审**：R2 汇编清单时静默丢了 R1 的"释放收入潜力"卡——合并清单必须逐条对源。
