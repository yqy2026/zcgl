## 第〇节：总判定——什么保留、什么推翻

用户的核心拷问是："目前这样的功能模块设置，真的有存在的必要吗？是否存在更短的业务路径？"v3.4 用约 900 行回答"钱和权限如何不出错"（§6–§9、§11、§13），只用约 300 行回答"用户如何更快完成业务"（§4–§5），并且把四组核心词汇悬置为"待确认"（§3.4）。**方向没有全错，重心严重偏移。**

**原样保留（这部分经得起第一性检验，不需要再动）：**

- 命令内核、幂等回执、金额单事实轴、历史不可静默改写、全通道防泄漏、迁移拒绝桶（§6–§9、§13.1–13.5）；
- 两级菜单深度上限、详情走子路由、URL 即上下文真相（§4.4）；
- 命名分层红线——内部聚合根名词禁入导航/按钮/URL（§4.3）；
- 模式 = 属性 + 筛选，不做布局（§5.2，v3.4 对 v3 泳道的修正是对的）；
- 行内核销 + 常驻合计条 + 回车跳行（§5.5）；
- 每页四态验收、岗位默认落地机制、预警/异常非任务语义（§3.2、§5.8、§13.6）。

**推翻（本评审的五个结构性结论）：**

1. **词汇不能悬置**：§3.4 的四组待确认词（账期/账单、收款与欠费/收付结算、租户与产权方/往来方、运营工作台·项目运营/工作台·项目）必须终审前一次裁决，不能"随 C 切片切换"——信息架构不能建立在临时名词上。
2. **七个一级入口是组织架构图，不是业务流**：按科室（合同岗、收付岗、资产岗、权限管理员）画菜单，与旧系统"按数据库表画菜单"同构，只是换了切片维度。收敛为五个"问题导向"入口。
3. **缺了"盘活"的起点**：业务前提是存量土地与产业园资产盘活，但 IA 从"签约之后"才开始——招商人员与决策层两类核心用户在岗位表（§5.8）里没有行。"到期即房源"是全案性价比最高的缺失面，且数据零新增。
4. **黄金视区错配**：项目驾驶舱首屏给月度损益（§5.2），收付工作台给低频危险动作常驻右轨（§5.5），合同向导把账单预览沉底（§5.4）——三处都把"当日决策"让位给了"月度报表"或"稀有动词"。
5. **首页挂建模欠账**：空置预警带"资产级口径·房间级租控未上线"角标（§5.1）——把 ADR 悬案绣在黄金视区上，是架构白旗；同一批数据对招商人员是"库存"不是"损失"，换个框架就是房源。

# 第一部分：首席架构师的顶层重构蓝图（Executive Summary）

## 1.1 这门生意的底层本质（三句话）

1. **把不可移动的空间，通过一组合同，变成可预测、可解释的现金流，并让国有资产保值增值。** 系统的存在理由不是"记录"，而是"盘活"——让闲置/低效空间尽快进入产生现金的合同，并让每一分钱的来龙去脉可向国资委与审计解释。
2. **系统只需保存三类原子事实**：空间现状（有什么）、权利与承诺（谁有权收益、谁欠谁）、现金流动（钱是否真的动了）。其余一切——状态、逾期、收缴率、空置率、风险、预警、损益——全部派生。v3.4 的后半句做对了（§2.2），前半句（空间）被推迟了（§2.1 不建 Space 表），于是"有什么"这一问在产品层悬空。
3. **任何用户问题都归约为五问**：有什么（资产）？租给谁（租约）？该收多少（账单）？实收多少（收付/核销）？差异何在（待办/报表）？**每个一级入口 = 一问，一问不多，一问不少。**

## 1.2 原子实体的解耦与映射（概念 ER / 业务架构全景图）

| 解耦 | 内容 | v3.4 现状 |

# 第二部分：四大维度"毁灭性评审"与落地提案

## 维度一：名词命名与核心概念（Nomenclature & Concepts）

### 🛑 当前致命缺陷

1. **"资产"一词四义**。在 v3.4 中"资产"同时是：决策层的组合概念（经营分析矩阵的行）、操作层的对象（资产台账的一行）、空间拓扑的载体（地块/楼宇/楼层/房间都是 Asset 类型）、权属法律的锚点（`owner_party_id` 挂在 Asset 上）。更严重的是，一级入口"**资产与空间**"直接把 §2.1 的未决建模争议（本轮不建 Space 表、空间拓扑后置写 ADR）绣进了导航——菜单名成了 ADR 悬案的展示位。
2. **"X 与 Y"菜单词 ×3**（资产与空间、租户与产权方、组织与权限）。每个"与"都是一次概念合并失败的瘢痕：两个词并列说明模型没能给出统称。且"租户与产权方"只点名了 Party 四角色（租户/产权方/运营方/其他）中的两个，另两个被入口名字 invisible。
3. **斜杠词"合同/协议"贯穿全案**。v3.4 命名红线明令"合同关系"不得进界面（§4.3），却放行"合同/协议"这个更普遍的斜杠词占据一级入口。四类合同（终端租约、上游合同、委托协议、未来的服务合同）对用户是四个不同对象，各应有专名；斜杠词是建模不确定性的用户侧泄漏。
4. **四组核心词悬置（§3.4）是 IA 的地基空洞**。方案自己承认候选词更准（账单更贴市场语言、收付结算覆盖付款、往来方是统称、工作台/项目消除碰撞），却推迟到"业务确认后随 C 切片切换"。后果：整个 C 阶段建立在临时词汇上，之后逐切片二次换名，直接违反方案自己的"新词与对应新页面同一发布"纪律。**方案尚未进入 C 阶段，此刻拖延换名只有成本、没有收益。**
5. **"账期"混淆了两个粒度**：账期是时间词（2026-08 这个月），账单是该月的应收/应付义务实例。出纳日常操作的是账单，报表聚合的是台账（账本）。v3.4 用"账期"同时指两者（"账期义务""账期工作台"），而 §5.5 的 ASCII 图自己写着"账单/账期列表"、§5.2 写着"统一合同/账期列表"——**方案的图已经词穷，正文还在坚持**。
6. **预警/异常/待处理三胞胎**（§3.2/§5.1）。为规避"任务"语义（语义裁决本身正确：无领取/关闭/转派）付出了三个近义词并存的词汇代价。用户只需要一个词。
7. **反面确认（做对的，保留）**：§4.3 内部模型名与用户语言分层表、内部词（`OperatingUnit`/`cash-application` 等）禁入导航的红线、表名不因纯词汇统一而重命名——这些是 v3.4 的正确投资，本评审全部保留。

### 💡 第一性原理重构

命名三定律：

1. **一词·一义·一层**。决策层词、操作层词、法律层词不混用。"资产"在国资语境是法定词、决策层词（资产盘活、保值增值），必须回归组合义；操作层的对象词让位给"房源/空间"；法律证据层用"产权证"。三层词各自唯一，在词汇表里声明层级。
2. **名词从用户的问题来，不从表来**。用户问"有什么可租"→房源；问"该收多少"→账单；问"和谁做生意"→往来单位。菜单上每个名词都应该是用户问题的直接答案。
3. **词汇裁决先于页面**。命名是 IA 的地基。终审必须包含一次词汇决断（与业务负责人 30 分钟逐词过一遍），之后 C 切片直接以终词开发。"待确认清单"不能带进实施。

## 维度二：前端信息架构（Information Architecture）

### 🛑 当前致命缺陷

1. **七个一级入口 = 科室组织图**。运营工作台/项目运营/资产与空间/合同与租赁/收款与欠费/租户与产权方/组织与权限——每个入口对应一个岗位或科室（合同运营岗、收付登记岗、资产与权证管理员、权限管理员）。这是旧系统"按技术模块堆叠"的镜像：切片维度从"数据库表"换成了"科室名"，**模块优先的思维没有变**。市场调研给出的明源通行链路是"房源/空间盘点→招商获客→…→合同签署→计费→催缴→收款→核销→对账→经营看板"——一条**业务流**，不是七个并列科室。
2. **IA 从"签约之后"才开始，缺"盘活"起点**。业务前提是"国企城投存量土地与产业园资产盘活"。盘活的第一环是"发现可租资源并租出去"：空置的房间、即将到期的合同（到期即释放房源）、可定价的资产。v3.4 的信息架构里这一环**没有任何面**——空置只以"损失"姿态出现在预警区（§5.1），到期只以"风险"姿态出现。对招商人员，同一批数据是**库存**。同一事实的两种心智框架（损失 vs 库存），方案只有前者，于是最高频的潜在用户在系统里没有家。**这是"更短业务路径"拷问下最大的缺口，且补齐成本≈零（资产 + 合同 + 到期日数据全在，缺的只是一个读视图和一屏）。**
3. **决策层无专属视图**。§5.1 工作台三个区（预警/工作区/经营分析）试图同时服务一线（今天干什么）和决策层（盘面如何），两头不靠。决策层要的是组合驾驶舱——按园区 × 模式的资产组合损益、盘活进度、趋势——不是从一线预警队列开始一天。§5.8 岗位表七行全是执行岗，没有决策层行。
4. **空间脊柱缺失的连锁代价已经显形**。§2.1 推迟 Space 表的裁决本身可以接受（范围控制），但它级联成了产品缺陷：首页空置预警挂"资产级口径·房间级租控未上线"角标（§5.1）——把建模欠账绣在黄金视区；项目驾驶舱无法回答"哪层空着"；招商人员无法沿"园区→楼→层→房"走位选房。**方案把"房间租控业务域"（该缓）和"空间可浏览性"（该上）混为一谈**——后者只是现有 Asset（含空间层级字段）+ 合同状态的只读组织方式。
5. **同一对象图有 3–4 个平行入口，靠 Context Trail 事后缝合**。§4.1 已经发现"项目 = 上下文容器、合同与收款 = 并列执行轴"，但入口结构仍给项目、合同、收付、资产各一个一级入口，再靠 §4.4 的 Context Trail 把跨域跳转缝起来。缝合是补救，不是结构。入口本身应该体现"**空间脊柱（资产人）+ 资金脊柱（财务人）交汇于项目**"的双轴结构。

### 💡 第一性原理重构

1. **对象脊柱唯一**：组合 → 园区 → 楼宇 → 房源 → 租约 → 账单 → 流水，一条可下钻、可返回、URL 即位置的连续体。任何对象页都在脊柱上。
2. **三层分离**：队列层（待办，按人组织）、脊柱层（对象，按空间组织）、报表层（口径，按组合组织）。工作台 = 队列，驾驶舱 = 报表，其余 = 脊柱。三层各自唯一，不再互相复制内容。
3. **到期即房源**：存量盘活的最短路径不是"预警→处理"，而是"到期/空置 → 释放房源 → 新租约 → 新账单"。到期合同列表就是未来房源库存，这个环节是整条业务链上投入产出比最高的一块。
4. **招商 CRM 依然不做**（守住 PRD 边界）：线索分级、带看、佣金是 CRM；可租资源视图不是——它是现有数据的读视图，是资产域的自然成员。

### 🛠️ 具象化落地提案

**五个一级入口（每个词一个概念，各回答一问）：**

| 入口 | 回答的问题 | 主要用户 | 对应 v3.4 |

## 维度三：菜单设置与导航拓扑（Menu & Navigation）

### 🛑 当前致命缺陷

1. **"运营"词头碰撞**：运营工作台 vs 项目运营——导航扫描时前两字相同，用户在两个入口间反复犹豫。§3.4 自己承认并给出候选词，仍然拖延。
2. **组织与权限占用一级入口（1/7 黄金导航位）**。使用频率约每月数次、受众 2–3 名管理员。且方案已把字典/系统设置/操作日志/数据策略包收进"设置中心"（头像菜单），却把同为后台管理的组织权限留在业务导航——这是设计者的 SSOT 分类（授权语义 vs 系统配置），不是用户的分类。用户眼里都是"后台管理"。
3. **"导入与确认"进了二级菜单**（§4.2 资产与空间下）。导入是动词、是工具、是数据运维动作，不是目的地。把后端流程性动作提升为导航目的地，是"后端流程前端化"的标本。正确的家：台账页的"导入"按钮 + 下载中心/数据工具里的任务列表（含行级失败重试，§10 批量语义不变）。
4. **服务费有两个家**。§4.2 菜单树把"服务费结算"列为收款与欠费的二级菜单项，同树"账期工作台"括号里又含服务费维度，§5.5 工作台左轨再有"○服务费"维度切换——同一功能两个入口、两种页面形态，方案内部自相矛盾。
5. **岗位默认落地表缺决策层行**（§5.8）。七行全是执行岗；高管/决策层登录落在运营工作台的预警流——让决策层从一线队列开始一天，方向反了。
6. **反面确认（保留）**：两级深度上限、详情走子路由不进菜单、按权限动态裁剪（无权限即隐藏而非点了 403）、岗位默认落地机制本身、全局搜索覆盖五类对象、深链无权对象显示原因码——全部是 v3.4 的正确投资。

### 💡 第一性原理重构

1. **菜单 = 五问**：一级入口数 = 用户核心问题的数量。有什么（资产）、租给谁（租约）、该收/实收多少（收付）、和谁（往来单位）、今天做什么/盘面如何（工作台）。五个，不多不少。
2. **频率 × 受众决定层级**：全员高频 → 一级；岗位高频 → 一级（岗位域）；少数人低频 → 设置中心或对象页内动作。
3. **动词不进菜单**：导入、确认、核销、补录都是按钮。菜单只放名词（对象与问题）。

## 维度四：功能布局与用户动线（UI Layout & User Motion）

### 🛑 当前致命缺陷

1. **收付工作台三栏过载（§5.5）**。左轨维度切换（4 个单选）+ 中间主表 + 右轨低频危险动作 + 底部合计条。两个问题：① 右轨"更正/作废/范围变更"是低频动作却常驻占据约 15% 宽度——为防误操作把稀有动词供成常驻居民；**隔离应该靠确认弹窗 + 原因 + 审计，不靠永久占地**。② 左轨 4 个维度用表头 tab 即可表达，省出一整列。③ 同一任务（核销一笔钱）的三个动词分布在三个角落：登记收付在右上（Context Trail 行）、核销输入在行内、提交核销在右下——**鼠标行程最大化**。
2. **项目驾驶舱黄金视区错配（§5.2）**。首屏第一行是"模式损益对照条"（月度、财务口径、决策内容），而项目负责人每天的第一问是**运营三问：谁到期、谁欠费、什么空着**。项目的物理身份（资产范围/空间与产权证）沉在页面底部折叠线以下。黄金视区给了月报，日循环挤到第二屏。
3. **账单预览沉底（§5.4 向导步骤二）**。Party/资产选择器"全宽展开"，账单生成预览表在其"下方"。整个向导的存在意义就是那份账单预览（钱的结果），它被放在视觉优先级最低的位置，且步骤一改字段时看不到金额联动——**确认动作是对着表单做，不是对着钱做**。
4. **预警卡四段式作文 + hover 口径卡（§5.1）**。每条预警要说明"发生了什么、为什么、影响什么、下一动作"四段，口径卡四行还要 hover 才可见。队列卡变成小作文，元数据不可见。一线用户的队列卡应该是一行、一数、一动作；口径属于按需深究，放展开区。
5. **双头堆叠（§4.4）**。顶栏之下还有一条独立的 Context Trail 带——每页两条横向带状占位，吃掉约 80–100px 黄金高度。面包屑应并入顶栏一行。
6. **资产台账列表页欠设计（§5.3 只有一段话）**。对比 §5.5 收付的四十行详述，最高频的资产/招商用户的主页面是全案着墨最少的页面：无筛选面板定义、无保存视图、无列配置、无批量操作动线、无租控/列表双视图。

### 💡 第一性原理重构

布局四律：

1. **黄金视区 = 当日决策**。首屏第一眼回答该页最高频的当日问题：驾驶舱答运营三问，收付答今天该收多少/已收多少，向导答这笔合同会生成哪些账单。
2. **动词就近**。一个任务的所有动词聚集在一个交互半径内：核销输入、合计校验、提交按钮同处一条竖向带。
3. **低频危险动作 = 稀有菜单项，不是常驻列**。误操作防护靠交互（确认、原因、审计、幂等——v3.4 已全部具备），不靠布局占地。
4. **预览即承诺对象**。向导中"将生成的账单"是用户的决策依据，必须常驻右栏、随选择实时刷新。键盘优先批核销（行内回车跳行）v3.4 已对，保留并推广到多选批量核销。
