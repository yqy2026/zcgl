# 土地物业资产运营系统重设计 v3.10 最终评审意见：补回物业闭环后的收敛裁决

> **日期**：2026-08-20
> **评审对象**：[土地物业资产运营系统重设计 v3.10](../backend-plans/2026-08-17-land-property-system-redesign.md)
> **对照证据**：[产品复核报告](./2026-08-17-land-property-system-product-review.md)、[市场调研报告](./2026-08-17-market-property-system-research-review.md)、[v3.8.1 外部对抗评审](./2026-08-20-land-property-redesign-v381-external-review.md)、[v3.9 毁灭性评审](./2026-08-20-land-property-redesign-v39-destructive-review.md)

## 一、结论先行

### 1.1 总裁决

v3.10 的主体方向成立：模块化单体、单库事务、空间/承诺义务/现金核销事实分离、高后果命令、历史版本链、幂等回执、全通道权限防泄漏和纵向切片实施都应保留。现有问题不支持“推倒重构”。

但 v3.10 还不能通过终审，也不能直接同步 SSOT 或启动依赖下列未决项的目标态切片。原因不是现有内核过重，而是商业产品与领域事实仍有六处未闭合：

1. **P0：终端租约没有覆盖产权方直租、承租转租和委托运营三种模式的可追溯授权来源与足额校验闭环**；
2. **P1：物业被整体排除，空间从“可出租”到“可交付、可持续运营”之间没有现场闭环**；
3. **P1：Space 仍二选一，物理拓扑地基没有在终审前裁死**；
4. **P1：当前可用、未来供给、法务冻结和现场可运营性仍被压进一个“可租/五态”展示口径**；
5. **P1：续租/展期这一高频商业承诺没有独立语义**；
6. **P1：产权方、上游出租方、委托方、收款归属方等 Party 角色仍可能被同义化使用**。

本轮明确推翻 v3.10 §3.4、§5.8、§11.6、§12 中“物业本期冻结/后续再说”的边界。这个裁决不是因为产品名称中出现“物业”二字，也不是照抄市场模块，而是基于三类证据：

- 产品复核报告 §3.8 已实测原系统存在“资产巡查计划—巡查任务—处理记录”，属于真实业务，不是原型文案；
- 市场调研报告 §5.4 证明成熟资产/物业产品把巡检、维修和现场证据做成独立闭环，而不是资产备注字段；
- 本轮用户产品范围指令明确要求按商业产品思路纳入物业闭环；该决策先进入 v3.11 评审稿，终审后再同步 SSOT。

因此，物业是本期 **P1 现场运营闭环和最终产品签字必要范围**，不是资金/历史正确性级 P0；它必须在最终产品签字前交付，但不阻断可独立推进的资金命令内核。

### 1.2 最终产品本质

系统不是“资产表 + 合同表 + 收款表”，也不是完整物业 ERP。它的商业本质是：

> 让国企城投知道每一处空间是否有权经营、是否能交付使用、承诺形成了什么义务、现金如何清偿，以及现场问题由谁在何时用什么证据关闭。

最终事实模型应从 v3.10 的三条事实轴扩为四条：

```text
                          Party / Organization
                         （主体、角色、授权范围）
                                   |
                                   v
Space / Asset -------- Agreement authority -------- Agreement / Obligation
物理空间与核算资产       出租/转租/代理授权来源         承诺与账单义务
     |                                                     |
     |                                                     v
     +---- Property condition / work -------- Payment flow / Allocation
           现场状态、巡检、工单、交付             现金与核销
                         \                         /
                          Evidence / Audit / Time
                         证据、审计、业务生效时间
```

- **空间轴**：回答“在哪里、是什么、当前物理形态如何”；
- **授权—承诺—义务轴**：回答“谁基于什么授权作出什么承诺、形成什么账单”；
- **现金—核销轴**：回答“钱实际发生在哪里、清偿了哪项义务”；
- **现场状态—处置轴**：回答“空间能否交付和持续运营、问题由谁处理并如何验收”；
- **Party、证据、审计、业务时间**横切四轴，不应被塞入任一单轴。

物业不是第五套资产主数据，也不能反向成为 Space、合同或资金的事实源。它只保存现场事实，并通过明确命令影响“可交付/可运营”派生结果。

### 1.3 对本轮外部意见的最终判断

下表以用户本轮转述的 GLM 回复为评审输入；归档中的既有外部评审只用于交叉验证，不将未写入仓库的对话原文伪装成当前 SSOT 证据。

| 外部意见主张 | 最终裁决 |
|---|---|
| 不判负、不推倒重构 | **采纳**。v3.10 主干成立，做定向修订 |
| 上游授权足额校验是 P0 | **采纳但加深**。不能只补一条 if 校验，必须先有授权来源事实和签约快照 |
| 产权方直租不应被上游协议模型遗漏 | **采纳**。直租无需伪造上游合同，但必须从有效产权/经营权事实冻结不可变授权快照，并与转租/委托统一校验 |
| B0 七项统一限五日过于乐观 | **采纳**。拆成 B0-A 既有裁决和 B0-B 新领域裁决；五日是裁决/核验时间盒，不是实现工期，超期只冻结依赖切片 |
| 最小物业闭环工作量被低估 | **采纳**。B4 按独立 Epic 和五个子切片排期，仍保留在模块化单体内；物业域增量不冒充整个产品最小商业闭环 |
| 空间树矛盾是 P0 | **降为 P1/B0 阻断项**。它阻断 Space 与物业切片，不足以令金额内核判负 |
| 当前可租/未来可租应拆分 | **采纳**，并增加现场可运营性轴 |
| 续租语义缺失 | **采纳**，但续租不得伪装成普通纠错 |
| 不建通用 Right 层 | **采纳**。改建窄而明确的合同授权来源关系 |
| 不补物业闭环 | **不采纳**。原系统实测与市场证据足以支持本期最小物业闭环 |
| “五态”不是数据库单枚举 | **采纳**，但仍需完整投影优先级矩阵 |
| 服务费不存在第二操作入口 | **采纳**。预警入口不等于第二写工作面 |
| 招商锁定附件必然合理 | **证据不足**。采用分级证据策略，不要求每次短锁都上传附件 |
| 菜单整体重构 | **不采纳**。保留五问主干，增加第六入口“物业”即可 |

## 二、终审发现

### F0-1 P0：终端租约缺少完整授权来源事实，直租与非直租均无可靠签约依据

**定位**：v3.10 §2.1“合同覆盖”、§7.4 `RecordAgreement`、§8.1“建立合同并生成账单”、§8.9“项目运营方变更”。

**结论**：方案能证明“某合同覆盖某空间”，却不能证明签约方“基于哪项产权/经营权事实，或哪份上游合同/委托协议，在什么期间、对哪些空间有权签这份终端租约”。`RecordAgreement` 当前冲突项没有授权模式、授权来源、授权期间、空间覆盖和许可动作校验。

**失败场景**：

- 承租转租模式下，上游合同覆盖 A 楼 1–3 层、2026-01-01 至 2027-12-31，并禁止转租；运营人员仍可在 2026-08-20 为 A 楼 4 层录入一份到 2028-06-30 的终端租约；
- 产权方直租模式下，系统仅在提交时读取 Space 当前 `owner_party_id`，没有冻结产权/经营权版本。产权变更、权利到期或经营范围收窄后，既无法证明签约当时有权，也可能把当前权利人错误套到历史合同。

空间没有其他活动终端租约且底价合规时，现有规则可能让上述合同定稿并生成账单。

**破坏的不变量**：

- 合同覆盖不等于出租授权；
- “没有上游合同”只表示产权方直租，不表示无需显式授权依据；
- 终端承诺不得超过授权空间、授权期间和授权动作；
- 上游或产权事实变化不得静默改写既有终端合同，但必须形成可追溯风险。

**最小修订**：不建立通用 `Right` 聚合。授权深模块对外只暴露 `ResolveAgreementAuthority`、`ValidateAgreementAuthority`、`FreezeAgreementAuthoritySnapshot`，内部按经营模式解析来源：

| 经营模式 | 权威输入 | 持久化结果 |
|---|---|---|
| 产权方直租 `direct_ownership` | 签约时点有效且覆盖目标空间/期间的产权或经营权事实版本 | 自动生成不可变 `agreement_authority_snapshot`；不要求人工创建上游 Agreement link |
| 承租转租 `sublease` | 上游租约定稿修订版本 | `agreement_authority_link` + 不可变授权快照 |
| 委托运营 `agency_leasing` | 委托协议定稿修订版本 | `agreement_authority_link` + 不可变授权快照 |

统一授权快照至少包含：

| 字段/关系 | 语义 |
|---|---|
| `target_agreement_id` | 被授权形成的终端租约 |
| `authority_mode` | `direct_ownership` / `sublease` / `agency_leasing` |
| `source_fact_type` / `source_fact_revision_id` | 产权、经营权、上游租约或委托协议的事实类型与定稿版本 |
| `covered_space_id` | 该来源实际承担授权的稳定叶子空间；多空间合同按快照分片精确覆盖 |
| `covered_from/to` | 该来源对该空间承担授权的期间 |
| `permission_snapshot` | 是否允许直租/转租/代理出租及关键限制的不可变快照 |
| `source_identity_snapshot` | 来源主体、权利身份和签约时可见范围的审计快照，不替代当前读取鉴权 |

`agreement_authority_links` 只承担上游协议修订与终端租约的可追溯关联，不为直租伪造一份“上游合同”。三种经营模式的 `RecordAgreement`、商业性合同修订、续租和存量合同导入必须共同校验：

1. 授权快照集合对目标“空间 × 期间”形成无缺口覆盖；
2. 同一空间/期间不得有许可规则冲突的重叠来源；完全同规则重叠也必须显式选定承担来源，不能让系统猜；
3. 每项来源的授权模式、权利主体和许可动作允许当前签约行为：直租签约方必须是产权/经营权事实中的权利主体或其显式有权代表，转租出租方必须是上游承租方或其显式有权代表，委托运营签约方必须来自有效委托关系；
4. 每项来源事实版本在签约时点有效，且未超出空间与期间边界；
5. 所有采用版本和许可快照被固化，后续产权或协议变化不回写历史。

这里的“唯一”指每个目标空间/期间分片只有一个被采用的权威来源，不要求一份多空间终端租约只能引用一份上游协议或产权事实。

来源提前终止、产权/经营权失效或授权范围被合法更正时，不自动终止或改写终端租约；派生 `agreement_authority_defect` 风险。未处置缺陷阻断续租、新增空间和新租户入住交付；通过显式 `ResolveAgreementAuthorityDefect` 记录“替换授权来源 / 法务确认继续履行 / 终止终端合同”等结果、依据和证据后，相关命令按处置结果继续。处置只关闭风险，不回写原签约快照。

**验证门**：

- 产权方直租不需要人工上游 Agreement link，但必须引用有效产权/经营权事实版本并冻结授权快照；只读取当前 `owner_party_id` 的实现不得通过验收；
- 直租来源缺失、失效、空间越界，或转租/委托越过上游期限、空间越界、许可动作被禁止时，均返回稳定冲突码且零写入；
- 同一授权来源并发变更与终端定稿只能有一方按版本规则成功；
- 来源提前终止或失效后，既有终端合同、账单和收款历史不变化，但风险立即可见；未处置前交付被拒绝，处置命令保留结论与证据；
- owner-only、manager-only 用户不能借授权关系看到范围外合同或空间。

### F1-1 P1：物业被整体排除，商业闭环停在“可租”而没有“可交付、可运营”

**定位**：v3.10 §3.4“物业本期冻结”、§5.8“物业动线边界声明”、§11.6“原系统缺口一律后续再说”、§12“明确不做”。

**结论**：上述边界应被 v3.11 明确推翻。空间、租约、欠费都被纳入本期，而巡检、维修、隐患整改和交付验收全部排除，会导致系统只能判断“账面上能不能租”，不能判断“现场能不能交”。这不是完整的存量资产盘活产品。

**证据**：

- 产品复核报告 §3.8：原系统实际存在巡查计划、巡查任务和处理记录；
- 市场调研报告 §5.4：独立维护流程至少包含来源、派发、时限、移动执行、照片、状态、验收、重开，并明确不能塞进资产 CRUD；
- 本轮用户产品范围指令：物业闭环进入本期；该指令先进入 v3.11 评审稿，终审通过后再同步 PRD/spec。

**业务后果**：

- 招商看到“空置可租”，现场却可能漏水、停电或存在安全隐患；
- 合同终止后直接 `ReleaseSpace`，没有退租检查、维修和验收证据；
- 资产管理员、物业人员和招商人员分别在线下维护状态，空间可用口径再次分裂；
- 决策层能看到空置率，却不知道多少空置空间因现场问题无法交付。

**最小修订**：按本文 §三新增本期最小物业闭环，成为第六业务入口；不建设完整物业 ERP、通用 BPM 或设备管理平台。

### F1-2 P1：Space 必须独立落表，项目不能成为物理树父节点

**定位**：v3.10 §2.1“空间/资产原子裁决”、§5.3“空间”、§6.5“路由草案”、§11.3 B0。

**结论**：最终裁决选择独立最小 `Space` 表，删除 `Asset` 双用途分支。物业纳入后，空间同时承载巡检位置、工单位置、交付位置和运营限制，继续让 `Asset` 兼任物理节点会把核算生命周期与物理生命周期耦合。

**拓扑规则**：

- `Project` 是经营上下文和筛选维度，不是物理父节点；
- 新增有效期化 `space_project_assignments`（名称可由 ADR 调整），表达某 Space 在何时由哪个 Project 经营；同一时点一个 Space 至多一个活动 Project 归属；
- 项目切换追加归属版本，不改写历史物业记录；新工单按创建时冻结 `project_id`/运营方，Space 当前页按 `as_of` 解析当前归属，历史读取按对象冻结归属鉴权；
- `Space` 使用类型化邻接树，不强迫所有资产走固定四级深度；
- 合法形态至少覆盖地块、建筑、楼层、房间/铺位、车位和其他可定位空间；
- UI 可以按项目显示虚拟分组根，但该分组不写成 `Space.parent_id`；
- `Asset` 是经营核算对象，可通过有效期关系挂一个或多个 Space，但 Asset 关系不得被反向猜成 Space 的项目归属；
- 合同、巡检、工单和交付引用稳定 `space_id`，不得按名称/编码猜位置。

**必须防御**：自环、祖先环、非法父子类型、重复叶子、孤儿节点、同一时点多父、面积汇总不守恒、同一时点多项目归属、跨项目误挂和叶子空间活动租约重叠。Space 项目切换必须预览活动合同、开放工单和运营限制；这些既有对象保留冻结归属，不能因当前 Project 改变而静默越权或失联。

### F1-3 P1：“可租”混入未来供给，且没有独立现场可运营性轴

**定位**：v3.10 §2.1“空间生命周期”、§2.2“派生状态”、§5.3“可租为默认筛选”、§13.1/§13.2 可租口径。

**结论**：`可租 = {空置可租, 临期} - {停用, 待确权}` 把当前可交付空间和未来可能释放空间混在一起。物业进入后，还必须表达“商业上可签但现场尚不可交付”的情况，不能继续增加一个更大的单状态枚举。

v3.11 应分成五个正交维度：

| 维度 | 权威来源 | 典型值 |
|---|---|---|
| 合同承诺 | 合同覆盖、终止、续租/变更 | 无活动租约、活动租约、临期、已终止 |
| 实际占有 | 入住交付、退租交还事实 | 未交付、已占有、待交还、已交还 |
| 权属/合规 | 产权和人工冻结事实 | 正常、待确权、限制经营 |
| 行政可用 | `space_state_marks` | 启用、停用 |
| 现场可运营 | 物业限制、交付验收 | 可交付、受限、不可用、待评估 |

派生集合改为：

```text
当前可交付 = 无活动终端租约
          AND 实际占有 ∈ {未交付, 已交还}
          AND 无活动锁定
          AND 权属/合规正常
          AND 行政启用
          AND 现场可运营 = 可交付

未来供给 = 临期合同覆盖
        AND 已知预计释放日
        AND 未命中永久性合规冻结
```

未来供给必须显示“预计释放日”和“现场评估状态”；退租检查未完成时显示“待评估”，不得以当前可租数量计入招商现货。合同终止、实际交还占有和再次可交付是三个不同事实：终止不自动证明租户已交还，交还后即使仍需维修也应表现为“空置 + 现场不可用”，不能用“继续在租”掩盖维修期。主标签只用于扫描，页面同时展示阻断原因徽章，不能靠一个枚举丢掉多维事实。

建议主标签优先级：待确权/限制经营 → 停用 → 现场不可用 → 已占有/活动租约 → 已锁定 → 临期 → 空置。该顺序只决定展示，不反向写事实。

### F1-4 P1：续租/展期不是普通纠错，必须有商业承诺语义

**定位**：v3.10 §5.4“录入—确认—生成账单—更正”、§7.4 `Start/FinalizeAgreementCorrection`、§8.6“合同更正”。

**结论**：方案没有说明合同到期后的续租、补充协议展期和新合同续签如何处理。把延长期限塞进普通更正会混淆“修正错误”与“形成新承诺”；一律终止重签又会割裂连续经营关系。

**最小修订**：将合同变化分成三个显式概念：

1. **录入纠错 `AgreementCorrection`**：修正录错事实，保留前后值、原因和证据；不得借此形成新商业承诺；
2. **商业变更 `AmendAgreement`**：租金、空间范围、免租期等协商条款变化，追加商业版本，只重算受影响的未来未结义务；
3. **续租/展期**：按真实法律文书产生两类结果：
   - 新合同续签：创建 successor Agreement，保存 `renewed_from_id`；
   - 补充协议展期：走 `AmendAgreement` 追加商业版本，保留补充协议证据。

续租入口可以统一，但领域结果不能混为同一操作。续租与商业变更必须重新校验授权来源、空间覆盖、活动锁定、底价、现场限制和未来账单；历史账单、已收款和旧条款不重建。successor 关系必须约束单一直接前序/后序，并显式表达允许的时间间隔与禁止的重叠。

### F1-5 P1：Party 角色必须按关系来源区分，不能只做词汇统一

**定位**：v3.10 §3.4、§4.3、§5.6、§7.4 和 §8.4。

**结论**：“产权方”“业主方”“上游出租方”“委托方”“资金归属方”“实际付款方”可能由同一 Party 承担，但不是同一业务角色。若因界面简化而把它们从 `Asset.owner_party_id` 或合同对手方反推，会造成签约资格、权限和资金归属错误。

v3.11 词汇表至少应裁死：

| 角色 | 来源 |
|---|---|
| 产权方 | 资产当前产权事实及其历史审计 |
| 上游出租方 | 上游租赁合同的签约角色 |
| 委托方 | 委托协议的授权角色 |
| 终端承租方 | 终端租约的承租角色 |
| 运营方 | 项目运营方有效期关系或合同冻结快照 |
| 资金归属方 | 流水类型 × 经营模式推导 |
| 实际收付对方 | 具体流水事实 |
| 物业服务方 | 物业工单或服务关系派生，可与运营方不同 |

Party 主档不手工勾选永久角色；当前角色仍由有效来源派生。前端可按场景显示“业主方”等通俗词，但契约、权限和统计必须引用明确来源角色。

### F2 P2：四项定向修订

1. **命令落点措辞**：§5.9“有且仅有一个动作落点”改为“一个规范执行工作面，可有多个携带上下文的发起入口”。
2. **催缴边界措辞**：§11.6 删除“催缴跟进不启动”的笼统表述；保留联系记录和承诺还款日，但仍不建催缴工单。
3. **锁定证据分级**：短期招商锁定要求结构化原因、意向方、到期日和审计；超期、续锁或高价值空间再要求附件或升级权限，不强制每次短锁上传文件。
4. **候选架构降噪**：§7.7 保留性能预算和建模条件，四个读模型名称移入非约束附录；`scope_diagnosis:read` 只有确认真实排障岗位后才实现，不发布无人使用的休眠端点。

## 三、本期最小物业闭环

### 3.1 产品边界

物业域回答一个问题：

> 哪些空间需要现场处理、由谁负责、何时完成、证据是什么，以及处理结果是否允许空间交付或恢复运营？

本期必须覆盖：

1. 周期巡检计划；
2. 巡检执行和逐项结果；
3. 临时报修/隐患上报；
4. 工单派发、处理、提交验收、驳回和重开；
5. 处理前后照片、附件和位置证据；
6. 关键隐患形成空间运营限制；
7. 入住/退租交付检查；
8. 物业岗位工作台和移动 Web 现场操作；
9. 权限、审计、超期和可下钻指标。

本期明确不做：

- 通用 BPM、跨域任务引擎和任意流程编排；
- 住户/租户门户、投诉客服和收费门户；
- 供应商招采、合同、报价审批、结算和付款自动生成；
- 设备台账、备件库存、保养策略和预测性维修；
- 能耗、IoT、门禁、访客、地图和数字孪生；
- 原生 App、离线同步和复杂调度地图；
- 事故上报、应急指挥、演练、法定安全报表；
- 完整装修项目、资本工程和成本控制。

一般安全巡检和隐患整改纳入本期；事故/消防专项监管系统不纳入。这样既补回真实现场闭环，又不把本系统扩成完整 IWMS。

### 3.2 最小事实模型

| 事实 | 必须保存的内容 | 不得承担的职责 |
|---|---|---|
| `InspectionPlan` | 适用空间集合、检查模板版本、频率、责任组织、启停状态、生效期 | 不保存“已完成率”累计字段 |
| `InspectionRun` | 计划来源或临时来源、空间、执行人、计划时间、实际时间、提交版本 | 不直接改 Space 租赁状态 |
| `InspectionReview` | 对需要复核的交还/入住检查保存复核人、结论、原因、时间和证据 | 普通例行巡检不强制多一层审批 |
| `InspectionFinding` | 检查项结果、严重度、描述、证据、是否要求整改 | 不作为可手工关闭的风险缓存 |
| `PropertyWorkOrder` | 来源 finding/报修/交付检查、空间、内部责任人、可选服务方 Party、优先级、到期日、当前版本 | 不变成通用跨域任务 |
| `PropertyWorkAttempt` | 每次处理说明、开始/提交时间、操作者、处理前后证据 | 驳回后不得覆盖旧尝试 |
| `PropertyWorkAcceptance` | 验收人、结论、原因、时间、证据 | 不能由执行人默认自验收高风险工单 |
| `SpaceOperationalRestriction` | 空间、原因、唯一来源、类型、阻断级别、生效时间、解除事实 | 不替代停用、待确权或合同状态；同一空间可并存多条 |
| `SpacePossessionReturn` | 退租合同、空间、实际交还时间、经办人和交还检查引用 | 只解除占有，不宣称维修完成或可交付 |
| `SpaceHandoverRecord` | 入住方向、合同、空间、已复核检查引用、双方/经办人、证据、时间 | 不修改合同历史或生成收付款 |

工单当前状态可以缓存，但权威历史由状态转移和处理尝试重建；关闭后不得编辑旧证据，修正通过追加新尝试或重开完成。

### 3.3 状态机

**巡检计划**：

```text
draft -> active <-> paused -> retired
```

同一计划、同一周期、同一空间最多生成一次巡检执行；调度重试必须幂等。

**巡检执行与交付复核**：

```text
InspectionRun:
  scheduled -> in_progress -> submitted
       \---------------------> cancelled（有原因、有权限）

InspectionReview（仅交还、入住等需要复核的检查）:
  pending -> accepted / rejected
  rejected -> 创建 successor InspectionRun
```

例行巡检提交即完成执行，不强制复核；交还/入住检查必须形成 `InspectionReview`。提交后检查项和证据不可原地覆盖；例行巡检错误走补充记录，交付类检查驳回后创建新的执行版本并引用被驳回版本。

**物业工单**：

```text
open -> assigned -> in_progress -> pending_acceptance -> closed
  \          \             \             |
   \---------- cancelled     <--- rejected+
                                      |
closed --------------------------> reopened -> in_progress
```

- `rejected` 不保存为脱离流程的终态，而是追加验收拒绝事实并回到 `in_progress`；
- `reopened` 追加重开事实并开启新处理尝试，不覆盖已关闭尝试；
- `cancelled` 必须有原因，关键隐患存在活动运营限制时不能用取消绕过整改；
- 超期由 `due_at` 与当前状态派生，不手工翻转。

### 3.4 关键命令

| 命令 | 结果 | 关键失败条件 |
|---|---|---|
| `CreateInspectionPlan` | 草稿计划和模板版本 | 空间越权、周期非法、无检查项 |
| `Activate/Pause/RetireInspectionPlan` | 计划生命周期变更 | 版本陈旧、越权、退休后仍试图激活 |
| `GenerateInspectionRuns` | 按计划/周期/空间幂等生成执行 | 计划非活动、范围失效、周期重复 |
| `StartInspectionRun` | 锁定执行人和检查版本 | 重复执行、空间越权、版本陈旧 |
| `CancelInspectionRun` | 追加取消事实 | 已提交、无原因、越权、版本陈旧 |
| `SubmitInspectionRun` | 不可变结果、finding、必要工单/限制 | 检查项缺失、证据缺失、版本漂移 |
| `ReviewInspectionRun` | 为交付类检查追加通过/驳回复核；驳回时创建 successor 执行 | 非交付类检查、职责冲突、版本陈旧 |
| `AppendInspectionSupplement` | 为已提交例行巡检追加补充记录 | 改写原记录、无原因、越权 |
| `ReportPropertyIssue` | 临时 finding 和工单 | 无空间、越权、重复请求 |
| `AssignPropertyWork` | 当前内部责任人、可选服务方和派发审计 | 被派人无有效岗位/范围、版本陈旧 |
| `StartPropertyWork` | 新处理尝试 | 非责任人、非法状态、版本陈旧 |
| `SubmitPropertyWork` | 处理结果和证据，进入待验收 | 必填结果/证据缺失、版本陈旧 |
| `Accept/RejectPropertyWork` | 验收事实；关闭或退回处理 | 职责冲突、版本陈旧、范围失效 |
| `ReopenPropertyWork` | 新重开事实和处理尝试 | 无原因、越权、已有关联新工单 |
| `CancelPropertyWork` | 追加取消事实 | 关键限制未另行处置、无原因、越权、版本陈旧 |
| `RestrictSpaceOperation` | 新增一条活动运营限制 | 无唯一来源、空间越权、同一来源重复 |
| `ReleaseSpaceOperationalRestriction` | 解除指定限制并保留原链 | 指定来源未验收、仍有关键 finding |
| `RecordSpacePossessionReturn` | 记录实际交还并解除占有；可同时形成运营限制 | 交还检查未复核、合同/空间不匹配 |
| `RecordSpaceHandover` | 记录新租户入住交付 | 检查未复核、活动授权缺陷、命中交付阻断策略、合同/空间不匹配 |

每个物业状态变更都复用统一命令执行器：请求携带 `expected_version` 和幂等键，事务内重鉴权、按固定顺序锁行，返回稳定回执/冲突码并写审计。移动网络超时后以原键查询回执，不得重复创建巡检、工单、限制或交付事实。物业命令不与资金事务混合，但同一命令内的 finding、工单、限制、证据链接和审计必须原子提交。

### 3.5 与现有领域的关系

| 领域 | 关系与约束 |
|---|---|
| Space | 每个计划、执行、finding、工单、限制和交付必须引用 `space_id`；物业事实不写租赁状态 |
| Project | 通过 `space_project_assignments` 有效期关系提供当前经营范围；巡检/工单创建时冻结 Project/运营方，历史可见性不随当前归属改写 |
| Asset | 可选引用 `asset_id` 表示核算资产或现有可维护对象；无设备台账时用空间 + 部位描述，不虚构设备身份 |
| Contract | 入住/退租事实引用合同；合同终止、实际交还和再次可交付分别建模；未来合同可先签，但授权缺陷或交付阻断策略拒绝入住交付 |
| Possession/Readiness | `RecordSpacePossessionReturn` 解除占有；活动运营限制继续使其“空置但不可交付”，维修验收不作为空置成立条件 |
| Party | 报修方、承租方、服务方可引用 Party；服务方只能来自工单的 `provider_party_id` 或后续显式服务关系，不从内部 assignee 推断 |
| User/Organization | 责任人和验收人是内部用户/组织；被派发不自动扩大其数据范围 |
| Payment | 本期不自动生成供应商应付或付款；报价/发票只能作为非财务证据，不进入经营金额指标 |
| Evidence | 已提交检查证据、处理前后照片和验收证据不可变；修正只追加 |
| Notification | 通知只是提醒通道；物业工单自身才有责任人、期限和状态，不能用已读状态代替处理状态 |

### 3.6 空间与合同的接线规则

1. **签约与交付分离**：未来起租合同可以在现场维修尚未完成时定稿，但必须展示运营限制和预计交付风险；新租户 `RecordSpaceHandover` 同时校验无活动授权缺陷且未命中交付阻断策略。
2. **限制策略而非“有记录即阻断”**：同一 Space 可有多条不同来源的活动限制；按 `restriction_type × blocking_level` 确定是否阻断招商展示、签约、续租、入住交付或已占用空间继续使用。普通观察项只展示风险，不自动成为合同障碍。
3. **当前房源口径**：任一命中“当前可交付”阻断策略的活动限制使空间退出当前可交付，但不删除空间、改变合同历史或伪装为仍在租。
4. **退租交还**：`TerminateAgreement` 处理合同承诺；交还检查复核后由 `RecordSpacePossessionReturn` 记录实际交还并解除占有。若发现问题，同事务生成 finding/工单/限制，空间表现为“空置 + 现场不可用/待评估”，不等待维修完成才变空置。
5. **维修与再交付**：工单验收关闭后只解除对应来源限制；所有交付阻断限制解除且其他维度正常时，空间自然重新进入当前可交付，不再用一个 `ReleaseSpace` 同时承担占有解除和维修验收。
6. **入住交付**：入住检查通过、无活动授权缺陷且未命中交付阻断策略才能形成入住交付记录；交付事实不反向修改合同生效日。
7. **关键隐患**：现场人员提交 `critical` finding 时，同一事务创建具有唯一来源的临时运营限制；解除必须由具备 `property:accept`/`property:restrict` 的不同职责人员完成。

“物业”是零子节点高频目的地，页内使用三组 tab：

- **现场任务**：我的待执行、待验收、超期、全部；
- **巡检计划**：计划、下一次执行、覆盖空间；
- **记录**：已关闭工单、巡检历史、交付记录。

现场执行必须支持移动 Web 的拍照、附件、检查项勾选、提交和回执查询；本期不承诺原生 App、离线执行或后台定位。

| `property:work` | 内部维修人员 | 提交处理结果，不自验收关键工单 |
| `property:accept` | 物业负责人、项目负责人 | 验收、驳回、重开 |
| `property:restrict` | 物业/安全负责人 | 创建和解除运营限制 |
| `property:handover` | 物业、合同运营、项目负责人 | 记录实际退租交还或新租户入住交付 |

物业域必须进入 v3.10 §9.2 的全通道矩阵：列表和 count、详情、工作台数字、搜索、通知、附件、导出、审计、命令回执和异步计划生成都按对象授权事实过滤。Space 当前页按 `space_project_assignments(as_of)` 解析，既有巡检、工单、限制和交付按创建时冻结的 Project/运营方授权；项目切换不得静默改写历史可见性。无权用户不得从“某空间有几条工单、是否有照片、由哪家服务方处理”等元数据反推范围外事实。

### 3.9 指标

本期只提供可由生命周期事实直接派生的指标：

- 待执行、待验收、超期工单数；
- 关键未关闭隐患数；
- 因现场问题不可交付的空间数和面积；
- 平均首次响应时长、平均关闭时长；
- 一次验收通过率、重开率；
- 巡检计划按期完成率。

不建立“物业服务指数”“安全分”“供应商评分”等无真实口径的综合分数。指标必须可下钻到计划、执行、工单、尝试、验收和证据。

## 五、实施路线重排

### 5.1 B0：分层裁决时间盒，不伪装成实现工期

五个工作日是完成事实核验、产品裁决和 ADR/G0 签字的时间盒，不是完成模型、迁移、接口、页面和测试的实现期限。B0 按成熟度拆成两组：

**B0-A：既有裁决收口**

1. 押金选择最小域；
2. 支付登记锚点集合语义；
3. 服务费版本骨架复用边界。

这些议题已经经过多轮评审，五个工作日内应以“签字 / 明确拒绝并记录替代方案”结束，不再扩散选项。

**B0-B：新领域裁决与事实核验**

1. Space 独立表、类型化拓扑和有效期化 Project 归属规则；
2. 产权方直租、承租转租、委托运营三种授权模式及来源异常处置；
3. 物业严重度、运营限制策略、验收职责和交付阻断规则；
4. 续租两类法律文书的领域结果。

B0-A 与 B0-B 自同一启动日并行，各自拥有五个工作日，不串行累加。B0-B 第五日必须产出“正式裁决”或“补证决定”之一；补证决定必须写明缺失证据、责任人、受影响切片和最多五个额外工作日的截止日，到期仍不能裁决则进入 `blocked` 并升级产品负责人，不得滚动续期或以临时假设开工。任一项超期，只冻结其依赖切片；可信度修复、共享命令地基、已完成裁决的资金内核和其他无依赖工作可继续。物业 B0-B 未关闭不阻断资金主链实现，但阻断物业 Epic 相关切片和最终产品签字。

### 5.2 后端双工作流与集成顺序

```text
B1 共享地基
  命令执行器 / 幂等回执 / 审计 / 权限上下文
  Space 身份、拓扑与有效期化 Project 归属 / 证据不可变规则

工作流 A：商业主链
  A1 授权解析、授权快照与合同-空间覆盖
  A2 招商锁定 / 合同定稿 / 录入纠错 / 商业变更 / 续租 / 终止 / 账单与服务费义务
  A3 支付流水锚点 / 分摊核销版本 / 押金现金动作 / 坏账

工作流 B：物业闭环（独立 Epic）
  B4.1 报事 -> 工单 -> 处理 -> 验收/驳回 -> 重开
  B4.2 多来源 SpaceOperationalRestriction 与策略矩阵
  B4.3 周期巡检计划、幂等生成、执行与复核
  B4.4 物业侧交还/入住检查、复核与交还/交付事实命令
  B4.5 移动 Web、指标、通知与全通道权限加固

集成切片（不重复实现 B4.4，只编排跨域前置条件与回执）
  I1 合同终止 -> B4.4 实际交还 -> 整改 -> 恢复当前可交付
  I2 新合同 -> 授权复核 -> B4.4 现场检查与入住交付

B5 组合投影
  工作台查询 / 四轴指标 / 水位与反向权限测试
```

工作流 A 与工作流 B 在所需 B0 裁决和 B1 地基稳定后并行开发；下节编号表达可独立验收的增量与跨域发布依赖，不要求团队按编号完全串行。B4 是工程量真实、可以独立验收的工作流/Epic，不是“小功能包”；它仍属于同一模块化单体和单库事务边界，不因独立排期拆成微服务。B4.4 负责物业侧检查、复核以及交还/交付事实命令，I1/I2 只编排合同、授权、限制和 B4.4 的跨域前置条件与稳定回执，不重复建事实或命令。物业费用与服务方结算不接入 A3，避免本轮新增第二条金额事实轴。

### 5.3 产品纵向切片与最小交付定义

以下编号是交付增量和依赖关系，不是禁止并行开发的瀑布顺序：

1. **共享空间地基**：稳定 `space_id`、Space 树、项目经营归属和合同占用口径；物业限制投影未接入前，现场状态一律为“待评估”，不得宣称“当前可交付”；
2. **商业主链 A1**：产权方直租/承租转租/委托运营的授权解析、覆盖校验与快照冻结；
3. **商业主链 A2**：招商锁定 → 合同定稿/续租 → 合同义务与账单；
4. **商业主链 A3**：流水 → 核销 → 押金/坏账；
5. **物业增量 B4.1/B4.2**：临时上报 → 派发 → 处理 → 验收/驳回/重开 → 运营限制解除；
6. **物业增量 B4.3**：巡检计划 → 幂等生成 → 移动执行 → finding/工单；
7. **物业增量 B4.4/B4.5 与现场投影**：交还/入住检查与复核 → 交还/交付事实命令 → 移动 Web、指标、通知和权限加固；接入 B4.2 限制策略后才发布“当前可交付/不可交付”现场投影和阻断原因；
8. **退租集成 I1**：合同终止 → 调用 B4.4 记录占有交还 → 带限制的空置 → 整改/验收 → 恢复当前可交付；
9. **入住集成 I2**：新合同 → 授权复核 → 调用 B4.4 检查并在无阻断时记录交付；
10. **工作台、往来方与设置中心**：四轴汇总下钻、跨域档案、组织、权限和审计。

“最小可交付”必须分三层表述，不能互相替代：

- **物业域最小可用增量**：第 5 条报事—处理—验收/重开闭环真实跑通；这证明物业深模块成立，但不等于整个产品可商业交付；
- **整个产品最小商业闭环**：第 1–4 条空间/授权—合同—义务—收付核销真实跑通；这是商业主链的最低交付线；
- **本期最终产品签字范围**：商业主链与物业闭环均完成，并至少通过 I1 退租交还、I2 入住交付两个跨域集成切片。

### 5.4 发布边界

- 不允许新旧物业任务双写；物业旧数据若迁入，按计划、任务、处理记录分层映射，无法映射的归档备查；
- 物业上线单向依赖稳定 `space_id`；Space、合同和资金可以先行发布，物业不得先用 Asset/名称临时挂工单再迁移；物业限制投影未上线或功能关闭时，前端必须显示“现场待评估”，不得将缺少现场事实的空间标成“当前可交付”；
- 首笔物业工单新写后只做前向修复，不回退为资产备注；
- 资金首笔新写后的不可回滚规则继续沿用 v3.10；物业与资金不可回滚点分别声明；
- 通知可晚于工单上线，但工单状态不得依赖通知送达。

## 六、验收门

### 6.1 出租授权与合同

1. 产权方直租不要求人工上游 Agreement link，但任一空间/期间分片缺少有效产权/经营权事实版本或不可变授权快照时，定稿零写入；
2. 承租转租或委托运营的任一空间/期间分片没有上游授权覆盖时，定稿零写入；
3. 多来源授权快照集合存在授权缺口或许可冲突重叠时，定稿零写入；
4. 终端租约结束日晚于任一承担来源的授权结束日，定稿零写入；
5. 来源明确禁止当前直租/转租/代理出租动作，或签约方与来源主体关系不成立（直租权利主体/有权代表、上游承租方/有权代表、有效受托运营方）时，合同定稿零写入；
6. 任一产权、经营权、上游租约或委托协议来源版本在预览后变化，提交返回 409；
7. 来源提前终止或失效只派生授权缺陷，不改写终端合同、账单和收款；未处置缺陷阻断新租户入住交付，合法处置后按处置结果继续且原快照不变；
8. 续租和商业变更重新校验授权、底价、空间覆盖和现场限制；录入纠错不能延长期限或改变协商条款。

### 6.2 Space 和可交付口径

1. 项目不写入物理父子关系，但 `space_project_assignments` 必须给出唯一活动经营归属和历史版本；
2. 环、自父、非法父子类型、同一时点多父/多项目归属和重复叶子均被拒绝；
3. 项目归属切换后，当前 Space 页面按新归属鉴权，既有工单仍按冻结归属保留历史可见性；
4. 临期空间只进入未来供给，不进入当前可交付；
5. 任一命中交付阻断策略的活动运营限制使空间退出当前可交付，解除后按其他事实重新派生；
6. 实际交还后空间可为“空置 + 现场不可用”，不得因维修未完成继续显示在租；
7. 工作台、空间页、物业页对当前可交付和不可交付集合完全一致；
8. 物业功能未上线或被关闭时，合同定稿—账单—流水—核销仍可完整运行；现场状态显示“待评估”，任何页面不得把缺少物业评估的数据标成“当前可交付”；
9. 主标签优先级和全部阻断徽章在组合状态下无信息丢失。

### 6.3 物业闭环

1. 同一巡检计划、周期和空间并发生成 20 次只产生一个 `InspectionRun`；
2. 计划退休、巡检取消、工单取消均只能通过对应命令，缺原因、越权或版本陈旧时零写入；
3. 提交巡检缺检查项或必需证据时零写入；
4. 交还/入住检查没有有效 `InspectionReview(accepted)` 时，占有交还/入住交付命令拒绝；
5. `critical` finding、工单和具有唯一来源的临时运营限制同事务成功或失败；同一空间可同时存在多来源限制；
6. 工单处理提交后旧证据不可覆盖；验收驳回开启新处理尝试；
7. 关闭后重开保留原关闭、验收和证据链；
8. 执行人不能验收要求职责分离的关键工单；
9. 被派发用户没有 Space 范围时仍不得读取工单，派发不产生授权；
10. 撤权后下一请求、附件下载、命令回放和移动端重试立即拒绝；
11. 退租交还后即解除占有；活动阻断限制只使其不可交付，不得让其继续显示在租；
12. 活动授权缺陷或命中交付阻断策略时入住交付拒绝，但未来起租合同可按规则定稿并显示风险；
13. 普通观察型限制不阻断签约/交付，只按策略显示风险；
14. 附件上传成功但数据库失败时不留下业务链接，暂存 blob 按 TTL 清理；
15. 命令成功但响应超时，原幂等键回放不重复创建巡检、工单、限制、交还或交付记录；
16. 390px 宽移动 Web 可完成检查项、拍照、提交和查看回执，无横向滚动；
17. 无权用户在 count、搜索、通知、导出、审计和附件元数据中均不能推断范围外工单存在性。

## 八、最终签字条件

### 8.1 量化结论

- **裁决**：退回定向修订，不推倒重构；
- **P0**：1 项；
- **P1**：5 项；
- **P2**：4 项；
- **可以立即同步 SSOT**：否；
- **可以立即开始依赖未决 B0/P0 的目标态切片**：否；
- **实施与签字边界**：B0 五日是裁决/核验时间盒而非实现工期；B4 按独立 Epic 排期，物业域最小增量不替代整个产品商业主链；
- **可以继续的独立工作**：阶段 A 可信度缺陷修复、无争议的命令执行器/审计地基、只读数据核查，以及在支付锚点/押金/服务费各自 B0-A 裁决完成后不依赖 Space/授权/物业的资金内核切片。

### 8.2 v3.11 方案签字门

v3.11 完成以下事项后，只需定向复核，不再做第五轮全量毁灭性评审；通过后才同步 SSOT、拆实施票据并进入目标态开发：

1. 统一授权深模块能区分产权方直租、承租转租和委托运营：直租从有效产权/经营权事实冻结快照且不伪造上游合同，非直租通过窄 link 精确表达多来源空间/期间覆盖，并均定义稳定冲突码和失败用例；
2. Space 独立表裁决落定，项目与物理树分离，并定义有效期化 Space—Project 经营归属和历史鉴权规则；
3. 合同终止、实际交还、当前可交付、未来供给、合规冻结和现场可运营性口径唯一；物业未上线时“现场待评估”的降级口径明确；
4. 物业最小事实、状态机、全转移命令、限制策略、权限、页面、交付接线和不做项完整；
5. 录入纠错、商业变更和续租/展期三种语义不再混用；
6. Party 角色来源词汇表唯一；
7. 押金、支付锚点和服务费骨架完成 B0-A 签字；Space/授权/物业策略/续租完成 B0-B 事实核验和责任人签字；B0 条款保留并行起算、五日非实现工期、补证最多额外五日、不得滚动续期和超期 `blocked`；

### 8.3 本期产品交付签字门

本期产品签字只在 v3.11 方案签字、SSOT 同步和实施完成后进行，必须同时满足：

1. 相关模型、迁移、命令、API、页面、权限和审计实现完成，受影响门禁通过；

3. B4.1–B4.5 每个子切片均具备 §6.4 定义的自动化测试和可引用验收证据；

6. 首笔资金与首笔物业新写后的前向修复边界、监控、回执查询和回滚禁区已经签字。

### 8.4 最终评价

v3.10 最强的部分仍是金额单一事实轴、历史不可静默改写、幂等与权限防泄漏；这些内容不应因产品增补而削弱。最危险的假设则是：有合同覆盖就等于有权出租、有空置状态就等于现场可交付、把物业整域排除仍能称为完整的土地物业资产运营产品。

v3.11 应做的不是增加一批菜单，而是把物业做成一个深模块：外部只有巡检、上报、处理、验收、交付几个清晰接口，内部集中承担计划生成、状态历史、证据、权限、运营限制和空间口径联动。这样既补回商业闭环，也不会把现有系统拖进通用 BPM、设备 ERP 或物业收费平台。
