## 1. 最终结论

毁灭性评审不整体接受，v3.13 也不继续修补为现行方案。

处理原则只有三种：

1. **接受**：问题判断和解决方向都成立，进入 v4.0。
2. **调整后接受**：问题成立，但评审给出的对象、流程或实施顺序不符合真实经营，按运营管理方决策重写后进入 v4.0。
3. **否决**：缺少业务依据、扩大范围或混淆理想模型与实际约束，不进入现行方案。

最终采用的不是“毁灭性评审版”，也不是“v3.13 修订版”，而是独立裁决后的 v4.0。

## 2. 评审意见最终处置

### 2.1 直接接受

| 评审意见 | 处置 | v4.0 落点 |
|---|---|---|
| 金额不能靠累计字段或手工状态形成第二事实源 | 接受 | 实收、实付只来自有效经营收付流水及分配；退款、核销、抵扣、减免分别记录 |
| 历史合同、账单、收付和归属不得被当前主数据静默改写 | 接受 | 合同、Space、项目归属和账单冻结签约/生成时快照；更正追加记录 |
| 同一 Space 同一期间不能生效两份终端合同 | 接受 | 事务内重验加数据库区间排斥约束，前端提示不作为最后防线 |
| 银行流水不能因高置信匹配而静默入账 | 接受 | 银行原始行只作证据，财务确认、运营认领和分配后才形成经营收付事实 |
| 工作台、空间详情、可租视图和租控图必须消费同一供给判断 | 接受 | 可租状态由合同占用、维修封闭和有效限制统一派生 |
| AI/OCR 关键字段需要按风险逐项确认 | 接受 | 主体、Space、期间、金额、计费规则和授权来源必须人工确认 |
| 一线工作台与管理驾驶舱不能使用同一首屏结构 | 接受 | 原型按岗位任务和管理决策分别组织，不复制同一组卡片 |
| 实施必须按可走通的纵向业务链交付 | 接受 | 承租转租 S1–S3、委托代理 S4–S5，禁止横向铺完全部地基后再交付 |
| “释放收入潜力”等伪精确指标会误导 | 接受 | 删除面积乘底价式伪收入指标；确定义务与预测严格分开 |

### 2.2 调整后接受

| 评审意见 | 原评审方案 | 最终处置 |
|---|---|---|
| Space、Asset、Project 必须拆清 | Space/Right/Motion 作为认知原子 | 保留 Space、登记单元、Asset、Project 分层；不采用三原子完整本体 |
| Project 只应表示日常运营责任 | 同一 Space 同时只能有一个当前 Project | 接受，但物业、改造、专项招商和合规责任另建独立责任关系，不能全塞进 Project |
| 跨项目协议不能只靠共享文件猜身份 | 原评审仍保留项目记录共享扫描件 | 改为一份签署文书身份和版本链，关联多个项目经营记录；项目账款与历史独立 |
| 企业需要补招商前端链路 | 建最小 Opportunity，包含报价和锁定 | 改为租赁意向加接受/反提/拒绝；取消正式报价对象和 Space Lock |
| 企业需要催收责任和证据 | 一个永久 `Party × Project` 催收事项，结清后再次激活 | 改为一个欠费账户加多个独立催收案件；关闭案件不重开，法务案件关联保留 |
| 银行流水应进入首期 | 银行流水是现金事实来源 | 文件导入进入首期，但银行原始行不是经营现金事实；确认业务性质后才生成收付流水 |
| 代理服务费需要从产权方实收租金出发 | 按直租实收和比例自动派生服务费 | 产权方逐笔确认到账，只用于试算；双方确认并上传双方盖章对账单后形成应收，实际收款独立登记 |
| 合同生效必须有治理门 | 评审侧重授权和底价 | 增加外部合同审批证据门；本系统不建 BPM，承租转租由运营方审批、代理直租由产权方审批 |
| 权属和出租授权需要可信控制 | 建统一权益读取和专业写模型 | 运营方录入、另一名授权人员复核；终端合同生效时验证 Space、期间和用途并冻结快照 |
| 现场问题必须与签约连起来 | 物业事项作为专业 Motion | 漏水修复等建立签约前置条件并可转物业工单；运营方授权人员可留痕豁免 |
| 报价低于底价必须受控 | 报价例外控制 | 没有正式 Quote；改为意向/合同条件低于有效底价时触发针对本次条件的例外审批 |
| 原型需要任务化导航 | 盘活招商、租约经营等多域入口 | 保留共享工作面，以模式标签和岗位默认落点组织；不把内部对象名放入菜单 |

### 2.3 明确否决

| 评审意见或方案 | 处置理由 |
|---|---|
| Space、Right、Motion 作为覆盖全域的最终本体 | Right 混合物权、合同权、债权、押金和限制；Motion 混合命令、事件和跨天事项，不能稳定约束专业写模型 |
| 建通用 Right 或 Motion 根表 | 会形成字段稀疏、约束松散的万能对象；产权、授权、租约、账单、催收和物业继续使用专业模型 |
| 产权方直租路径优先实施 | 不符合运营方“以承租转租为主、委托代理为辅”的真实业务结构 |
| 正式报价对象 | 实际证据是潜在承租人提交租赁意向，运营方执行条件审议；单独 Quote 会制造不存在的业务阶段 |
| Space 锁定或押金锁位 | 运营方明确不需要锁定；多个客户可洽谈，只有生效合同产生排他占用 |
| 银行导入行直接等同租金、押金或服务费事实 | 导入行可能是合并付款、第三方代付、冲正、手续费或内部划拨，必须人工确认业务性质 |
| 永久 `Party × Project` 单一催收案件 | 不同欠费周期、合同和争议会被混成一案，破坏责任、周期和结案统计 |
| 在本系统建设合同审批流 | 已有独立合同审批系统；重复建设会造成两套审批结果和责任冲突 |
| 先建设全部 Space/Right/资金/物业横向底座再交付 | 会长期只有表和接口，没有岗位能完成一条真实业务 |
| 把现有代码投资当作保留领域模型的理由 | 代码只能作为迁移来源，不能反向决定产品对象、导航和业务边界 |

## 3. v3.13 原优化方案处置

v3.13 已移入 `docs/archive/backend-plans/`，状态为“被 v4.0 取代”。不再继续在原正文中追加 v4.0 规则。

### 3.1 保留进入 v4.0 的部分

- 金额单一事实轴、有效分配和历史不可变原则。
- 全通道权限、数据范围和附件防泄漏。
- 高后果命令的幂等、事务内重验、固定锁序和数据库约束。
- Space、Asset、Project 分层方向及专业权利写模型。
- 合同更正、商业变更、续租和终止语义分开。
- 物业巡查、工单、限制、交还与交付不混成合同状态。

### 3.2 被 v4.0 替换的部分

- 项目合同副本共享扫描件 → 签署文书加项目经营记录。
- 合同补录即生效 → 外部审批证据、最终签署文件和出租方确认后生效。
- 不验证上游授权覆盖 → 合同生效前验证并冻结出租授权。
- 正式报价和 Space Lock → 租赁意向和条件审议，无锁定。
- 不做催收 → 欠费账户、独立催收案件和内部任务。
- 服务费按租金实收自动派生 → 双方盖章对账单确定应收、独立收款。
- 产权方直租优先 → 承租转租完整链优先、委托代理第二。
- 全部历史迁移 → 仅迁移有效合同、未结账款、保证金和必要主数据。

### 3.3 只作为迁移来源的部分

- 现有 `ContractGroup`、`Contract`、`ServiceFeeLedger` 和经营台账字段。
- 现有 API、页面、权限点和测试证据。
- 旧合同号复合唯一、项目级合同副本和服务费派生实现。

这些内容可用于盘点数据和设计迁移，不能直接充当 v4.0 目标模型。

## 5. 进入原型的唯一输入

原型只消费 v4.0，必须至少演示：

1. Space 可租判断、租赁意向和条件审议。
2. 物业前置条件、底价例外和外部合同审批证据。
3. 承租转租的上游授权、下游合同、账单、保证金、银行收付和催收。
4. 委托代理的产权方合同确认、终端租金逐笔确认、双方盖章对账单和代理费独立收款。
5. 合同变更、续租、交接、提前终止和退场结算。

原型不得继续出现正式报价、Space Lock、补录即生效、代理费自动派生或永久单一催收案件。
