# 原土地物业系统与当前项目产品能力复核报告

> **报告日期**：2026-08-17  
> **报告类型**：产品与系统现状分析报告  
> **调研对象**：原土地物业系统、当前土地物业资产运营管理系统  
> **使用范围**：内部产品评审、前端重构决策、MVP 产品验收准备  
> **安全说明**：原系统登录凭据仅用于本次只读调研，不在本文档及其他产物中记录或复述。

## 执行摘要

本次复核的核心结论是：当前项目并非没有业务能力，也不是一个只有页面外壳的静态原型；其后端已经形成了资产、项目、合同、租金条款、经营台账、收付款流水、服务费、主体客户、产权证、组织权限和经营分析等较完整的 MVP 工程主链路。但这些能力尚未被前端组织成面向岗位任务的可用产品，因此用户感知仍然是“没有一处满意”，尤其表现为页面多、上下文弱、任务不连续、状态不清晰、列表与详情脱节、操作后缺少闭环和业务优先级不明确。

原系统的调研结果也不支持将其直接作为新系统的交互模板。原系统覆盖土地台账、房屋及空间管理、合同租赁、应收收入、催缴、客户、权证、安全生产巡查、统计分析等较多传统物业管理场景，业务字段和作业边界具有参考价值；但其旧式菜单、固定侧栏、多层 tab、iframe、覆盖层和大量技术模块入口造成了较高的学习成本。当前项目如果复制原系统菜单，只会继承旧系统的问题，而不能解决用户不满意的根因。

当前最重要的产品判断如下：

1. **不建议推倒后端重来**。现有后端已经足以支撑下一阶段产品重构，优先工作应是围绕真实作业闭环补齐前端信息架构、页面模型和关键场景。
2. **不建议继续按模块局部修补前端**。需要先确立岗位任务和项目运营主轴，再重做若干高频垂直切片。
3. **项目运营应成为主要业务入口**。资产、合同、客户、权证和台账应围绕项目和资产关系组织，而不是彼此孤立地作为菜单页。
4. **第一批应重做五个场景**：项目运营工作台、项目详情、资产/房屋详情、房间租控、收款与欠费工作台。
5. **原系统的明确缺口需要按产品范围处理**。巡查、安全生产、催缴、房间租控和客户作业不能被当前已有的资产、台账或技术监控页面“代替”，应单独决定是否进入下一阶段范围。
6. **工程通过不等于产品验收通过**。当前追踪文档中已有大量工程证据，但真实业务人员仍需对数据口径、页面可用性、任务闭环和岗位效率进行抽验。

最终建议是：将本项目定位为“以项目和资产为主线的经营运营系统”，采用任务导向的信息架构，收敛菜单和页面层级，强化跨域上下文保持，先完成关键作业闭环，再扩大模块覆盖面。

## 一、背景与复核目标

### 1.1 背景

原土地物业系统长期被使用者反馈为“不好用”，当前项目因此从零开始建设。当前项目已经投入较多工程工作，但使用反馈仍然集中在前端问题，说明单纯增加接口、菜单和表单并未改善实际工作体验。

本报告不把问题简单归因于“原系统老旧”或“当前项目前端粗糙”，而是从产品结构、业务闭环、信息架构、交互任务、工程实现和产品边界几个层面复核：

- 原系统到底覆盖了哪些真实业务和字段；
- 当前项目到底已经实现了哪些能力；
- 哪些能力只是源码、菜单或原型文案，尚未被证明可以使用；
- 当前前端为什么会让用户感到“没有一处满意”；
- 新系统应该继承哪些业务事实，拒绝哪些旧系统模式；
- 下一阶段应先重构什么、补什么，以及如何验收。

### 1.2 复核目标

本次复核形成以下交付判断：

- 建立原系统和当前项目之间的能力差距矩阵；
- 区分浏览器实测、代码证据、文档声明和未验证内容；
- 识别当前前端的产品级根因，而非只列 UI 缺陷；
- 给出目标信息架构、优先级和实施路线；
- 为后续产品负责人抽验和前端重构提供可执行的验收标准。

## 二、范围、方法与证据等级

### 2.1 调研范围

原系统重点查看：

- 首页、一级菜单和快捷入口；
- 土地及资产台账；
- 房屋资产统计分析；
- 房间租控图；
- 权证管理；
- 收入、应收和催缴相关页面；
- 客户和用户管理；
- 安全生产、资产巡查计划、巡查任务及处理记录；
- 菜单、tab、iframe、筛选、列表和详情的交互结构。

当前项目重点复核：

- 前端正式路由、菜单和页面入口；
- 资产、项目、合同、台账、客户、组织、权证和分析实现；
- 后端 API、服务、CRUD、模型和 schema；
- 文档中的产品边界、架构决策和需求追踪；
- 巡查、安全生产、催缴、房间租控等缺口；
- 前端路由孤儿、死服务、导出占位和未挂载模块。

### 2.2 方法

本次复核采用两条证据链并行：

1. **浏览器只读调研**：登录原系统，读取页面、字段、筛选条件、列表结构和可见业务流程；不执行新增、编辑、删除、审批、确认、提交或其他写操作。
2. **源码与文档复核**：检查当前仓库的前端路由和组件、后端 API/服务/模型、测试、PRD、规格、架构决策和追踪矩阵。

本轮没有把历史验收文档中记录的测试结果重新表述为本轮实测结果。历史文档中的门禁和测试结果仅作为“历史记录”引用，不能替代本轮产品验收。

### 2.3 证据等级

| 等级 | 定义 | 本报告用法 |
|---|---|---|
| A | 浏览器中实际读取到页面或字段 | 可表述为“原系统实测” |
| B | 当前仓库存在正式路由、API、模型、服务或测试证据 | 可表述为“当前项目已有工程证据” |
| C | PRD、ADR、追踪文档或原型文案声明 | 只能表述为“文档声明/设计意图” |
| D | 仅菜单可见、源码残留、孤儿页面或未稳定打开 | 不得视为已完成业务能力 |
| E | 本轮没有成功读取或复现 | 标记为“未验证” |

## 三、原系统浏览器实测复核

### 3.1 总体交互结构

原系统登录后进入 hash 路由首页，页面采用传统企业后台结构：左侧固定菜单、顶部工具栏、业务 tab、星标快捷菜单和多个覆盖层并存，部分业务内容通过 iframe 加载。页面中可见文本与实际可点击区域并不总是同一 DOM 层级，部分菜单点击需要经过覆盖层、tab 或 iframe 切换才能确认结果。

这种结构说明原系统的业务覆盖面较广，但也解释了用户对其“不好用”的反馈：系统将菜单、页面容器和业务作业混合在一起，用户需要记住模块位置、tab 状态和页面层级，才能完成一次连续任务。

### 3.2 土地与资产台账

原系统存在“土地（资产）台账”类页面，能够看到较复杂的资产字段和分类维度，涉及土地、房屋及空间、使用状态、经营状态和权属相关信息。其价值在于：土地物业业务并不是简单的资产名称和面积列表，而需要承载多种面积、用途、权属、出租和经营属性。

浏览器实测可确认：

- 台账是原系统的核心数据入口之一；
- 资产信息维度较多，存在资产和空间层级差异；
- 列表、统计和详情之间存在不同业务视图；
- 资产台账与租赁、收入、权证等模块之间存在隐含关联。

未在本轮稳定完成的内容：所有资产字段的完整业务口径、资产变更全流程和全部导出规则。

### 3.3 房屋资产统计分析

原系统可以进入房屋资产统计分析页面，能够看到按照资产或空间相关维度组织的统计视图。该页面与资产台账不是同一类任务：台账用于查找和维护对象，统计分析用于判断规模、分布和经营状态。

这说明新系统需要把“记录管理”和“经营判断”区分开来，不能只把统计卡片堆在列表页面顶部，也不能让用户从统计页面重新寻找底层资产。

### 3.4 房间租控图

原系统存在房间租控图类入口，体现出楼宇、楼层、房间、商铺等空间对象的租赁状态可视化需求。该能力与一般资产列表不同，核心任务是快速回答：

- 哪些房间已经出租；
- 哪些房间空置；
- 哪些房间处于到期、欠费或异常状态；
- 某个楼层或项目的空间使用情况如何。

当前项目模型虽然包含楼宇、楼层、房间和商铺等空间层级枚举，但本轮没有发现与原系统同等成熟的房间租控业务页面。因此，空间层级存在于模型并不等于空间运营已经完成。

### 3.5 权证管理

原系统能够实际打开权证管理页面并读取权证相关数据和字段。权证管理并非单纯附件归档，而是与资产、权利人、证号、面积、土地和房屋信息相关联的数据管理任务。

本轮浏览器实测确认权证是原系统的独立业务入口。新系统的产权证模型、附件、抽取会话、权利人关系和风险派生已经有较明确的工程证据，但仍需要在统一资产详情和项目风险视图中提供更强的上下文，而不是让用户单独进入权证模块寻找关联对象。

### 3.6 收入、应收与催缴

原系统能够看到收入应收类菜单结构、应收相关字段和催缴记录查询条件。催缴页面至少体现了以下作业意图：

- 按合同、客户、项目或账期查找应收；
- 按欠费状态筛选；
- 查询催缴记录和跟进结果；
- 以应收而不是仅以流水为中心组织工作。

本轮没有稳定打开全部收入明细、实收明细和催缴完整流程，因此不将其表述为原系统完整流程已验证。但“应收和催缴是独立运营任务”这一点已由菜单结构、筛选字段和记录页面得到支持。

当前项目已有合同台账、经营收付、支付流水、分摊和服务费台账，但没有发现与原系统相当的催缴工单、跟进记录和催缴成功率闭环。财务台账不能自动替代催缴作业。

### 3.7 客户与用户管理

原系统存在统一客户管理、用户管理和客户相关入口，体现了客户档案、合同关系和运营人员视角的客户作业需求。本轮能够读取客户和用户相关结构，但未稳定完成客户完整详情、客服处理和全部客户生命周期流程。

新系统已经具备 Party、客户档案、联系人、审核、合同历史、风险标签和主体范围绑定等工程能力，但前端仍需要把“客户档案”从主体主数据页面提升为可处理合同、应收、风险和沟通记录的工作页面。

### 3.8 安全生产与资产巡查

原系统能够实际打开“资产巡查计划”“资产巡查任务”和任务处理记录相关页面。浏览器证据说明，巡查不是原型文案，而是原系统中的真实业务模块，至少包括计划、任务和处理记录三个层次。

当前项目源码、测试、追踪文档和正式路由中没有发现可计入真实业务实现的巡查、安全生产、隐患、事故或消防检查模块。前端原型中出现过“消防系统季度巡检”文案，但这只能作为原型文案，不能作为已实现功能。当前的系统监控组件和后端监控代码属于技术监控，不是资产巡查或安全生产业务。

## 四、当前项目代码实现复核

### 4.1 总体判断：已有正式 MVP 工程主链路

当前项目采用 React 19、TypeScript、Vite、Ant Design、TanStack Query、React Hook Form、Zustand 和 React Router；后端采用 FastAPI、SQLAlchemy、Pydantic、PostgreSQL 和 Redis。前后端不是静态演示页面，而是已经形成正式 API、服务、CRUD、模型、测试和权限结构的工程系统。

正式路由已覆盖：

- Dashboard；
- 资产列表、创建、导入、详情和分析；
- 项目列表和详情；
- 合同组、组内合同、合同详情和 PDF 导入；
- 经营台账；
- 客户和主体；
- 产权证列表、导入和详情；
- 组织、用户、角色和系统管理；
- 分析和统计。

因此，当前最主要的问题不是“完全没有功能”，而是功能之间没有形成面向岗位的作业路径。

### 4.2 资产、项目和运营主链路

当前项目已形成以下核心模型关系：

```text
资产 → 项目 → 合同/协议 → 租金账期 → 经营收付 → 分摊/服务费 → 分析
```

资产模型包含土地、建筑、构筑物、车位、仓储、地块、园区、楼宇、楼层、房间和商铺等类型或空间层级；同时承载土地面积、房产面积、可出租面积、已出租面积、出租率、证载用途、实际用途、经营模式、接收协议和合同关系等字段。

项目服务已提供资产、合同、台账、租户、风险和分析等聚合接口，项目详情也已有资产清单、租赁摘要、风险和分析相关内容。这些能力是重做项目运营工作台的基础。

### 4.3 合同、文档解析和台账

合同域已经包含合同组、组内合同、租赁明细、代理明细、扫描件、审计日志、租金条款、合同台账、经营支付流水、支付分摊和服务费台账。

文档解析采用“候选值 + 置信度 + 人工确认”的方式，合同和产权证都有抽取会话、候选确认、人工修正和正式数据创建链路。解析不会直接覆盖主数据，也不会自动创建 Party 或 Asset。这一边界是合理的，但前端必须把“待确认字段、证据来源、确认动作和创建结果”组织成一个连续工作流，而不是只展示一个上传页面。

当前明确存在的工程证据包括：

- 合同组和合同生命周期 API；
- 合同扫描件查询和替换；
- 合同纠错、终止、作废和审计；
- 租金条款和台账接口；
- 合同解析会话；
- 产权证解析会话；
- 人工确认和纠错 schema。

### 4.4 客户、主体、组织和权限

当前项目已经将 Party 作为主体主数据基础，支持主体列表、创建、详情、更新、审核、生命周期、联系人、客户档案、合同历史和风险标签。组织模型、用户主体范围绑定、角色、权限和授权引擎也已存在。

这说明数据范围和权限基础并不薄弱，但前端需要避免把主体、组织和客户拆成相互孤立的系统管理页面。业务用户关心的不是“Party 表中的一条记录”，而是某个客户关联哪些资产、合同、账期、风险和联系人，以及当前用户是否有权处理这些对象。

### 4.5 产权证和风险

当前项目已经具备：

- 产权证列表、详情、创建、更新和删除；
- 房地产、房屋所有权、土地使用权等证件类型；
- 证号唯一性；
- 资产和权利人关系；
- 附件生命周期；
- 抽取会话和人工确认；
- 权利人不匹配及信息不完整风险派生。

其工程能力已经超过单纯的“附件上传”，但前端产品仍应回答实际任务：哪些资产证照不完整、哪些权利人不一致、哪些证照即将到期、谁负责处理、处理后如何验证风险是否消失。

### 4.6 分析和导出

当前项目有 Dashboard、资产分析、综合分析、趋势、分布、出租率统计和导出服务。前端分析组件已有图表和筛选维度，后端分析服务也有缓存和聚合逻辑。

但分析页面仍需进一步产品化：

- 明确每个指标的业务口径和数据范围；
- 从指标下钻到项目、资产、合同和账期；
- 保持筛选条件和视角上下文；
- 将风险、空置、欠费和到期事项纳入经营判断；
- 完成正式 PDF 导出闭环。当前 `frontend/src/utils/exportAnalytics.ts` 中仍存在 placeholder 或文本回退，不能视为正式报表交付能力。

## 五、差距矩阵

| 业务域 | 原系统浏览器事实 | 当前项目工程证据 | 当前产品判断 | 优先级 |
|---|---|---|---|---|
| 土地/资产台账 | 已实际读取复杂台账和分类字段 | Asset 模型、列表、筛选、详情、导入、分析 | 数据基础具备，但需要以项目和空间上下文重组 | P0 |
| 房屋/空间运营 | 已看到房屋统计和房间租控图 | 有空间层级枚举，未发现同等成熟租控页 | 数据模型不等于空间运营能力 | P0 |
| 项目运营 | 原系统入口分散于资产、合同、收入等模块 | 项目聚合 API 已包含资产、合同、台账、租户、风险、分析 | 最适合成为新系统主入口 | P0 |
| 合同/租赁 | 菜单和部分结构已见，详细流程本轮未稳定打开 | 合同组、合同、租金条款、扫描件、审计、台账、解析均有证据 | 后端能力较完整，前端需改为合同工作台 | P0 |
| 应收/收款 | 已见收入应收结构和催缴查询条件 | 有经营台账、收付款流水、分摊、服务费 | 收付记录有基础，催缴闭环缺失 | P0 |
| 客户 | 已见统一客户管理和用户管理结构 | Party、客户档案、联系人、合同历史、风险标签 | 主体主数据有基础，客户作业上下文不足 | P1 |
| 权证 | 已实际读取权证管理页面和字段 | 证照、附件、解析、权利人关系、风险派生 | 工程基础较好，应纳入资产风险主线 | P1 |
| 巡查/安全生产 | 已实际打开计划、任务、处理记录 | 未发现正式模型、服务、API、路由或测试 | 明确业务缺口，不能用技术监控替代 | P1 |
| 报表分析 | 已见统计分析入口，具体大屏未稳定验证 | Dashboard、综合分析、趋势、分布、出租率 | 有统计能力，缺少下钻、口径和正式导出闭环 | P1 |
| 组织权限 | 原系统结构可见，完整流程未验证 | 组织、主体范围、RBAC、授权引擎和绑定均有证据 | 工程基础具备，业务页面需减少管理复杂度 | P1 |
| 催缴工单 | 已见催缴记录和筛选结构 | 未发现催缴工单、跟进记录和成功率闭环 | 是否进入产品范围需明确决策 | P1 |

## 六、当前前端问题与根因诊断

### 6.1 根因一：信息架构按技术模块组织，不按岗位任务组织

当前菜单主要按资产、项目、合同、客户、产权证、分析、组织和系统管理等模块展开。模块划分本身没有错误，但缺少“今天要做什么”的工作入口。用户需要自行完成以下推理：

- 先去项目还是资产；
- 先看合同还是台账；
- 某个欠费客户应该从客户页还是台账页处理；
- 某个证照风险应该从权证页还是资产页处理；
- 某个项目的空置、到期和欠费是否需要分别打开多个页面。

这会导致页面数量增加，但任务完成效率没有提升。

### 6.2 根因二：跨页面上下文丢失

当前项目已经有项目聚合接口，但前端页面仍然容易把项目、资产、合同、客户和台账当作独立入口。用户在一个页面筛选出的项目、资产或客户，进入下一级页面后，筛选口径、数据范围和来源上下文没有稳定保留。

产品上应把以下信息作为贯穿上下文：

- 当前组织和数据范围；
- 当前项目；
- 当前资产或空间；
- 当前合同和客户；
- 当前经营视角；
- 当前时间范围和账期状态。

### 6.3 根因三：状态表达不足以支持运营判断

当前系统已有 review_status、合同生命周期、支付状态、风险和抽取候选等状态，但前端需要将状态转化为任务：

- 待确认的合同字段有哪些；
- 待处理的产权证风险有哪些；
- 哪些资产长期空置；
- 哪些合同即将到期；
- 哪些账期欠费；
- 哪些任务由当前用户负责；
- 操作之后是否已生成台账、分摊或审计记录。

如果状态只以标签或表格字段展示，而不形成待办、筛选和下一步动作，用户仍需手工判断。

### 6.4 根因四：列表、详情和动作没有形成闭环

常见页面模式仍然是“列表 + 新增按钮 + 查看详情”。对于运营系统，关键是：

```text
发现问题 → 进入对象 → 查看关系与证据 → 执行动作 → 验证结果 → 留下审计
```

例如，欠费处理不应停在支付流水列表；证照风险处理不应停在风险标签；合同解析不应停在上传成功。当前前端需要把动作结果、缓存刷新、状态变化、审计记录和下一步操作明确呈现出来。

### 6.5 根因五：产品边界没有转化为页面边界

PRD 和 ADR 已明确排除通用 BPM、合同审批、财务总账、税票、银行对账、批量解析、催缴工单等内容。但前端菜单和源码中仍存在一些退休残留或孤儿入口，容易让用户误以为这些能力已经存在：

- `NotificationCenter.tsx` 存在，但 `/system/notifications` 未在正式路由注册；
- `EnumFieldPage.tsx` 是孤儿页面；
- `assetDictionaryService.ts` 仍调用已下线的 `/system-dictionaries*` 旧域；
- `monitoring.py` 和 `system_monitoring/` 源码存在但没有正式 v1 挂载；
- Ownership 页面和路由常量存在退休残留；
- 产权证历史文档曾有冻结或非 MVP 口径，当前代码和路由又存在正式入口，需要统一 SSOT。

这类问题不是视觉细节，而是产品信任问题：用户点击之后发现 404、空页面或旧路径，会认为整个系统不稳定。

### 6.6 根因六：工程质量和产品可用性被混为一谈

当前追踪文档记录了大量工程证据，但工程测试通过只能证明接口、服务或组件符合既定契约，不能证明：

- 业务人员能否快速找到入口；
- 页面是否保留了工作上下文；
- 指标是否解释得清楚；
- 一次作业是否能从发现到完成闭环；
- 用户是否知道下一步做什么。

下一阶段必须增加产品验收和岗位任务验收，不能只继续累积工程门禁记录。

## 七、目标信息架构建议

### 7.1 主导航

建议将一级导航收敛为以下任务域：

1. **工作台**：我的待办、风险、到期、欠费、解析待确认、最近项目和快捷任务。
2. **项目运营**：项目总览、经营状态、资产、合同、客户、收款、风险和分析。
3. **资产与空间**：资产台账、楼宇/楼层/房间、空置、出租和空间租控。
4. **合同与租赁**：合同中心、租金条款、到期、纠错、扫描件和解析审核。
5. **收款与欠费**：应收、实收、账期、欠费、分摊、服务费和催办记录。
6. **客户**：客户档案、联系人、合同、资产、欠费、风险和沟通历史。
7. **权属与风险**：产权证、权利人、证照完整性、权利人不匹配和处置任务。
8. **分析报表**：经营总览、项目对比、出租率、空置、收入、欠费和导出。
9. **系统管理**：组织、用户、角色、权限、字典、通知和审计。

不建议把“接口能力”直接等同为“一级菜单”。只有能够形成稳定用户任务和页面闭环的能力，才应成为一级入口。

### 7.2 页面统一模型

每个核心业务页面建议采用统一结构：

- 页面标题和当前上下文；
- 关键指标和异常摘要；
- 主筛选区，筛选条件可保存或从上级页面继承；
- 主列表或空间视图；
- 详情抽屉或详情页；
- 关系导航：项目、资产、合同、客户、账期、权证、风险；
- 明确的下一步动作；
- 操作反馈、审计记录和失败原因。

### 7.3 项目详情作为核心壳层

项目详情不应只是项目基础信息和若干 tab，而应成为一个可运营的业务壳层：

- 项目经营状态摘要；
- 资产规模、出租率、空置和空间分布；
- 合同数量、即将到期和异常合同；
- 应收、实收、欠费和服务费；
- 客户和运营方；
- 权证风险和待处理事项；
- 巡查、安全生产或其他 vNext 任务；
- 可追溯的操作时间线。

## 八、优先重做的五个垂直切片

### 8.1 项目运营工作台

**目标**：让项目负责人打开系统后，能够判断项目当前经营状态并直接进入待处理事项。

**必须包含**：

- 项目选择和组织范围；
- 资产数量、出租率、空置面积；
- 合同总量、近期到期、异常状态；
- 应收、实收、欠费和待分摊；
- 权证风险和数据完整性风险；
- 待确认解析、待处理事项和最近操作；
- 点击指标后下钻到对象列表。

**验收重点**：不依赖用户记忆多个菜单；从指标到对象最多两次明确操作；筛选条件在下钻后保持。

### 8.2 项目详情

**目标**：围绕一个项目形成资产、合同、客户、收款和风险的统一上下文。

**必须包含**：

- 项目基础信息和当前管理范围；
- 资产和空间清单；
- 合同和租赁摘要；
- 客户、运营方和产权关系；
- 台账和欠费摘要；
- 权证风险；
- 分析与导出；
- 页面级时间线或审计入口。

**验收重点**：从项目进入资产、合同、客户和台账时不丢失项目筛选；返回项目后保留原位置和条件。

### 8.3 资产/房屋详情

**目标**：从单个资产或房屋对象出发，统一查看空间、合同、客户、产权和经营状态。

**必须包含**：

- 资产身份和空间层级；
- 面积、用途、出租和经营状态；
- 当前及历史合同；
- 当前客户和运营方；
- 产权证和权利人；
- 收款和欠费摘要；
- 风险、审计和变更历史；
- 明确的下一步动作。

**验收重点**：用户不需要分别打开资产、合同、客户和权证四个模块才能回答“这个资产现在怎么样”。

### 8.4 房间租控

**目标**：面向楼宇、楼层、房间和商铺运营，快速判断空间占用和租赁状态。

**必须包含**：

- 项目/楼宇/楼层筛选；
- 房间格局或空间列表；
- 空置、已出租、到期、欠费、装修或不可用状态；
- 房间对应合同、客户和租金摘要；
- 点击房间进入统一资产/房屋详情。

**验收重点**：空间视图不是单独的视觉展示，而是能够下钻到合同、客户和账期。

### 8.5 收款与欠费工作台

**目标**：让运营人员围绕应收和欠费处理任务，而不是只查询流水。

**必须包含**：

- 按项目、客户、合同、账期和状态筛选；
- 应收、实收、部分收款、欠费和逾期摘要；
- 账期明细和金额口径说明；
- 支付流水和分摊关系；
- 当前项目范围内的待处理事项；
- 在产品范围确认后接入催缴记录或催办任务；
- 操作后可看到状态变化和审计结果。

**验收重点**：能够从欠费汇总下钻到账期和合同；金额口径清楚；不把“有支付流水”误认为“欠费工作已经闭环”。

## 九、实施路线与优先级

### 阶段一：前端产品基线与死路清理

**目标**：先消除不稳定入口和信息架构混乱。

重点工作：

- 收敛一级导航和路由入口；
- 清理 404、孤儿页面、退休模块和旧 API 服务；
- 补齐通知路由或移除不可用入口；
- 处理旧字典服务、未挂载监控和 Ownership 残留；
- 统一产权证、分析、组织和数据范围的 SSOT 口径；
- 建立页面上下文协议：项目、资产、客户、合同、时间范围和视角。

### 阶段二：重做五个垂直切片

**目标**：用真实作业闭环证明前端重构价值。

建议顺序：

1. 项目运营工作台；
2. 项目详情；
3. 资产/房屋详情；
4. 收款与欠费工作台；
5. 房间租控。

每个切片都必须同时覆盖页面结构、数据查询、权限范围、空状态、错误状态、操作反馈和下钻路径，不能只改视觉层。

### 阶段三：补齐明确业务缺口

根据产品负责人确认的范围，选择性建设：

- 巡查计划、巡查任务和处理记录；
- 隐患、事故和消防检查；
- 催缴工单、跟进记录和成功率；
- 客户沟通和服务记录；
- 房屋空间的更多运营状态；
- 正式报表导出和经营快照。

这些内容应先完成业务定义、状态机、权限和验收用例，再进入开发，不能只增加菜单名称。

### 阶段四：产品验收与持续优化

**目标**：将“工程实现完成”与“岗位可以使用”分开验收。

需要至少选择以下岗位进行任务验收：

- 项目负责人；
- 资产管理员；
- 合同/租赁管理员；
- 收款或运营人员；
- 权证管理员；
- 系统管理员。

每个岗位选择 3 至 5 个高频任务，用任务完成时间、误操作、返回路径、数据口径理解和异常处理结果评价，而不是只检查页面是否打开。

## 十、产品验收标准

### 10.1 导航与上下文

- 一级导航不超过九个任务域；
- 用户从工作台进入对象列表、详情和动作页时，项目、组织范围和筛选上下文不丢失；
- 退休模块、孤儿页面和不可达入口不出现在正式菜单；
- 所有正式入口都有明确的空状态、加载状态、错误状态和无权限状态。

### 10.2 运营闭环

- 从异常指标可以下钻到具体对象；
- 从对象可以查看关联资产、合同、客户、账期、权证和风险；
- 执行动作后可以看到状态变化、结果和审计记录；
- 失败时显示业务原因和可执行的修正方式；
- 不以静态标签替代待办、责任人和下一步动作。

### 10.3 数据口径

- 出租率、空置面积、应收、实收、欠费、服务费和风险指标都有明确口径；
- 项目、资产、客户和合同之间的数量能解释差异；
- 所有统计支持当前用户的数据范围和视角；
- 导出文件包含筛选条件、时间范围和生成时间；
- 正式 PDF 导出不再使用 placeholder 或文本回退。

### 10.4 权限与数据范围

- 页面展示、下钻、导出和动作使用同一数据范围；
- 无权限时不泄露数量、名称或详情；
- 管理员全局视角与普通用户组织范围有明确界面提示；
- 组织和主体范围变更后，页面缓存和列表结果及时失效。

### 10.5 产品负责人抽验

产品负责人应对以下场景进行真实数据抽验：

- AI 合同和产权证解析候选质量；
- 历史账期与补缴回补；
- 多主体绑定和不同权限视角；
- 逾期筛选和欠费口径；
- 合同激活后台账生成；
- 产权证风险生成和消失条件；
- 项目详情中的资产、合同、客户、台账和风险汇总；
- 移动端关键任务是否仍可完成。

## 十一、明确的产品边界

以下内容当前不能直接当作缺陷，应由产品负责人单独决定是否进入 vNext：

- 通用 BPM 和合同审批；
- 资产变更审批和项目 review 生命周期；
- 财务总账、税票、完整发票流程；
- 支付结算和银行对账；
- 高级 BI 和独立大屏中心；
- 批量扫描件解析和批量采纳候选；
- 催缴工单、催缴成功率和完整客服流程；
- 独立 Ownership 管理；
- SaaS 多租户产品化；
- 用户物理删除。

边界之外的能力可以不做，但正式菜单、文案和页面必须明确隐藏、冻结或标注为规划中，不能留下看似可用的死入口。

## 十二、最终结论与决策建议

当前项目的主要矛盾不是“功能数量不足”，而是“已有能力没有被组织成可工作的产品”。原系统的问题是旧式交互和模块堆叠，当前项目的问题则是把工程模块直接暴露给用户，尚未形成新的任务系统。两者都不能作为完整的产品模板。

建议管理层做出以下决策：

1. 将下一阶段目标从“继续补菜单和页面”改为“完成项目运营主线和五个垂直切片”。
2. 将项目详情、资产详情和收款欠费工作台列为前端重构的 P0；将房间租控和巡查/安全生产列为产品范围确认后的 P0/P1。
3. 暂停没有明确用户任务的局部页面优化和孤立组件扩展。
4. 建立页面级产品验收清单，把上下文、下钻、状态、空错权限和操作反馈纳入完成标准。
5. 对当前代码中已确认的死路由、孤儿页面、旧服务和未挂载模块进行清理，先恢复系统可信度。
