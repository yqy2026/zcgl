# 土地房产系统重构方案（v3.9）毁灭性评审 · 首席产品架构师视角

> 评审对象：`docs/archive/backend-plans/2026-08-17-land-property-system-redesign.md`（v3.9，修订待终审）
> 对照资料：仅用于命名/能力基线交叉验证，不对其展开评审
> 裁决铁律：①数据库表/内部模型直接映射菜单→数据库思维前端化；②为管理而管理/线下流程原样搬→伪需求；③批评必须带精确定位
> 第一性原理：三原子 Space（空间）/ Right（权益）/ Motion（动线）+ 第四原子 Party（主体，论证不可归并）

## 第一部分：顶层重构蓝图

### 1.1 一句话点破本质

本系统最底层的商业与物理本质是：**国企城投存量资产的「经营操作系统」——把"物理空间能租出去、契约义务能收回来、现金能核干净"三件事钉在同一条不可静默改写的可追溯链上**。它不是台账软件，不是 CRM，不是财务总账；它的唯一价值是让"空置→出租→收款→核销"每一条动线在物理、契约、现金三层事实对齐。

### 1.2 原子实体关系与数据流向

```text
                 Party（主体·第四原子，横切所有层，不可归并）
        ┌────────────────────────────────────────────────────┐
        │  产权方 │ 承租户 │ 运营方 │ 供应商                    │
        └────────────────────────────────────────────────────┘
                          │ 签约/收付/归属
        ┌─────────────────┼─────────────────────────┐
     Space（物理原子）   Right（权益原子）        Motion（动线原子）
   地块⊃楼栋⊃楼层⊃房间   产权证/租约/账单/底价      招商锁定→签约→退租释放
        │                   │                          │
        └── 合同-空间覆盖 ───┘── 账单←租约条款 ─────────┘
                    │
              现金-核销轴（流水→分摊→账期，唯一事实轴）
```

**第四原子 Party 的不可归并性论证**：方案已隐含采用 Party（§4.1「Party 范围」、§5.6「往来方」），但未在框架层显式论证。本评确认：**Party 不能归并进 Space 或 Right**。理由：同一法人可同时为产权方（持有 Space）、承租户（持有 Right）、运营方（承载现金流归属 `funds_beneficiary`）三角色，且角色随有效来源派生（§5.6「业务角色由当前有效来源派生」）。若把主体塞进 Space（"这间房的业主"）或 Right（"这份合同的对方"），将丢失跨合同/跨资产的主体全景与风险归集能力，直接破坏财务出纳"三流一致"与决策层"全局可视"。故 Party 为独立横切原子，方案处理正确，本评不挑战，仅作框架显式确认。

## 第二部分：维度 1–4

### D1 名词与概念

🛑 **当前致命缺陷**

1. 【定位】§3.4「资产词消歧」与 §4.2「终版两级菜单树」〔矛盾〕｜事实：§3.4 明文裁决"「资产 › 资产台账」不得成立——二选一：二级节点改「台账」或一级入口改「空间与资产」"；但 §4.2 菜单树原文仍写 `资产 ├─ 资产台账`，一级入口"资产"下直接挂子节点"资产台账"，与自身裁决自相矛盾。｜业务后果：前端落地时必有一处违反词汇终审，要么改菜单要么改裁决，终审会签失去意义。
2. 【定位】§3.4「物业本期冻结」/ §5.8「物业动线边界声明」与业务背景硬约束"五类用户含物业（诉求：省事·一次录入自动流转）"〔矛盾〕｜事实：方案将"物业人员"从岗位表删除、声明本期不服务物业动线（§11.6 巡查/维修/安全全 defer）；但本任务业务背景把物业列为五类核心用户之一，且明确要求"一次录入、自动流转、零重复操作"。｜业务后果：四类用户闭环，唯独物业被整体剔除，违反"任何设计若同时对五类人都不友好判死"——此处是五类中有类直接缺席。
3. 【定位】§3.4「空间/房源/铺位」与 §5.3「空间（菜单节点）」〔明文〕｜事实：方案已裁决物理统称"空间"、"房源"仅限可租列表标题词；但 §5.3 行内动作同时出现 [锁定]/[标记停用·待确权]/[释放]，而「房源」作为可租视图标题与「空间」作为物理统称在导航与列表标题间切换，新人不察仍会三词并行。属已裁决但未在落地层彻底消歧的残留风险。

💡 **第一性原理重构**

名词 SSOT 的第一性原理：**一个概念一个词，词的位置等于它在原子框架中的层（决策层/操作层/展示层），绝不跨层**。资产=Space+Right 的核算投影（决策层），空间=物理拓扑（操作层），房源=可租集合（展示层）。三者必须永不嵌套、永不对等并列。

🛠️ **具象化落地提案（新旧名词对照表·节选）**

| 现用词（方案内残留） | 裁决终词 | 层级 | 处置 |
|---|---|---|---|
| 资产 › 资产台账（§4.2 菜单） | 一级「资产」→ 二级改「台账」（页面标题保留"资产台账"） | 操作层 | 立即修 §4.2 菜单树，消除自矛盾 |
| 物业（岗位/菜单） | 本期「资产与权证管理员」承接其"省事"诉求；二期独立物业域 | 边界 | 在岗位表补一行"物业（只读消费者视图）"，不与硬约束冲突 |
| 房源 / 空间 / 铺位 | 物理统称"空间"；"房源"仅可租列表标题 | 操作层 vs 展示层 | §5.3 列表标题统一，导航只用"空间" |

### D2 信息架构

🛑 **当前致命缺陷**

1. 【定位】§2.1「空间/资产原子裁决（ADR 二选一）」〔明文〕｜事实：方案核心数据模型 Space 至今未决——"实现路径写 ADR 二选一，且 ADR 前禁止默认任一选项"；ADR①最小 `Space` 表，ADR②`Asset` 显式双用途。§11.3 更设"5 工作日裁决时限、超期降级冻结切片"。｜业务后果：一份标注"修订待终审"的方案，其**物理原子地基尚未选定**，C 切片（空间视图）被自己设的时限机制冻结。未决地基即送终审，等于让终审在悬空之上签字。这是本方案最大的就绪度缺陷，非功能缺陷。
2. 【定位】§5.3「资产台账」与「空间」双兄弟节点〔明文〕（ADR② 风险）｜事实：在 ADR② 下，资产即空间拓扑节点（parent_asset_id），则"资产台账"与"空间"是同一原子的两个 UI 切面，兄弟并列正是铁律①"数据库表映射菜单"。｜业务后果：若选 ADR②，导航暴露两张表而非一个物理实体。

💡 **第一性原理重构**

Space 是**物理拓扑原子**（地块⊃楼栋⊃楼层⊃房间/铺位），Asset 是**经营核算原子**（承载面积/底价/权属的核算单元）。二者逻辑分离是方案自己认定的（§2.1）。由此推演：**ADR①（最小 `Space` 表）为唯一正确解**——把拓扑塞进 Asset 表（ADR②）恰恰是铁律①禁止的"物理结构进核算表"。物理拓扑与核算单元生命周期不同（楼栋不随租约变，房间随租约变状态），强行双用途将制造 `parent_asset_id` + 形态/状态字段 + 双用途不变量的脆弱耦合。裁决：终审前必须落 ADR①，撤销"二选一未决"状态。

🛠️ **具象化落地提案**

「空间拓扑 × 生命周期」双轴联动架构：左侧空间树（物理轴，挂楼栋/楼层聚合徽章——可租/在租计数与空置率，v3.9 已补），右侧租约生命周期动线（生命周期轴，五态）。资产台账降为空间的"核算属性"侧栏而非平行入口；若 ADR① 落地，"资产台账"作为独立菜单节点撤销，改为空间详情「核算」tab，消除双表映射。

### D3 菜单与导航

🛑 **当前致命缺陷**

1. 【定位】§4.2 菜单树 `资产 ├─ 资产台账`〔矛盾〕（同 D1-1，导航层复现）｜事实：§3.4 已禁此嵌套，§4.2 仍呈现，且 §6.5 路由 `/assets`（资产台账）与 `/assets/spaces`（空间）并存。｜业务后果：第 3 级虽未出现字段名，但第 2 级已出现"实体表名并列"，违反铁律①精神。
2. 【定位】§5.7「scope_diagnosis:read」+ §9.1 + §13.2〔明文〕｜事实：方案自认"若组织内确无此类岗位，该能力标记为休眠（保留能力码，不向任何角色授予）"（v3.9 休眠脚注）。即方案自己承认这是可能零用户的推测性能力。｜业务后果：为"可能不存在的排障岗位"预留独立诊断能力码+端点+审计，属铁律②"为防呆而防呆"。

💡 **第一性原理重构**

菜单只回答"我今天要完成什么判断和动作"，轴只能是角色动线，不能是实体表、不能是内部模型、不能是防呆占位。零子节点入口必须是一步直达高频目的地；任何能力的存在前提是"有真实角色会每天/每周用它"，否则进"明确不做"。

🛠️ **具象化落地提案（≤3 级，按角色动线重排）**

```text
工作台          （零子节点：待处理 / 组合驾驶舱 页内切换）

├─ 项目总览
├─ 空间        （树+列表双视图；五态；默认"可租"）  ← 资产台账降级为空间详情「核算」tab
└─ 产权证
合同            （零子节点：台账即一级；录入/更正走顶栏+子路由）
收付            （零子节点：账单 / 流水·待核销 / 服务费 页内 tab）
往来方          （零子节点：档案+角色筛选）
设置中心        （仅管理岗）
├─ 组织与权限    （含权限诊断，复用审计日志，不再单列 scope_diagnosis）
├─ 数据工具
└─ 审计日志
```
`scope_diagnosis:read` 从方案删除（见第三部分删减清单）。

### D4 功能布局与动线

🛑 **当前致命缺陷**

1. 【定位】§5.1「组合驾驶舱·盘活进度（v3.9 P0）」〔缺失〕（数据前提不具备）｜事实：盘活进度=滚动 12 月空置→在租转化率，"按空间状态变迁事实派生"。但空间五态与状态变迁事实是 v3.8/v3.9 **新加**的能力，0→1 上线首日为 0 条历史变迁。｜业务后果：决策层首屏 P0 指标在至少 6–12 个月内恒为空/失真，是为"看起来专业"而建的无数据指标，违反铁律②。
2. 【定位】§5.4 合同录入两步向导〔明文〕｜事实：原件 35% + 中栏确认 + 右栏账单预览常驻，逐字段人工确认、候选永不自动选中。对存量合同（上千份）是正确防呆；但对**新签标准合同**仍强制走完整两步向导+PDF 原件上传，路径偏长。｜业务后果：招商"从线索到签约步骤最少"诉求被过厚录入摩擦拖累（Q2 更短路径未达成）。

💡 **第一性原理重构**

四核心页面（资产看板/资源列表/资产详情/签约表单）的黄金视区只放"核心经营+下一动作"。决策层首屏先用**有数据的**空置结构卡+账龄卡，等状态变迁事实积累后再点亮盘活进度。录入区分"新签"与"存量补录"两条路径：新签标准合同走轻量模板（复制上一份+字段预填，方案 §5.4 已有"复制上一份同类合同"），仅存量补录走完整 OCR 两步向导。

🛠️ **具象化落地提案（核心页面区块）**

【屏幕上方：核心经营看板——空置率 / 收缴率 / 本月到期】（盘活进度卡灰显"数据积累中"）
-----------------------------------------------------------------
【左侧：空间拓扑树（五态聚合徽章）】 │ 【右侧：租约生命周期动线】

### 四大能力缺口逐一裁决

1. **产权确权追溯** — 覆盖（部分）〔明文〕：`ChangeAssetOwner`+产权沿革只读区块（§2.1）+待确权冻结（§8.11）+产权证三类 warning（§5.3）已建所有权变更 trails 与冻结态。但**不足**：仅渲染 `ChangeAssetOwner` 前后值审计链，未建"原始权证→历史变更→现状"的来源链（A2），对"历史遗留产权不清"这批硬约束资产，缺从权证出发的溯源视图。结论：变更 trail 覆盖，来源链不足。
2. **闲置/空置资产全景** — 覆盖〔明文〕：空间五态+可租集合+空置起算锚点+拓扑节点聚合（v3.9 补）+工作台空置待处理，且空间视图与工作台同源同口径（§13.2 安全门）。此为方案最强项，覆盖充分。
3. **动态租金定价风控** — 覆盖不足〔明文〕：仅静态 `floor_price` 底价校验（§5.4/§7.4），无市场/历史成交对标。存量盘活场景下定价风控应含"同项目同形态历史成交单价基准"参考（A3）。结论：底价门禁覆盖，动态对标缺失。
4. **应收账款风险催收** — 风险可视覆盖 / 催收动作缺失〔缺失〕：账龄分桶、逾期、坏账核销（§2.2/§8.12）使风险**可视**；但催收动作（联系/承诺还款日跟进/逾期升级）被显式 defer（§11.6 催缴工单、§3.2 预警非任务）。跟进记录字段（§2.1）存在但无催收闭环。结论：风险可见覆盖，催收动作缺失（A4）。
