### P1 — REQ-NTF-001 是下一面墙（同病灶、未清、机制无家）

- **现状**：§7.10 单格 **1262 字**（实测，全 PRD 最大格），塞入：5 类通知 + **档位幂等**（幂等键元组「接收人, 对象, 类型, 优先级档位」、`NORMAL→HIGH(≥7天)→URGENT(≥30天)`、到期 30/15/7 天档位）+ `days_overdue`/`days_remaining` 派生 + 数据范围过滤 + 系统通知广播豁免（`related_entity_id`、PII 约束）+ 企业微信 `touser` 定向推送 + 应用消息接通开关 + 重试...
- **复核坐实**（2026-06-20）：api-contract §4.12「通知」端点行同样含档位幂等键、`touser`、`related_entity_id` 中立约束、ADR-0015/0016 全套——与 NTF-001 **逐条跨文档复制**；`domain-model` 确无 Notification 对象（`通知` 唯一命中在 §4.14 台账段「统计、风险、筛选与通知统一按逾期派生」的顺带提及，非对象）。
- **诊断**：与开工前的 REQ-AST-005 **完全同构**——把机制（幂等阈值 / `touser` / `related_entity_id` / 档位派生）塞进 PRD 表格格子。核对 `domain-model` §3 对象清单（Party…Attachment 共 17 个）**无 Notification 对象**（`通知` 词在 domain-model 仅命中 1 处）；而 api-contract §4.12 又抄了一遍 → **PRD ↔ api-contract 跨文档复制**，正是批 4 在 §4.3/§4.10 刚消除的形态。
- **影响**：违背刚立的单一真相；任一处改档位口径要同步 PRD + api-contract（撞 §3.2 口径一致性指标）。Check 7 当前 token 集未覆盖通知机制 token，故未被守卫挡住——属覆盖盲区。
- **收口建议（同产权证打法，决策已成熟）**：
  1. `domain-model` 新增 `Notification` 对象（5 类枚举 / 幂等键 / 优先级档位派生 / 系统通知中立硬约束 / 企业微信 `touser` 通道 / 「提醒非工单」无处理闭环）；档位阈值与派生口径落此。
  2. PRD REQ-NTF-001 削成产品级：「站内通知五类 + 通知是提醒不是工单 + 接收人按数据范围过滤 + 系统通知广播需内容中立 + 企业微信可选定向推送；机制见 domain-model §X」。
  3. api-contract §4.12 削成端点契约 + 引用 domain-model。
- **风险**：低。决策已定——档位幂等（ADR-0015）、企业微信 `touser`（ADR-0016）、系统通知中立生产者（2026-06-18 grill）。与代码侧 `docs/issues/2026-06-18`（I1~I3 通知）对齐即可。

### P2 — §7 altitude 方差仍刺眼（详略未拉平）

- **现状（实测字数，2026-06-20）**：同一份 §7 内，REQ-CUS-001（65 字）/ SYS-001~003 / PRJ-002 / RNT-002 是**一行**；而 NTF-001 **1262 字**、AST-005（已削）**701 字**、RNT-005 **642 字**、RNT-006 **623 字**。
- **诊断**：方差本身 = 文档被 grill 不均匀加厚的残迹（哪里 grill 狠哪里厚）。其中 RNT-005/006 比 NTF-001 更可辩护（台账重算 / 逾期派生 / 固化归属是核心业务价值），但仍是 essay 塞进表格行。
- **「自然地板」洞见**：批 1 把 AST-005 从约 2000 字削到 701，**仍是 ~700 字**——因 5 项硬门槛 + 证号重复 + 风险派生这些产品级要点本就需要篇幅。AST-005/RNT-005/RNT-006 收口后均落在 **642~701 字**，说明复杂业务 REQ 有个约 **650~700 字的自然地板**。**修正此前报告口径**：批 1 报「AST-005 削到 ~400 字」属低估，实为 701。故 **NTF-001（1262）的现实收口目标是降到该地板（约 650）、而非 200**——降幅来自机制下沉（档位/`touser`/`related_entity_id` → domain-model），不是硬压字数。
- **建议**：把 essay 型 REQ 统一为「做什么 + 引用」，机制 / 公式下沉 `domain-model` §6 统计口径或对象契约。AST-005/RNT-003/DOC-001 已做；NTF-001（P1）、RNT-005/006 待评估（RNT-005/006 的「重算只动未收 / 已收派生陈旧风险」口径建议保留要点、细节移 domain-model §4.14——注：domain-model §4.14 台账段已承载该口径，PRD 侧可进一步引用）。

### P3 — 表格当散文（格式错配）

- **诊断**：大量「验收标准」格子是多句小作文，违背表格「可扫描并列」的本意。NTF-001 / RNT-005 这类应是**带小标题的正文小节**，而非表格行——读者无法在表格里扫读一段 1100 字的格子。
- **建议**：超过约 2 句的 REQ 改为正文小节（REQ 编号保留为小标题），表格只放可扫描的「需求一句话」。与 P2 同批做最省。

### P4 — Out-of-Scope / §5 的防御性沉积

- **现状**：§4.2 line 65（财务总账：「支付结算 vs 台账实收登记 二者须区分」）、line 69（合同 BPM：「注意区分 MVP 仍保留最小生命周期」长 caveat）、line 73（催缴）；§5 line 89（perm_admin 长 bullet：静态授予边界 vs 职责互斥的辨析）。
- **诊断**：grill 留下的**边界澄清话术**，必要但臃肿——大量「注意区分 X 不属于本项 / 不冲突」的防御性句子。
- **建议**：保留边界结论本身，把「为什么这样切」的 provenance 移到对应 ADR；PRD 只留「不做 X；但 Y 属 In Scope（见 §Z）」一句。低优先。

### P5 — ADR 引用噪音（provenance 与 authority 混层）

- **现状**：PRD 中 ADR 引用分布于 **20 行**（`ADR-0` 命中 20 行，其中 `见 ADR-0xx` 形式 18 处，余为「同 ADR-0002 资产口径」等行内引用）。
- **诊断**：每个格子同时承担 provenance（为什么这么定）与 authority（绑定决策）。对业务 / 设计读者是噪音；正文口径被引用淹没。
- **建议**：考虑把 inline ADR 引用收敛——正文只留口径，provenance 集中到 `requirements-trace.md` 或每节末一行「相关决策：ADR-00xx」。**需权衡**（可追溯性 vs 可读性），取向请 yellowUp 定。中低优先。

### P6（根问题）— 声称读者 ≠ 真实读者

- **现状**：§1 称本文档「业务、产品、设计、研发和验收共同使用」。但实际 register 满是 `owner_party_id` / `manager_party_id` / `scope_mode=all` / `related_entity_id` / `risk_type=...` / 「幂等键为（接收人, 对象, 类型, 优先级档位）」。
- **诊断**：PRD 已**悄悄变成一份穿着 PRD 外衣的工程规格**。没有业务 / 设计读者读得下去这种 register。这是比「详略」更根的病，**搬运解决不了**。
- **两条路（需 yellowUp 拍板）**：
  - **(A) 收窄 §1 读者声明**为「产品 + 研发 + 验收」——诚实、零成本，承认它是 PM/Eng 工件。
  - **(B) 补一层薄的业务面 PRD**——成本高，仅当确有业务读者诉求时。
  - 倾向先 A；B 视真实读者需求。

### P7 — §3.2 成功观测单薄

- **现状**：上线后三个月成功指标仅剩「关键报表口径一致性问题 ≤ 2 个/月」，人工逐月认定，无任何采用 / 使用信号。
- **诊断**：砍掉两个伪指标（无口径的台账完整率、无基线的处理时长）是**对的**，符合减法纪律。但「三个月成功」只靠一条主观指标、零客观使用信号，**成功是欠观测的**。
- **建议**：评估是否补一个**客观、低成本、可证伪**的采用信号（如「核心流程被真实使用」的二元达成，而非比率）。需产品判断，不预设。
