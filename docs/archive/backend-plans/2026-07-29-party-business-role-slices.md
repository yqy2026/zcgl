# 2026-07-29 主体业务角色切片实施方案

**状态**：✅ 已完成（2026-07-29）
**需求**：REQ-PTY-003
**决策**：[ADR-0021](../architecture/ADR-0021-party-business-role-slices-derived.md)

## 目标

在主体中心提供按当前业务角色查看 Party 的能力，消除法律主体类型与运营角色混用造成的检索障碍，同时保持 Party 单一主档、现有数据范围和客户统计口径不变。

## 已锁定口径

- 角色只有 `owner`（产权方）、`operator`（运营方）、`terminal_tenant`（终端租户）。
- 角色是查询时从当前有效资产、项目和合同/协议关系派生的投影，不写入 Party 或独立 Profile。
- 一个 Party 可以同时拥有多个角色；全部列表按 Party ID 去重并展示全部当前角色标签。
- `customer_type` 仅内部/外部展示，`UserPartyBinding.relation_type` 仅数据范围，二者不得成为角色来源。
- 仅有历史合同的 Party 不进入当前终端租户切片；历史签约继续通过 CustomerProfile 展示。
- 本期不做客户等级、评分、自动分群、客户合并或批量回填角色缓存。

## 交付范围

1. 后端：扩展 Party 查询 schema、API、service 与 CRUD，支持 `business_role=owner|operator|terminal_tenant`，复用现有分页、搜索和 Party 数据范围。
2. 后端：按既有有效性规则从资产产权方、项目运营方、下游转租/直租承租方派生角色；同一 Party 同角色多来源命中必须去重。
3. 前端：主体列表提供“全部、产权方、运营方、终端租户”切片，并在每个 Party 行展示全部当前角色标签；不得以 `customer_type` 模拟角色。
4. 测试：覆盖多角色同列、仅历史合同不进入当前租户、无权限关系不泄露、分页总数与筛选一致、合同失效后角色消失，以及 `customer_type`/用户主体绑定不影响角色归属。
5. 文档：实现完成后补代码与测试证据，将 REQ-PTY-003 状态从“未开始”更新为“已有证据”；验证通过后将本方案归档。

## 实施顺序

1. 先为 Party 查询服务补失败用例，定义当前有效关系的最小查询边界。
2. 实现服务和 CRUD 派生查询，再接入 API schema；不在路由层拼装角色。
3. 为主体列表接入 React Query 查询参数与稳定 Tab 状态，补组件和服务契约测试。
4. 完成定向测试、类型检查、文档门禁和性能复核；若查询计划不能满足列表分页需要，再单独提出读模型 ADR，不在本方案内预置缓存。

## 实施结果

- `GET /api/v1/parties` 已支持 `business_role=owner|operator|terminal_tenant`，按 Party 数据范围过滤后，从当前有效资产、活跃项目及当前有效下游转租/直租合同实时派生角色；响应返回去重且稳定排序的 `business_roles`。
- 主体列表已提供“全部、产权方、运营方、终端租户”Tab，并显示每行的全部当前角色标签；切换 Tab 通过 React Query 查询参数请求服务端筛选。
- 已覆盖多角色合并、过期合同/合同组排除、直租承租方识别、范围外 Party 不泄露、Service 参数传递和前端请求契约。
## 验收场景

- 一个 Party 同时拥有当前有效资产产权方和直租承租方关系时，全部列表只显示一行，标签同时含“产权方、终端租户”。
- Party 只有已失效或已作废下游合同，不出现在当前终端租户切片，但客户档案仍保留历史签约。
- 运营方绑定用户只能看到其既有数据范围内的角色结果；角色标签不得通过关联关系泄露范围外 Party。
- 切换角色 Tab 后，服务端分页、搜索结果和列表行保持同一筛选口径。
- 内部/外部 `customer_type` 改变或用户绑定关系改变，不会凭空改变 Party 的业务角色。
