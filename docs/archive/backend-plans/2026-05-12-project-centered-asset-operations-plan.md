# 项目主轴资产运营全局规划

## Status

✅ 已完成（2026-05-16 完成 Phase 0-4 收口并归档）

## 1. 规划背景

当前系统已经具备资产、项目、主体、合同组、合同关系、台账、分析等基础对象，但用户侧体验仍像技术后台：

- 普通用户直接看到“合同组管理”“合同组编码”“组内合同”等实现概念。
- 合同详情页暴露主体 ID、`LEASE` / `AGENCY`、规则 JSON，缺少业务可读表达。
- 资产、项目、合同、主体、收付款之间的关系没有以日常工作方式组织。
- 承租转租和代理运营都存在，但入口和页面没有体现两类业务的并列关系。
- 合同中心容易被误解为主入口，导致用户先面对零散合同，而不是先面对项目经营单元。

本规划的目标是重排全局信息架构，先解决“系统围绕什么工作对象展开”的问题，再进入代码改造。本版吸收 2026-05-13 评审意见，补充关键领域决策、Phase 0 输出物、工作量估算、依赖关系、回滚策略、存量数据处理和 SSOT 同步清单。

## 2. 核心定位

系统定位调整为：

> 项目制资产运营管理系统。

项目是普通用户的第一工作对象：

> 项目 = 一个运营管理方在一段时间内，对一批资产或物业进行经营管理的业务单元。

项目可以对应园区、楼宇、片区、物业组合或其他实际经营单元。项目下承载资产、合同关系、收付款、客户、风险和经营分析。

## 3. 已确认原则

1. 普通用户不看到“合同组”这个词。
2. `ContractGroup` 继续作为后端聚合根和技术实现，但不能作为普通用户菜单、页面标题或列表主对象。
3. “合同关系”是 `ContractGroup` 的用户展示投影，不新增 ORM 对象。
4. `ContractGroup` 应新增 `project_id`，合同关系归属项目，组内合同自然归属项目。
5. 项目是主轴，合同中心是辅助入口。
6. 一个项目可以同时存在承租转租和代理运营两种模式。
7. 单条合同关系不能混合模式。
8. 资产可以随时间转入或转出项目，但同一时点只能归属一个项目；历史归属优先通过 `project_assets` 有效期关系保留，Phase 0 需复核现有表结构是否满足该语义。
9. 上游承租合同和委托协议先绑定项目，再选择覆盖的资产范围。
10. 下游出租合同和直租合同先绑定项目，再选择涉及资产。
11. 下游合同或直租合同不强制手工绑定具体上游合同或委托协议，系统通过项目、资产、时间范围推导对应关系；首期可先做风险提示，不强制自动绑定。
12. 项目详情里需要“合同关系”层，但不作为一级菜单。
13. 收付款台账以合同为源头生成，在项目下统一查看；全局台账用于跨项目查询、筛选和导出。
14. 项目经营分析按经营模式分区展示，不能把承租转租和代理运营口径硬混。

## 4. 关键设计决策

| 决策 | 结论 | 理由 | 后续动作 |
|---|---|---|---|
| 合同如何绑定项目 | `ContractGroup` 增加 `project_id` | 合同关系约等于 `ContractGroup` 的用户展示层，归属项目后组内合同自然归属项目 | 同步 domain-model、api-contract，设计 Alembic migration |
| “合同关系”是否新增 ORM | 不新增 ORM，对 `ContractGroup` 做展示投影 | 避免再造一层聚合对象，降低数据迁移和一致性成本 | 前端/API 使用“合同关系”文案，后端仍维护 `ContractGroup` |
| 是否保留 `ContractRelation` | 保留 | 它表达合同之间的父子关系，不承担用户可见主对象 | 用于上游-下游、委托-直租关系推导和风险提示 |
| 是否立即删除 `/contract-groups` | 不直接删除，先隐藏或降级为内部/高级入口 | 降低 Phase 1 上线风险，保留回退路径 | 菜单隐藏，路由可临时保留，完成验证后再清理 |
| 存量数据是否立即迁移 | 需要补 `project_id`，但合同关系展示可先由现有数据投影 | 支持项目详情新入口需要项目归属；展示层可兼容存量聚合 | Phase 0 设计回填规则，Phase 1a 执行 migration |

## 5. 目标一级菜单

| 一级菜单 | 定位 | 主要内容 |
|---|---|---|
| 工作台 | 个人和项目风险入口 | 待办、到期、逾期、应收应付提醒、异常数据 |
| 项目运营 | 主入口 | 项目列表、项目详情、资产、合同关系、收付款、租户、风险、项目分析 |
| 资产资源 | 资源台账入口 | 资产台账、产权证、资产归属历史、资产反查项目和合同 |
| 合同中心 | 辅助入口 | 跨项目合同查询、PDF 导入、待处理合同、合同快速检索 |
| 财务台账 | 跨项目账务入口 | 应收、应付、押金、发票、收付款记录、导出 |
| 主体中心 | 业务主体入口 | 产权方、运营方、终端租户、集团公司、联系人、主体审核、主体关系 |
| 经营分析 | 跨项目分析入口 | 集团、运营方、项目、模式、客户、资产维度分析 |
| 系统管理 | 系统配置入口 | 用户、组织、权限、字典、模板、审计 |

说明：全局菜单使用“经营分析”，项目详情内部使用“项目分析”，避免两个层级重名。

## 6. 项目详情信息架构

项目详情应成为日常运营工作台，而不是只展示项目基础字段。

| 页面区域 | 内容 | 说明 |
|---|---|---|
| 项目概览 | 项目名称、运营方、状态、资产数量、经营模式分布 | 经营模式分布从合同关系实时聚合，首期不在 Project 表冗余缓存 |
| 资产清单 | 当前有效资产、历史转入转出、面积、出租状态 | 资产同一时点只能属于一个项目 |
| 合同关系 | 承租转租关系、代理运营关系、合同覆盖资产 | 替代用户可见的“合同组” |
| 收付款 | 应收、应付、实收、实付、逾期、付款计划 | 数据源来自合同台账 |
| 租户/客户 | 终端租户、客户主体、合同数、风险标签 | 客户以 Party 为唯一主档 |
| 押金发票 | 押金、保证金、发票记录 | 首期作为运营台账，不做财务总账 |
| 风险提醒 | 合同到期、付款逾期、覆盖冲突、空置风险 | 从合同、资产、台账推导 |
| 项目分析 | 承租转租和代理运营分区指标 | 避免混合统计口径 |

## 7. 两类经营模式

### 7.1 承租转租

业务链路：

```text
产权方公司 -> 上游承租合同 -> 运营管理方公司 -> 下游出租合同 -> 终端租户
```

项目下应展示：

- 上游承租合同覆盖哪些资产。
- 下游出租合同涉及哪些资产。
- 上游应付和下游应收。
- 收入、成本、经营差额。
- 出租率、空置面积、空置成本。
- 上游合同到期对下游合同的影响。

### 7.2 代理运营

业务链路：

```text
产权方公司 -> 委托协议 -> 运营管理方公司
产权方公司 -> 直租合同 -> 终端租户
运营管理方公司 -> 服务费结算 -> 产权方公司或约定结算方
```

项目下应展示：

- 委托协议覆盖哪些资产。
- 直租合同涉及哪些资产。
- 服务费计算口径和结算状态。
- 委托资产规模、直租合同规模、客户情况。
- 委托协议到期和直租合同到期风险。

## 8. 核心对象关系

```text
主体 Party
  ├─ 产权方
  ├─ 运营方
  └─ 终端租户

项目 Project
  ├─ 运营方主体 manager_party_id
  ├─ 当前有效资产关系
  ├─ 承租转租合同关系
  ├─ 代理运营合同关系
  ├─ 台账汇总
  └─ 项目分析

资产 Asset
  ├─ 当前项目
  ├─ 产权方主体
  ├─ 运营方主体
  └─ 历史项目归属关系

合同关系 ContractGroup 展示投影
  ├─ 承租转租：上游承租合同 + 下游出租合同
  └─ 代理运营：委托协议 + 直租合同

合同 Contract
  ├─ 所属合同关系
  ├─ 覆盖资产范围
  ├─ 签约主体
  ├─ 生命周期
  └─ 台账源头
```

说明：

- “合同关系”是用户可见层；`ContractGroup` 是技术层。
- 项目可以包含多条合同关系。
- 每条合同关系有且只有一种经营模式。
- `ContractGroup.project_id` 绑定项目，合同通过所属合同关系归属项目。
- 合同选择资产范围，资产范围必须是对应项目在合同期间内的有效资产子集。
- 系统通过项目、资产、时间范围推导合同之间的对应关系；有冲突时提示风险。

## 9. 与现有实现的关系

| 现有对象或入口 | 目标处理 |
|---|---|
| `Project` | 提升为主业务对象和主入口 |
| `ContractGroup` | 保留为后端聚合根，新增 `project_id`，前端普通用户不可见该名称 |
| `ContractRelation` | 保留为上游-下游、委托-直租的合同父子关系 |
| `/contract-groups` | 迁移为项目内“合同关系”能力，短期隐藏或降级为内部/高级维护入口 |
| 合同中心 | 保留为跨项目查询、导入、待处理合同辅助入口 |
| 资产详情 | 增强为资产反查项目、合同关系、收入成本和空置状态 |
| 台账 | 保持以合同生成，在项目和全局两个层级展示 |
| 经营分析 | 增加项目维度和模式分区，避免混合口径 |

## 10. 存量数据与回滚策略

### 10.1 存量数据处理

- Phase 0 先盘点现有 `ContractGroup` 与资产、项目、主体的可推导关系。
- Phase 1a 增加 `ContractGroup.project_id` 后，需要回填存量合同关系所属项目。
- 回填优先级建议：
  1. 若合同组关联资产均有同一当前有效项目，回填该项目。
  2. 若资产历史归属能按合同生效期唯一命中项目，回填该项目。
  3. 若命中多个项目或无法命中，标记为“待人工确认”，不强制写入错误归属。
- 存量展示可先做投影转换：用户看到“合同关系”，底层仍读取 `ContractGroup`、`Contract`、`ContractRelation`。

### 10.2 回滚和兼容策略

- Phase 1 不直接物理删除 `/contract-groups` 路由，先从普通菜单隐藏。
- 新项目详情入口上线后，保留旧入口作为内部排障入口一个发布周期。
- 若项目详情新入口反馈不可用，可恢复旧菜单入口，同时保留已新增的 `project_id` 字段，不做数据回滚。
- API 新增端点优先采用增量方式，不破坏现有合同组 API。
- 待项目详情和合同录入路径稳定后，再清理旧入口、旧文案和测试夹具。

### Phase 0：现状盘点与术语收口

目标：确认当前系统中暴露给用户的技术概念和菜单混乱点，完成后续开发前置决策。

输出：

- 前端“合同组”可见点清单，包含文件、行号、文案、建议处理方式。
- 当前菜单到目标菜单的映射表。
- 当前项目、合同组、合同、资产、台账的数据关系盘点。
- `project_assets` 或同类关系表是否能承载资产项目历史归属的结论。
- `ContractGroup.project_id` migration 设计和存量回填规则。
- `docs/prd.md`、`docs/specs/domain-model.md`、`docs/specs/api-contract.md`、`docs/traceability/requirements-trace.md` 的修订清单。
- 对“一资产一有效合同组”约束是否阻碍项目内多合同关系的结论。

### Phase 1a：后端基础

目标：让项目具备读取合同关系的后端基础。

输出：

- `ContractGroup` 新增 `project_id`。
- 合同关系展示投影 API，例如 `GET /api/v1/projects/{id}/contract-relations`。
- 项目维度收付款摘要 API，例如 `GET /api/v1/projects/{id}/ledger-summary`。
- 项目风险摘要 API，例如 `GET /api/v1/projects/{id}/risks`。
- 存量合同关系 project 回填脚本或迁移。
- 清理代码文件头、注释和 REQ 引用中的旧口径，避免继续描述为“合同组作为主业务对象”。
- 单元测试覆盖 project scope、存量回填、未归属数据兜底。

### Phase 1b：前端重构

目标：先让项目详情成为可用的业务入口。

输出：

- 项目详情页信息架构调整。
- 项目详情新增“合同关系”区域。
- 项目详情按承租转租、代理运营分区展示合同关系。
- 页面不再展示合同组编码、主体 ID、规则 JSON 等技术信息。
- 普通菜单隐藏“合同组管理”，保留内部路由回退。

### Phase 2：合同录入路径重排

目标：让合同从项目进入，而不是从抽象合同组进入。

输出：

- 项目下新增上游承租合同。
- 项目下新增下游出租合同。
- 项目下新增委托协议。
- 项目下新增直租合同。
- 合同选择项目和资产范围，系统自动维护 `ContractGroup` 和 `ContractRelation`。

### Phase 3：项目台账和风险闭环

目标：让项目能回答应收、应付、逾期、到期和风险问题。

输出：

- 项目维度应收应付汇总。
- 项目维度合同到期提醒。
- 资产覆盖冲突提示。
- 下游合同缺少上游或委托覆盖时提示风险。
- 承租转租和代理运营分别计算项目指标。

### Phase 4：全局菜单与分析收口

目标：完成主导航重排和跨项目能力收口。

输出：

- 一级菜单调整为本规划第 5 节结构。
- 合同中心定位为辅助入口。
- 经营分析支持项目维度和模式分区。
- 旧 `/contract-groups` 用户可见入口清理完成。
- SSOT 文档更新完成。

## 12. 验收标准

### Phase 1

- 普通用户入口中不出现“合同组管理”。
- 项目详情能看到资产清单、合同关系、收付款摘要和风险提示的页面骨架。
- 合同关系区能区分承租转租和代理运营。
- 上游、下游、委托、直租四类合同以业务名称展示。
- 项目详情不直接展示主体 ID、`LEASE` / `AGENCY`、规则 JSON。
- 合同中心仍可用于跨项目查询和 PDF 导入，但不作为日常主入口。
- 文档同步说明 `ContractGroup` 是技术实现，不是普通用户业务对象。

### Phase 2

- 用户可以从项目详情发起四类合同录入。
- 新建合同时必须选择项目和资产范围。
- 系统能自动维护底层 `ContractGroup` 与 `ContractRelation`。
- 合同中心列表展示所属项目和合同角色。

### Phase 3

- 项目详情展示应收、应付、实收、实付、逾期和到期提醒。
- 下游合同缺少有效上游或委托覆盖时出现风险提示。
- 代理模式直租租金不进入运营方自营租金收入。

### Phase 4

- 一级菜单完成目标结构重排。
- 全局经营分析可按项目和经营模式分区。
- 旧合同组用户入口、面包屑、菜单和普通页面文案清理完成。

## 14. 边界情况

- 一个项目同时包含承租转租和代理运营，需要按模式分区汇总。
- 一个资产在时间上转入新项目，历史项目的合同和台账不能被当前项目误聚合。
- 上游承租合同覆盖多个资产，下游出租合同只涉及其中部分资产。
- 下游合同期间超过上游合同期间，需要提示覆盖风险。
- 下游合同涉及的资产没有有效上游承租合同或委托协议覆盖，需要提示风险。
- 代理模式下直租合同租金不应默认计入运营方自营租金收入。
- 同一终端租户在不同项目或不同合同中出现，应以主体去重，同时保留合同数。
- 多绑定用户查看项目列表时，应按授权主体范围展示并集去重结果。
- 合同到期后新签应形成新的合同关系，不修改历史合同关系。
- 存量合同关系无法唯一归属项目时，应进入人工确认队列，不自动写入猜测值。

## 15. 建议测试用例

- 项目详情加载后不出现“合同组”文案。
- 项目详情同时展示承租转租和代理运营两个合同关系分区。
- 下游合同只绑定项目和资产时，系统能按时间范围推导上游覆盖关系。
- 下游合同超出上游期间时，项目风险区出现覆盖风险。
- 代理运营项目的直租租金不进入自营租金收入指标。
- 资产转入新项目后，旧项目历史台账仍可追溯，当前项目不重复统计旧期间收入。
- 合同中心合同列表展示所属项目和合同角色，不展示合同组主对象。
- 多主体绑定用户只能看到授权范围内项目，并按项目主键去重。
- 存量 `ContractGroup` 回填 `project_id` 时，多项目命中应进入待人工确认，而不是随机选择。
- 隐藏普通菜单中的合同组入口后，内部回退路由仍可访问并受权限控制。

## 16. 待确认问题

以下问题不阻塞 Phase 0，但会影响后续实施细节：

- “项目运营”一级菜单下是否直接展示项目列表，还是先展示项目工作台。
- 项目是否需要区分园区、楼宇、片区等项目类型。
- 项目是否补充 `description`、`project_type`、`start_date`、`end_date` 字段；若补，需要评估历史清理过的 legacy 字段是否应以新契约恢复。
- 项目下资产是否需要进一步拆到空间、楼层、房间级经营单元。
- 押金和发票首期是否只做台账，还是需要与收付款计划联动。
- PDF 导入入口是保留在合同中心，还是也要支持从项目详情发起。
- 当前 `ContractGroup` 的“一资产一有效合同组”约束是否需要调整为“单条合同关系内不重复覆盖”，避免项目内多关系场景受限。
