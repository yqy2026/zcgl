## 1. 总裁决与第一性原理

### 1.1 设计输入合起来证明了什么

| 证据源 | 已确认事实 | 对设计的强制结论 |
|---|---|---|
| 原系统浏览器实测 | 业务覆盖面真实存在：资产台账、房间租控、权证、收入应收、催缴、客户、巡查安全；但入口按旧式菜单/技术模块堆叠，任务不连续 | 不能复制旧系统菜单、tab、iframe；缺口业务（租控、巡查、催缴）应作为独立产品域决策，不能用台账或监控页面代替 |
| 当前项目产品复核 | 后端主链路已具备：资产、项目、合同/协议、台账、收付、服务费、Party、产权证、权限、分析均有正式工程证据；主要问题是前端任务组织、上下文、闭环与可信度 | **不推倒后端重来**；先把已有能力组织成岗位工作闭环，先修可信度缺陷 |
| 市场调研 | 成熟产品的共性不是“模块数量”，而是业务动作链：资产台账 → 空间/房源 → 租赁 → 计费 → 催缴 → 收款 → 核销 → 对账 → 经营看板；但没有一个公开产品能同时满足本项目的双模式、冻结归属、Party 范围、人工确认和历史口径 | 核心领域自研，成熟交互借鉴，专项能力集成；前端必须使用市场通行的业务语言，不能使用内部聚合根名词 |

`docs/archive/reviews/2026-08-19-land-property-redesign-destructive-review.md` 是 v3.5 起的修订输入：五入口收敛、房源读视图、词汇终审裁决门、三页重排与首屏契约均由其驱动。`docs/archive/reviews/2026-08-19-land-property-redesign-v372-destructive-review.md`（v1.3，含 v1.2 终审会签）是 v3.8 的直接输入：空间原子地基、砍补清单与体验门降级均由其驱动。

同时，v1 方案对现有代码的复核仍然成立，并构成本版保留的硬发现：

- `CONTEXT.md` 与 PRD/领域模型/API 契约在服务费实收口径上真实冲突；
- 收付分摊当前是删除旧行后重插，没有版本集合；
- 收付流水没有命令幂等键，也没有外部流水号条件唯一约束；
- 项目运营方原地覆盖，没有有效期关系；
- 前端项目详情并行 fan-out 多个聚合接口拼页面；
- 用户视角审计存在登录错误反馈、产权证 422、项目空态、组织树告警等真实可信度缺陷。

### 1.2 十条第一性原理

1. **岗位任务先于模块边界**：一级入口回答“我打开系统要完成什么判断和动作”，不按数据库表或技术域命名。
2. **业务事实与派生结果严格分离**：Space 拓扑与有效期归属、核算资产、授权来源与签约快照、承诺、义务、现金、清偿、实际占有、现场限制与处置、证据、人工决定、审计是可写事实；状态、可租/即将释放集合、逾期、收缴率、风险和摘要只能派生。
3. **金额只有一条事实轴**：实收/实付只来自有效流水及其分摊；任何累计金额字段不得手填。
4. **历史不可静默改写**：归属、金额、状态、条款一旦形成有效事实，更正只能追加新版本或显式作废并保留原链；但“历史不可静默改写”不等于“历史错误不可修正”，显式、版本化、可审计的更正命令必须存在。
5. **授权先于行、聚合、计数和文件**：未授权对象的名称、ID、数量、金额、附件元数据在所有通道都不得泄漏；待核销流水的整笔金额和余额按活动范围锚点集合鉴权，不得借单锚点视图泄漏其他锚点的金额。
6. **高后果写作用显式命令**：资金、分摊、合同授权/定稿/变更/终止、服务费来源、Space 拓扑/核算映射/经营归属、产权方与项目运营方变更、空间锁定与现场限制、占有交还与交付、物业工单验收与重开、坏账核销、范围变更必须走幂等命令；正常 Agreement 不存在作废语义，低后果主数据才允许轻量 CRUD。
7. **模块化单体 + 单库事务**：合同、账期、流水、分摊和服务费保持同库强一致；不因“未来可能拆服务”预装分布式设施。
8. **CQRS 是性能优化，不是架构信仰**：只有经实测需要重构读取形态的工作面才建读模型；详情和台账默认用规范写模型强读。
9. **前端业务语言与后端模型语言分层**：后端可以叫 `PaymentAllocationSet`，用户看到的必须是“收款分摊”；内部聚合根名称不得进入导航、路由参数、按钮和提示。
10. **纵向切片先于全局重命名**：每个切片同时交付页面、命令、事实表/约束、权限、测试和旧入口退出条件；不为统一词汇先做全库重命名。

### 1.3 当前态与 v3.13 修订摘要

### 1.4 成功标准

| 编号 | 结果 | 可验收标准 |
|---|---|---|
| O1 | 从偏差到权威事实 | 任一指标或预警/异常在 2 次操作内到达组成它的合同、账期、流水或证据（验收方式：预定义 30 条“指标/预警→下钻路径”自动化脚本，每条路径操作次数 ≤2 且最终命中权威对象） |
| O2 | 动作不破坏历史 | 已有有效分摊的账期、冻结归属、已定稿条款被静默改写事件为 0；作废/更正保留原事实链 |
| O3 | 金额只有一条事实轴 | 实收/实付 100% 可回溯到有效流水及分摊（“可回溯”定义为：任一账期金额可由流水→活动分摊集合→账期的不可变链重建，且重建哈希与账面一致）；待核销余额由流水与分摊派生，可继续核销，不存在手填累计金额 |
| O4 | 人工确认与签约授权有真实门槛 | 解析字段写入主数据前 100% 有逐字段人工决定，自动绑定 Party/Space/Asset 为 0；每份终端合同均有覆盖目标 Space × 期间的不可变授权快照，缺口或冲突时零写入 |
| O5 | 权限不从统计侧漏 | 未授权名称、ID、数量、金额、附件元数据在定义的全通道矩阵中泄漏为 0；跨锚点流水的单锚点用户不得见整笔流水金额或待核销余额 |
| O6 | 资金命令可安全重试 | 同一资金命令并发重复 50 次只产生一次副作用；同键异载荷 409；回放重新鉴权 |
| O7 | 上下文连续 | 下钻和返回保持项目、合同、账期和筛选；删除 2% 统计化门槛，改为 3 条自动化 smoke 中 URL 参数回归保持项目/合同/账期上下文不丢 |
| O8 | 用户语言可理解 | 岗位现场 checklist：用户在 30 秒内凭一级导航或顶栏动作找到“登记收款”“录入合同”“找可租空间”“找产权证”“处理物业问题”，并能从合同或流水详情 2 跳内到达往来方详情；导航、URL 上下文和按钮不出现 DDD/ERP 内部术语，且不出现“合同关系”作为页面对象名 |
| O9 | 保留已验证投资 | 现有主链路回归测试持续通过；任何表重命名必须证明产生行为收益，纯词汇统一不作为重命名理由 |
| O10 | 产品可信度 | 已知登录错误路径、产权证 422、组织树告警、项目空态和 PDF 导出占位在第一批切片内清零；正式入口无死路由、无未挂载页面 |
| O11 | 性能不倒退 | 列表/详情 P95≤800ms；工作台/分析/搜索 P95≤2s、P99≤5s；超预算页面必须显示陈旧水位或降级态，不得静默慢 |
| O12 | 空间与物业事实不撒谎 | 合同终止、实际交还、现场修复、重新可租四件事可分别追溯；存在未解除现场限制时“可租”误报为 0；物业问题均能到达责任人、期限、证据、验收和重开链 |

## 2. 必须保存什么、只能派生什么

### 2.1 系统必须保存的事实

| 类别 | 典型事实 | 规则 |
|---|---|---|
| 稳定身份 | Party、Organization、Space、Asset、Project、Agreement、账单义务、PropertyWorkOrder | `Space` 是物理拓扑节点，`Asset` 是经营核算对象，`Project` 是经营上下文；三者不可用一个表的不同状态互相冒充 |
| 有效期关系 | Space 父子拓扑、`asset_space_assignments`、`space_project_assignments`、项目运营方、组织代表 Party、用户主体范围 | Space 父子关系表达物理结构；Asset 与 Project assignment 均明确生效区间；不按名称、编码或展示顺序猜测 |
| 出租授权 | `property_leasing_authority_revisions`、`agreement_authority_snapshots`、窄 `agreement_authority_links`、`agreement_authority_defects` | 支持 `direct_ownership` / `sublease` / `agency_leasing`；签约冻结覆盖 Space × 期间的来源修订、权限和身份快照；来源后续变化不回写原快照 |
| 合同覆盖 | `contract_space_links` | 每个可出租叶子 Space 同一时点最多一份活动终端租约；合同终止关闭承诺覆盖，但不等于实际交还或重新可租；不虚构空间级金额 |
| 承诺 | 合同/协议定稿、补充协议、续租后继关系、计费规则、服务费比例、覆盖空间、定价底价与依据 | 定稿形成可追溯版本；纠错、商业变更、续租语义分离；根身份变化不通过普通纠错覆盖 |
| 义务 | 租金应收/应付账单、服务费应收、押金应收 | 由生效承诺确定性生成；冻结历史归属和来源版本 |
| 现金事实 | 收付流水、发生日期、金额、实际收付方、资金归属方、凭证、外部单号、非空范围锚点集合 | 命令接受非空锚点集合；UI 默认单锚点并允许登记时显式多选；集合版本化且 active 流水活动锚点数 ≥ 1；不可被累计字段替代 |
| 清偿关系 | 流水分摊到账单；坏账核销 | 决定账单实收/实付；并发、总额和范围受强约束；坏账核销单列统计、退出欠费口径 |
| 实际占有与交付 | `SpacePossessionReturn`、`SpaceHandoverRecord` | 合同终止、实际交还、修复完成和新租户交付是四个独立事实；交还或交付冻结发生时的 Project/operator 上下文 |
| 物业现场事实 | `InspectionPlan`、`InspectionRun`、`InspectionReview`、`InspectionFinding`、`PropertyWorkOrder`、`PropertyWorkAttempt`、`PropertyWorkAcceptance`、`SpaceOperationalRestriction` | 周期巡查计划/执行提交、交还/交付专用检查复核、问题、责任人、期限、处理证据、验收/驳回/重开均为事实；例行执行无 review，同一 Space 可存在多个独立现场限制 |
| 证据 | 合同盖章扫描件、授权依据、跨项目共享协议扫描件、收付凭证、巡查/工单/交接附件 | 正式证据采用不可变内容 + 证据版本链；最后一份事实附件不可删；现场记录冻结创建时 Project/operator |
| 产权证附件 | 产权证扫描件/照片 | 沿用现行轻量规则并做最小加固：至少保留一份；替换/重登时旧证附件转历史只读，不建完整版本管理 |
| 人工决定 | 解析字段决定、对象显式绑定、授权来源选择、服务费来源核对、底价例外、现场限制释放、工单验收/驳回 | 记录操作者、版本、理由、证据和结果；模型建议不能越过人工决定 |
| 跟进事实 | 联系记录、承诺还款日 | 轻量记录，不改变金额、逾期或风险状态；沿用跟进权限与审计 |
| 审计 | 命令、原因、前后摘要、权限范围摘要、结果 | 只追加；与 domain event 分离；不泄露 PII 或存储路径 |

产权/经营权的唯一可写事实源是只追加的 `property_leasing_authority_revisions`。每个 `source_root_id` 的修订是该来源在一组叶子 Space 上的**完整权利快照**，而不是局部 patch；`ChangeAssetOwner` 与 `RecordOperatingAuthorityRevision` 都只通过追加完整修订表达变化，携带业务生效日、权利主体/有权代表、完整覆盖叶子 Space、允许动作、证据版本和 `supersedes_id`。预先登记的未来修订若需改期、替换或取消，也只能追加一个 superseding 完整修订；“取消”以恢复届时应继续有效的完整权利快照表达，不删除旧排期。权威读取按 `as_of` 从线性修订链选择最新已生效且未到期的完整修订，绝不依赖投影。已生成台账的冻结产权方归属不回写。`Asset.owner_party_id` 仅是当前时点的非写入展示投影，普通 CRUD/导入不得直接修改；命令记录 `projected_from_revision_id/next_transition_at`，当前立即生效时事务内刷新，未来边界由耐久到期任务幂等刷新并由周期修复扫描兜底。显示读取若发现 revision id 不匹配必须从权威修订返回并告警，投影漂移不得用于授权。产权沿革从来源修订重建，不从投影或宽泛审计猜测。未核销流水的范围锚点属于现金事实的一部分，其增删改走 `ExtendPaymentScope`/`CorrectPaymentScope` 命令而不是通用 PATCH。

**Space/Asset 最终裁决**：新增最小 `Space` 表作为地块、建筑、楼层、房间/铺位/车位等物理拓扑的唯一身份；`Asset` 只承担经营核算与权属台账，不再保留 `Asset` 双用途分支。`asset_space_assignments(asset_id, space_id, relation_type, effective_from, effective_to, source_revision_id)` 以有效期关联两者：一个 Asset 可覆盖多个 Space；每个可出租叶子 Space 同一时点至多一个 `primary_accounting` Asset，`reference` 关系不得用于授权、金额分摊或 Project 推断。`Project` 不是物理树父节点，而是经营上下文；`space_project_assignments(space_id, project_id, effective_from, effective_to, source_revision_id)` 同一 Space 同一时点最多一个活动版本，不保存 `operator_party_id`。当前运营方按 assignment 对应 Project 的 `project_operator_assignments(as_of)` 解析；物业记录、合同授权快照和交接记录冻结发生时的 Project/operator，不随未来调配回写。

Space 基础写入只允许三类预览/提交命令：`Preview/CommitSpaceTopologyChange` 修改类型化父子树，`Preview/CommitAssetSpaceAssignment` 修改核算映射，`Preview/CommitSpaceProjectAssignment` 修改经营上下文。预览必须列出父子层级、叶子重复/孤儿、面积守恒差异、现有产权/经营权覆盖、活动或未来合同、开放工单、活动限制、计划中巡查/交付和新旧 Project/operator 可见性；提交锁定相关 Space、祖先链、Asset/Project assignment 和受影响来源修订后重新计算预览摘要。调配不回写活动合同、开放工单、限制和历史交付记录的冻结归属；跨生效边界存在这些对象时必须同时拥有新旧范围、填写原因并显式确认影响。Asset 映射变化不自动扩张出租授权，缺少覆盖来源修订时后续签约失败。禁止自环、祖先环、非法父子类型、重复稳定叶子 ID、多父、非根孤儿和子级面积合计超过父级可核面积；导入时无法证明关系或面积的行进入拒绝桶。

**合同—Space 覆盖与出租授权**：`contract_space_links` 保存合同对叶子 Space 的半开期间 `[covered_from, covered_to)`，并在行内冻结 `coverage_lane=terminal_occupancy|authority_source`。只有终端租约使用 `terminal_occupancy`；上游租约和委托协议作为出租授权来源使用 `authority_source`。每个可出租叶子 Space 同一时点最多一份 `terminal_occupancy + enforced` 覆盖，数据库使用局部 GiST 区间排斥约束而不是普通部分唯一索引；上游/委托来源与其授权的终端租约允许同 Space/期间重叠，命令仍分别校验来源权限和终端占用，冲突码 `SPACE_ALREADY_LEASED` 只用于终端占用冲突。覆盖关系不证明出租权，`RecordAgreement` 必须先调用 Agreement Authority 深模块完成来源解析、校验和快照冻结：

```text
ResolveAgreementAuthority
ValidateAgreementAuthority
FreezeAgreementAuthoritySnapshot
```

授权模式只有三种：`direct_ownership`（产权/经营权事实直接出租）、`sublease`（上游承租权转租）、`agency_leasing`（有效委托关系代理出租）。直租不伪造上游 Agreement link，但必须引用签约时点有效的产权或经营权事实修订；转租和代理只使用窄 `agreement_authority_links`。统一不可变授权快照至少包含：

```text
target_agreement_id
authority_mode
source_fact_type
source_fact_revision_id
covered_space_id
covered_from
covered_to
permission_snapshot
source_identity_snapshot
```

快照必须无缺口覆盖目标 Space × 合同期间；冲突来源一律拒绝，相同重叠来源也必须显式选择唯一来源。签约 Party 必须与来源关系一致：直租为权利人或明确授权代表，转租为上游承租人或明确授权代表，代理为有效委托关系导出的主体。来源后续终止、到期或法律范围修正只派生 `agreement_authority_defect`，不得回写或自动终止原终端合同；未处置缺陷阻断续租、增加 Space 和新承租户交付。`ResolveAgreementAuthorityDefect` 只允许登记替代来源并重验覆盖，或附法律证据确认继续；成功时原子追加处置并关闭 defect。用户选择“终止合同”时不调用该命令，而是携 defect 上下文进入唯一 `TerminateAgreement` 工作区；终止事务同时追加 `resolution_type=terminated`、终止回执并关闭 defect。原授权快照始终不可修改。

**Space 五维事实与供给口径**：不再把空置、在租、临期、停用、待确权、现场不可用压入一个可手改状态。每个 Space 分别表达：

1. 合同承诺：无活动终端租约 / 有活动终端租约 / 临期覆盖；
2. 实际占有：未交付 / 已交付占用 / 已交还；
3. 权属合规：正常 / 待确权 / 合规冻结；
4. 行政可用：启用 / 停用；
5. 现场可运营：`可交付` / `受限` / `不可用` / `待评估`。

现场可运营是确定性投影，不是可手改枚举，优先级为：未完成初始化或最新交还/入住检查尚未接受复核 → `待评估`；存在阻断继续占用或认定空间无法安全进入的活动限制 → `不可用`；存在其他活动运营限制（含只阻断营销/签约/续租/交付或观察项）→ `受限`；已完成有效评估且无活动限制 → `可交付`。同一事实集合在工作台、Space、物业和供给视图必须得到相同结果；阻断动作仍由 `restriction_type × blocking_level` 决定，四值主标签不替代限制明细。

锁定是独立 `space_locks` 事实，不是 Space 状态；同一 Space 仅一条活动招商锁定，锁定—签约交接继续执行 `SPACE_LOCKED_BY_OTHER` 不变量。现场限制由可并存的 `SpaceOperationalRestriction` 表达，不得复用招商锁或行政停用。派生公式唯一为：

```text
可租 = 无活动终端租约
          AND 实际占有 ∈ {未交付, 已交还}
          AND 无活动招商锁定
          AND 权属/合规正常
          AND 行政启用
          AND 现场可运营 = 可交付

即将释放 = 临期合同覆盖
        AND 已知预计释放日
        AND 未命中永久性合规冻结
```

临期合同只进入即将释放，不得计入可租。合同终止只结束法律承诺；`RecordSpacePossessionReturn` 记录实际交还；物业整改与验收解除现场限制；满足全部公式后才重新派生为可租。交还后仍待维修时，准确状态是“无活动租约 + 已交还 + 现场不可用”。不再使用 `ReleaseSpace` 把 Space 直接改成“空置可租”。

**押金最终裁决**：本期建设最小押金域，不保留“只读余额”或整域隐藏分支。合同定稿按押金条款生成押金应收；每个 `payment_flow_root_id × deposit_receivable_id` 形成唯一、不可变身份的 `deposit_holding_lot`。`deposit` 流水活动分摊快照每次切换时，系统以该 root 对押金应收的新旧有效分摊差额追加 signed `deposit_holding_adjustment`，正数确认新增持有、负数冲减误分金额，修订本身不可覆盖；`recognized_amount = SUM(adjustments)`。退租结算由 `DepositOffset`/`DepositReturn` 追加 `deposit_disposition`（`offset`/`return`）：抵扣引用欠费义务，退还引用同事务创建的 `deposit_return` 流水；两者都不把原押金流水重新分摊到其他义务。数据库与命令共同保证每个 lot 的 `recognized_amount >= 0` 且有效 disposition 合计不超过该金额；`total_deposit`/可用押金仅由 recognized holding − 有效 offset − 有效 return 派生。B0-A 只核验源数据、会计边界和签字证据，不重开做/藏选择。

**底价合规补充**：`floor_price` 必须配套 `floor_price_valid_until` 与评估依据（评估报告编号/备案号）；过期底价不拦截签约，但进入待处理预警。

通用 `Attachment` 按 `owner_type` 拆分生命周期：`contract` 和 `payment_flow` 的正式证据采用不可变内容 + 版本链，替换只追加并保留旧链；`property_certificate` 沿用现行轻量规则；`asset` 非正式证据附件维持现行规则。三类规则在 domain-model §4.22 分列，不共用一条“替换即删”规则。

### 2.2 只能派生的状态和指标

以下状态不得由用户直接翻改，也不得形成第二条可漂移真相轴：

- 合同/协议已到期；
- 账期 `unpaid/partial/paid`；
- 流水待核销余额（有效流水金额 − 有效分摊合计）和流水 `unallocated/partially_allocated/fully_allocated`；
- 未核销停留时长（登记日/最近一次分摊变更日到当前，按工作日分桶提示，不生成任务）；
- 终端租户租金逾期、逾期金额、账龄分桶和收缴率；
- 承诺到期未还（跟进记录有承诺还款日且到期后未核销）；
- 当前 Party 业务角色；
- 产权证资料不完整、权利人与当前产权方不一致、证载面积/用途与台账面积/实际用途偏差；
- 合同更正后历史账期与当前条款不一致；
- 服务费来源、比例、基数或归属不一致；
- 项目、合同与协议的经营摘要；
- 当前 Space 的合同承诺、实际占有、权属合规、行政启用、现场可运营五维摘要；
- 资产级空间状态分布（按叶子 Space 五维聚合为可租/在租/受限/待评估等徽章；不派生单一“资产当前状态”或资产级空置时长，空置时长只在叶子 Space 行内展示）；
- 可租集合与即将释放集合（严格按 §2.1 两套公式，不互相并入）；
- 招商锁定的转化回执（签约事务解除本方/空挂锁时派生“已转化为合同 XXX”，进入工作台“我的锁定”清单）；
- Space 空置时长分桶（<3 月 / 3–12 月 / >1 年）；空置起算锚点 = 最近一次实际交还后满足全部可租条件的时点，从未出租的 Space 以导入确认且完成现场评估的时点为锚；
- 楼栋/楼层节点的可租、即将释放、占用和现场受限数量，均从叶子 Space 同源聚合；
- 盘活进度：滚动 12 月“不可租 → 可租 → 新合同交付”的转化漏斗；事实不足一个滚动窗口时灰显“数据积累中”，不得以 0 充当成绩；
- 租金滚存：未来 12 月应收 × 模式 × 项目（已确定义务 + 临期释放预测），只读经营应收视图，标注“非会计口径”；
- 释放收入潜力：即将释放 Space 的 Σ 面积 × 当前底价 × 12，纯派生，与租金滚存同口径水印；
- 合同授权来源有效性与 `agreement_authority_defect`；
- 工单逾期、待验收、被驳回、重开次数，巡查计划执行率与发现闭环时长；
- 底价有效期到期预警；
- 坏账核销后账期退出欠费口径、单列坏账统计；
- 押金可用余额 = `SUM(deposit_holding_adjustment.amount)` − 有效 `deposit_disposition(offset)` − 有效 `deposit_disposition(return)`，按稳定 holding lot 聚合；禁止手填、另存余额字段、把全量分摊快照重复累计，或把原押金流水重新分摊到欠费义务。
- 运营方收入、成本、服务费和经营净流入口径。

例外项用确定性键 `source_type/source_id/rule/version` 派生。源事实修正后例外自然消失，不保存“已处理”按钮。逾期跟进可以记录联系事实，但不能关闭逾期或改变金额。

### 2.3 不可逆错误优先级

P0 设计首先防止以下错误，而不是首先追求页面数量、动画或代码复用：

1. 未授权业务对象、数量、金额或附件信息泄漏；
2. 流水或分摊被覆盖，无法还原真实收付；
3. 资产或项目调整追溯改写历史经营口径；
4. 解析候选自动变成主体、资产或正式字段；
5. 同一请求重复产生合同、账期、流水或分摊；
6. 跨项目共享证据被无权用户替换；
7. 迁移按名称猜关系或用金额容差掩盖差异。

## 3. 实施前 P0 语义裁决

### 3.1 服务费两条事实轴

现行资料存在**三向冲突**，不是单点冲突：

- `docs/prd.md`、`docs/specs/domain-model.md` 和 `docs/specs/api-contract.md` 已规定：服务费**应收** = 代理直租租金**实收** × 委托协议历史比例；服务费**实收**由 `service_fee_receipt` 流水独立登记并分摊形成；
- `CONTEXT.md` 的 `ServiceFeeLedger` 口径为：`amount_due` = 直租租金 `amount_due` × 比例（应收基数按租金**应收**），`paid_amount` 随来源直租租金实收派生，并禁止服务费实收独立登记；
- 因此冲突包含两个差量：①服务费应收基数取直租租金应收还是实收；②服务费实收是独立现金事实还是直租租金实收的派生值。ADR 必须同时记录并裁决这两个差量，不能只修实收一条。

本方案采用可还原现金事实、且与三份现行 SSOT 一致的口径：

```text
服务费应收 = 同租金账期代理直租租金有效实收 × 委托协议历史比例
服务费实收 = 有效 service_fee_receipt 流水分摊到该服务费应收的金额合计
```

直租租金实收只能证明服务费计算基数成立，不能同时证明产权方已支付服务费。该口径**保留** `CONTEXT.md` 的业务约束“服务费应收不旱涝保收、只随已对账直租租金形成”，但**修订**其“应收基数按租金应收、实收随直租租金实收派生并禁止独立登记”的结论：应收基数按已对账直租租金实收；服务费实收是产权方支付给运营方的独立现金事实，必须通过 `service_fee_receipt` 流水承载。实施前必须修正 `CONTEXT.md` 对应词条、补 ADR 记录上述两个差量并取得业务确认；ADR 必须直接引用 2026-06-19 grill 的业务依据，并显式标注本方案“保留其不旱涝保收结论、修订/推翻其实收不独立登记结论”，避免 `CONTEXT.md` 与 ADR 各说各话；在唯一口径形成前，服务费新架构不得编码。

两个差量的统一前提是**资金归属方**：收付流水新增 `funds_beneficiary`（`operator`/`property_owner`），由流水类型 × 授权模式推导、用户只读确认。产权方直租和委托代理的终端租金都是 `property_owner` 账户事实，前者解析到签约冻结的有效权利主体，后者解析到签约冻结的委托方（运营方仅代登记）；承租转租的终端租金和服务费则是 `operator` 账户事实。任何模式都不得从当前 `Asset.owner_party_id` 投影推导资金归属；同一笔流水只允许一个资金归属方。ADR 顺序改写为：先落 `funds_beneficiary` 模型，再记录服务费两个差量作为其推论。

**服务费修订机制（v3.11 最终裁决）**：`CorrectObligation` 与服务费修订复用“追加版本 + 活动切换 + 单活动版本唯一约束”的技术骨架，但领域命令和来源语义分列。`CorrectObligation` 处理人工受控账单更正；`service_fee_receivable_revisions`/`ReconcileServiceFeeSource` 处理来源身份 + 计算指纹变化后的重算与 mismatch，保留独立命令、来源身份、计算指纹、审计和错误码。后续 ADR 只记录共享骨架、锁序、约束名和迁移细节，不得重开“是否复用骨架”或把两种命令合并。

### 3.2 预警不是任务；物业工单是窄承诺对象

通知、解析线索、产权证风险、金额异常和授权缺陷默认仍是派生预警，不泛化为任务中心：它们没有领取、完成、关闭或转派语义，源事实修复后自然消失。

物业工单是明确例外，因为它具备责任人、期限、处理证据、提交验收、接受/驳回和重开生命周期。该例外只建立 `PropertyWorkOrder` 及其处理/验收事实，不建立通用 BPM 或全域任务引擎。巡查发现可以触发工单，但 `InspectionFinding` 与工单保持独立身份和引用关系。

### 3.3 经营视角不是授权范围

- `EffectivePartyScope` 决定用户可以访问哪些对象；常规列表、详情、搜索、附件和命令不接受 `view_mode`。
- `view_mode=owner|manager|all` 只用于显式声明需要经营解释的分析和摘要。
- `all` 是混合授权并集下的浏览/分析模式，不是第三种单一经营口径。
- 常规并集列表按业务主键去重。
- 综合分析在客户双指标需要单视角时拒绝 `all`。
- 项目分析若客户双指标只是载荷的一部分，只抑制这两个字段并给出原因，其他合法指标继续展示。
- 工作台组合驾驶舱按“项目分析式”混合载荷端点处理：`all` 下只抑制客户双指标并给原因；独立的综合分析/客户双指标页面仍对 `all` 硬拒绝。该端点分类写入 API 契约，不得由前端自行解释。

### 3.4 词汇裁决（架构师任务，不阻断独立切片）

命名是信息架构的地基。**架构师按本表裁决 → 写入 `PRODUCT.md`/`CONTEXT.md` 词汇表 → 一次会议关闭**；该任务不阻断无关切片，但对应业务切片编码前不得再留双词。以下为裁决值，业务只允许在一词·一义·一层框架内修正，不得留空：

| 现用词 | 推荐裁决词 | 层级 | 裁决要点 |
|---|---|---|---|
| 账期 / 账期义务 | 账单（操作粒度）；账单集合称“账单列表” | 操作层 | “台账”不再作“账本集合”义；“资产台账 / 合同台账”为对象登记册复合专名；时间词“账期”归还日历字段 |
| 收款与欠费 | 收付 | 操作层 | 域内同时覆盖收款与付款（上游成本）；“欠费/欠付”降为列表筛选值 |
| 租户与产权方 | 往来方 | 操作层 | Party 四角色统称；“方”兼容法人与自然人 |
| 运营工作台 / 项目运营 | 工作台；项目并入资产域为“项目总览” | 操作层 | 消除“运营”词头碰撞 |
| 资产（入口名） | 入口名维持”资产”，词表声明其为空间脊柱域的操作层用法；组合、资产台账、决策报表义分层使用；**同词嵌套消歧（v3.10 已裁死）：一级入口维持”资产”，二级节点改”台账”，页面标题保留”资产台账”；”资产 › 资产台账”不得成立** | 操作层 vs 决策层 | 一词·一义·一层，堵住”入口用决策层词”与”资产包含资产”的自嵌套 |
| 项目 / 园区 | **项目**=经营容器（系统词）；**园区**=项目形态类型值（展示词） | 操作层 vs 展示层 | 一处裁决全库统一，禁止斜杠并存进菜单、对照表或顶栏 |
| 物业 | **本期正式业务域**；一级入口“物业”，覆盖巡查、问题、工单处理/验收/重开、现场限制、实际交还和交付检查；不扩成完整物业 ERP/IWMS | 操作层 | 物业事实挂稳定 `space_id`，工单与一般预警严格区分 |
| 巡检计划 / 巡查；记录（v3.12 增补裁决） | **巡查**为唯一域词；“巡查计划”为菜单/tab 专名；页内历史聚合 tab 用**“现场档案”**，不用无内容词“记录” | 操作层 | 菜单、路由、工作区矩阵、验收门与 SSOT 同步清单必须同词；编码前不得再留“巡检” |
| 合同/协议 | **合同**为域词；租约、上游合同、委托协议为类型筛选专名 | 操作层 | 域词外延覆盖域内全部对象；与“＋录入合同、合同更正、合同临期”同词根 |
| 预警/异常/待处理 | 待处理 | 操作层 | 与 §3.2 原文一致；无 to-do 任务暗示 |
| 空间 / 铺位（v3.13 终词） | 物理统称**空间**；**可租 / 即将释放**为供给集合视图词；**可出租**保留给结构属性；铺位为形态类型值 | 操作层 vs 视图层 | “房源”纪律退役；待确权/停用等合规冻结态禁止进入可租 |
| 核销 / 分摊 | 核销为用户词；分摊保留内部词 | 操作层 | 沿用 §4.3 分层 |

裁决纪律：架构师裁决结果写入 SSOT 后，菜单树、路由、快捷动作和验收项按终词预对齐；若签字时改动任一词，必须执行全量替换而不是局部悬置。**v3.9 增补三项必裁在 v3.11 的结果**：①“资产台账”节点消歧已裁死为一级「资产」→二级「台账」，页面标题保留「资产台账」；②“账单”为唯一对象词，“账期月”为唯一时间字段词，用户文案与 URL 参数不得保留“账期/账单”双轨；③物理统称“空间”。**v3.12 增补**：物业域统一用“巡查/巡查计划/现场档案”，不再出现“巡检计划”或“记录”tab。**v3.13 增补**：“房源”作为界面集合词退役；供给视图终词为“可租 / 即将释放”，“可出租”仅用于可出租叶子 Space 等结构属性；市场调研引用与历史评审标题中的“房源”按原文保留，不作为界面词。

### 3.5 金额含税口径

MVP 所有合同金额、账单金额、流水金额默认**含税**；`is_tax_included=true` 与 `tax_rate` 为 SSOT 口径声明，报表/导出页必须显示“金额含税”口径角标。任何页面不得混用含税与不含税口径；未来开票对接前再单独立项做价税分离。

## 4. 产品架构与信息架构

### 4.1 主轴选择

| 候选 | 优点 | 根本缺陷 | 结论 |
|---|---|---|---|
| 资源中心 | 资产、空间、权证和 Party 档案清晰 | 运营人员仍需自行拼合同、账期和收付 | 并入资产脊柱，不做独立主轴 |
| 项目中心 | 保持组织与资产上下文 | 易形成超大详情和多层 Tab | 保留为上下文容器和资产域的项目总览，不做唯一执行入口 |
| 合同与收款执行轴 | 从决策直达承诺、账期、流水与证据 | 若把合同、收款、服务费压成一个“作业”抽屉，会退回技术聚合 | 分解为“合同、收付”两个问题入口 |
| 六域业务流 | 有什么→凭什么出租→承诺什么→现金如何清偿→现场是否可运营→谁负责处置 | 需要更强词汇纪律和跨域编排 | **采用：工作台 / 资产 / 合同 / 收付 / 物业五个任务型业务入口 + 往来方档案库（按岗位动线出发频率排序，往来方固定导航末位）** |

推荐心智模型：

- **工作台回答“今天该处理什么、整体盘面如何”**：一线看待处理，决策层看组合驾驶舱；
- **资产回答“有什么、在哪、当前是否可租、未来何时释放”**：Space、台账、项目总览、产权证构成物理与核算脊柱；
- **合同回答“凭什么出租、承诺了什么、如何变更或续租”**：三种授权模式、终端租约、上游合同、委托协议、纠错/商业变更/续租；
- **收付回答“该收多少、现金到了多少、如何核销”**：账单、流水、核销与服务费；
- **物业回答“现场发生了什么、谁处理、是否验收、能否交付”**：巡查、问题工单、现场限制、交还与交付；
- **往来方回答“谁以什么来源角色参与”**：Party 档案库，按来源角色切片；导航末位保留为档案入口，不作为任务型业务入口；详情可从合同/流水 2 跳到达；
- **组织与权限、数据工具、系统配置进入设置中心**，不占用业务导航。

### 4.2 一级信息架构

一级入口收敛为五个任务型业务入口 + 往来方档案库；设置中心对具备管理能力的用户渲染为导航末位一级入口，其余用户保留头像菜单入口：

| 入口 | 回答的问题 | 主要工作面 |
|---|---|---|
| 工作台 | 今天该处理什么、整体盘面如何 | 单页按角色渲染：决策层落组合驾驶舱，一线落待处理；页内可切换 |
| 资产 | 有什么、在哪、当前是否可租、未来何时释放 | 空间（拓扑+可租+即将释放）、台账、项目总览、产权证 |
| 合同 | 凭什么出租、承诺了什么、如何纠错/变更/续租 | 合同台账、授权依据、录入、账单预览、纠错、商业变更、续租 |
| 收付 | 该收多少、现金到了多少、如何核销 | 收款 / 付款 / 待核销三个一级 tab；租金、押金、服务费为类型筛选 |
| 物业 | 现场发生了什么、谁负责、是否验收、能否交付 | 问题工单、巡查、现场限制、交还与交付 |
| 往来方 | 谁以什么来源角色参与、历史如何 | 档案库：按产权方/上游出租方/委托方/终端承租方/运营方/资金归属方/实际收付方/物业服务方筛选；导航末位 |

全局搜索覆盖项目、合同/协议、空间/资产、客户与 Party、产权证（含证号，v3.9 补）。通知仍是顶栏提醒，不升级为一级”任务”入口。组织与权限、数据工具（导入任务/字典/系统设置/导出记录）、审计日志统一进设置中心。

**终版两级菜单树（最大深度 2，详情走子路由不进菜单；全部节点为名词性目的地）**：

```text
工作台                （零子节点：按角色渲染——决策层落驾驶舱，一线落待处理；页内切换）
资产
├─ 空间               （空间树 + 可租/即将释放双视图）
├─ 台账               （页面标题“资产台账”）
├─ 项目总览
└─ 产权证
合同                  （零子节点：合同台账；授权/录入/纠错/变更/续租走子路由与页内动作）
收付                  （零子节点，一级 tab 平铺：收款 ｜ 付款 ｜ 待核销；租金/押金/服务费为类型筛选）
物业                   （零子节点：现场任务 / 巡查计划 / 现场档案为页内 tab；详情走子路由）
往来方                （零子节点：档案库；来源角色=筛选；导航末位）
设置中心              （仅管理岗可见，导航末位）
├─ 组织与权限
├─ 数据工具
└─ 审计日志
```

- **资产域序位**：按岗位出发频率排序——空间（招商日频）→ 台账（资产与权证管理员日频）→ 项目总览（周期决策）→ 产权证（低频治理）；
- **物业页内工作面**：一级入口一步直达“现场任务”tab；“现场任务”含我的待执行、待验收、超期和全部，“巡查计划”含计划、下一次执行和覆盖 Space，“现场档案”含已关闭工单、巡查历史、交还/交付与限制记录；工单/巡查详情走子路由，不进入菜单；
- **零子节点入口规则**：零子节点入口必须是一步直达的高频目的地；有子节点的入口，子节点必须是异质任务而非同一工作面的两个视角。“任何一级入口不得恰好只有 1 个子节点”的旧单节点测试整条删除；
- 动词不进菜单：导入、确认、核销、录入、结算、导出都是页内按钮或快捷动作，不是菜单节点；
- 录入无持久会话、无草稿态，由顶栏”＋录入合同”和合同台账页按钮发起，不设菜单节点；存量合同结构化导入入口为合同台账页按钮（与资产导入同构，v3.9 回迁），导入异步任务清单留设置中心”数据工具”；
- 服务费操作面唯一：收付 › 收款 tab 的“服务费”类型筛选态；代理结算岗默认落地 = 收款 + 服务费筛选；不设“服务费”一级 tab 或“资金流水”菜单节点；
- 往来方保留为档案库入口，不作为任何任务型业务入口或岗位默认落地页；O8 验收保持“从合同或流水详情 2 跳内到达往来方详情”；中期在合同录入流内提供 Party 就地建档；
- 词汇裁决为架构师任务（§3.4），不阻断无关切片；对应切片编码前必须使用唯一终词。

### 4.3 命名分层：内部模型名与用户语言必须分开

后端需要严谨的内部概念，但用户语言遵循市场通行业务词汇：

| 内部模型/模块名（代码与文档） | 前端可见名（导航、标题、按钮、URL 参数） |
|---|---|
| `Project` / 未来可能的 `OperatingUnit` | 项目（园区=项目形态类型值）；项目总览挂资产域 |
| `ContractGroup` / 未来可能的 `OperatingArrangement` | 不单独展示；页面按合同/租约/上游合同/委托协议显示，禁止“合同关系”作为页面对象名 |
| `Contract` → `Agreement` 概念 | 合同（域词）；租约 / 上游合同 / 委托协议（类型筛选专名） |
| `ContractLedgerEntry` → `ChargeObligation` 概念 | 账单；账单集合称“账单列表”；“台账”不作账单集合义，账期降为时间字段 |
| `OperationalPaymentFlow` | 收付流水 / 收款 / 付款 |
| `PaymentAllocationSet` / `PaymentAllocation` | 核销（用户词）；分摊保留内部词 |
| `ServiceFeeLedger` → `ServiceFeeReceivable` 概念 | 服务费应收 / 服务费结算 |
| `Party` | 往来方（统称）；产权方/上游出租方/委托方/终端承租方/运营方/资金归属方/实际收付方/物业服务方按来源角色切片 |
| `Space` | 空间；“可租 / 即将释放”为供给视图词；“可出租”仅用于叶子空间结构属性；铺位/房间/车位是空间形态值 |
| `PropertyWorkOrder` | 物业工单；问题、处理中、待验收、已完成、已取消为业务状态 |
| `EffectivePartyScope` | 数据范围 / 当前视角 |
| `read model` / `projection` | 工作台数据 / 统计口径 |

命名红线：

- 一级导航、按钮、空态文案不得出现 `OperatingUnit`、`OperatingArrangement`、`cash-application`、`master-data`、`access-governance` 等内部或 ERP 术语；
- “合同关系”只作为内部建模词，不得进入导航、标题、按钮、URL 参数或空态；“合同/协议”斜杠词不得进入一级/二级菜单节点，页面按合同、租约、上游合同、委托协议显示专名；
- 后端表名是否重命名由迁移设计按“是否带来行为收益”决定，纯词汇统一不作为开工理由；
- 用户手册和界面可以先于数据库改名切换词汇，数据库遗留名不得反向决定用户心智。

### 4.4 全局框架与上下文协议

```text
+-------------------------------------------------------------------------+
| 顶栏：工作台/资产/合同/收付/物业/往来方 │ 面包屑: 资产 › 空间 › A-301  │
|       范围摘要 · 全局搜索 · 通知 · ＋收款 · ＋录入合同 · 用户            │
+-------------------------------------------------------------------------+
| 主工作面                                      关系/证据检查器（按需）      |
+-------------------------------------------------------------------------+
```

面包屑并入顶栏单行，保持唯一规范叙事（URL 即位置）；顶栏常驻 `＋收款`、`＋录入合同` 两个全局快捷动作，按角色权限渲染，无权限不显示；`＋付款` 回收到收付页“付款”tab 页头。跨域下钻（如组合驾驶舱进入项目驾驶舱）不重写面包屑，而用来源条“来自 工作台”表达来路。

可分享和可返回的业务上下文以 URL 为真相：

| 参数 | 含义 |
|---|---|
| `project` | 当前项目 |
| `contract` | 当前合同/租约/上游合同/委托协议 |
| `period_from/period_to` | 账单的账期月范围（§3.4 v3.9 增补②终词，原"账期/账单范围"双轨描述随终词清理） |
| `mode` | 承租转租/代理运营过滤，不是授权视角 |
| `alert` | 被定位预警/异常的稳定例外键（明文业务参数，服务端鉴权后解析；例外键非机密） |
| `return_to` | 应用内白名单路由参数，不接收任意外部 URL |
| `view_mode` | 仅分析路由允许 |

筛选、排序、分页和选中的工作记录进入 URL；临时表单输入留在表单状态；服务器数据只由 React Query 管理；认证和范围摘要仍由 Context/Zustand 管理。任何跨对象链接必须通过类型化导航器生成。`return_to` 只接受应用内白名单路由参数，前端与命令成功页均拒绝任意外部 URL；不引入服务端 token 签发/过期/回放无效化设施。

凡带 `alert` 例外键进入的页面必须渲染来源条“⟵ 来自预警：城东园区 3 户逾期（08-17）”；命令成功页提供“返回来源”主按钮，消费白名单 `return_to` 回到出发页，并让用户可见地看到该预警随派生事实消失。业务通知跳转一律携带 `alert` 例外键，落点为工作台待处理对应例外行或对象详情；通知集合与待处理对应例外集合必须同源同口径。

## 5. 核心工作面设计

### 5.1 工作台（单页，按角色渲染）

工作台为零子节点一级入口，单页按角色渲染，页内可切换“待处理 / 组合驾驶舱”，不再设两个二级页：

- **待处理（一线队列）**：按业务域分组（收付 / 合同 / 物业 / 资产 / 质量），组内按金额 × 期限排序；**首版只点亮 5 类例外**：合同临期、终端租户逾期、未核销停留超阈值、现场受限、产权证数据质量；其余例外（合同到期、授权缺陷、即将释放、物业工单逾期/待验收、服务费来源不一致、资产台账陈旧、底价有效期到期）随对应切片交付后按域点亮，不一次性平铺 11 类；
- **招商人员“我的锁定”分区**：`LockSpace` 成功回执进入“我的锁定”清单；签约事务解除本方/空挂锁时，向锁定人发通知并生成“已转化为合同 XXX”回执；分区只读、无完成/关闭语义；
- **组合驾驶舱（决策层）**：默认落地视图为园区 × 模式组合损益、账龄结构、可租/即将释放结构、现场受限结构、**未来 12 月租金滚存卡**、趋势与下钻；盘活进度只在 Space/交还/限制/交付事实至少覆盖一个滚动 12 月窗口时点亮，否则灰显“数据积累中”；“即将释放”卡旁挂**释放收入潜力**（Σ 面积 × 当前底价 × 12，纯派生，与租金滚存同为经营应收读模型，标注“非会计口径”和 §9.3 口径水印，不碰财务总账/会计确认边界）；
- **盘活月报导出模板**：固定口径 = 滚存 + 盘活漏斗 + 释放计划 + 欠费账龄，经设置中心 › 数据工具导出，复用 §9.3 鉴权与水印；可排最后切片甚至 v1 后交付；
- 同一用户几乎不会同时高频使用两个视图；视图切换为页内 tab，不占菜单节点；
- 导出不再设独立菜单/专页：各列表页保留“导出”按钮；导出记录、下载重鉴权与口径水印统一进设置中心 › 数据工具，组合驾驶舱不内嵌“导出记录”抽屉。

待处理卡采用**一行一数一动作**：

- 每行：标题 + 关键数字 + 单一动作按钮；展开区只显示“发生了什么 + 下一动作”；口径卡四行（口径句/统计窗/数据水位/责任域）收进 ℹ️ 悬停/二级展开，默认不占展开区首屏；
- 空间供给预警采用 Space 级口径：可租与即将释放严格按 §2.1 分列；动作按钮分别为“查看可租 →”与“查看即将释放 →”，进入资产 › 空间；
- “待处理”只是查询入口，无领取、完成、关闭或转派语义；
- 点击金额进入组成它的账期义务，点击数量进入稳定预警/异常列表；
- 源事实修复后预警自动消失，页面不提供“标记完成”；
- 表头固定展示账期、统计口径版本、数据水位和范围来源；
- `all` 混合模式下，客户主体数/合同数显示“需选择产权方或运营方视角”，其他合法指标继续显示。

### 5.2 项目驾驶舱（资产域·项目总览）

项目是上下文容器，不是七八个互不相干的 Tab。首屏先回答当日运营三问，次行为本周动线，月度损益降为第三行：

```text
项目：城东园区   运营方：A公司   账期：2026-08           [口径/水位]
+----------------------------------------------------------------------+
| 运营三问条：临期合同 4 份 │ 欠费 32万/11 户 │ 可租 8 / 即将释放 4 |
+----------------------------------------------------------------------+
| 本周动线条：本周到期 n 份 │ 本周应收日 n 笔 │ 承诺还款日 n 个              |
+----------------------------------------------------------------------+
| 模式损益对照条：承租净差 +82.3万 │ 代理服务费 +11.7万 │ 合计 +94.0万   |
+----------------------------------------------------------------------+
| 统一合同/账单列表（模式=列+筛选，不按模式劈开页面）  │ 空间/产权证数字链  │
| 预警徽章跟随行级对象                                │ （点击下钻）       │
+----------------------------------------------------------------------+
```

- 模式是合同/协议的一个属性：承租转租、代理运营以列、筛选和损益对照行表达，不作为页面布局结构；
- 不再提供双模式泳道/空间分配泳道可视化，损益对照条足矣；
- 选择合同、资产/空间或账期后，右侧关系/证据检查器同步定位；
- 右栏速览块折叠为数字链，点击下钻；项目时间线移入子路由，不占 1440px 首屏；
- 重详情使用可分享子路由，不把全部信息塞入 Drawer；
- 空项目必须有明确空态和“导入资产/录入合同”动作，不允许近似空白。

### 5.3 资产与空间

**资产台账 / 项目总览**：

- 资产台账的菜单节点为“资产 › 台账”（页面标题保留“资产台账”，v3.10 裁死）；列表页必须有筛选面板（项目、资产形态/空间层级、当前产权、使用状态、审核状态、面积区间）、保存视图、列配置、批量提交/确认；
- 资产详情按四区组织：一句话状态条（资产名/面积/空间状态分布徽章组：可租 n · 在租 n · 受限 n · 待评估 n；底价与底价有效期）+ 空间与权属（权证+权利人一致性）+ 当前与历史合同/账单 + 变更与审计；不显示单一“资产当前状态”，也不显示资产级空置时长——空置时长只在叶子 Space 行内展示，资产级最多展示“最长空置叶子”为“空间名 + 定位链接”，不展示内部 `space_id`；欠费摘要为关联合同列表，不虚构资产级金额；
- 导入是台账页按钮，导入任务进设置中心“数据工具”，不作为菜单节点；
- 资产详情增加“产权沿革”只读区块，由有效期 `property_leasing_authority_revisions(source_type=ownership)` 重建；`Asset.owner_party_id` 只显示当前派生值，不建独立可写时间轴；

**空间（菜单节点：资产 › 空间）**：

- 独立 `Space` 拓扑树表达地块/建筑/楼层/房间/铺位/车位，Project 通过有效期 assignment 过滤，不作为树父节点；当前视图按查询时点解析 Project，历史物业/合同记录显示冻结 Project/operator；
- 空间工作面采用固定双轴版式契约（与 §5.2/§5.4/§5.5 同级施工图）：

```text
【顶部供给条：可租 23 / 即将释放 7 / 受限 4 / 待评估 2 ｜ 项目▾ 形态▾ 账龄▾ 底价区间▾】
--------------------------------------------------------------------------------
【左 30%：空间拓扑树（节点徽章 = 可租/即将释放/受限数）】  【右 70%：生命周期列表】
                                                       五维列 + 锁定 + 底价 + 预计释放日
                                                       行内动作：锁定 ｜ 报物业 ｜ 录入合同
```


- 右侧提供“可租 / 即将释放 / 全部空间”分段视图。可租严格执行 §2.1 六项合取；即将释放必须有临期合同和预计释放日。现场尚未评估时显示“待评估”，不得进入可租；
- 列表按五个正交维度展示合同承诺、实际占有、权属合规、行政可用、现场可运营，并单列招商锁定；禁止用一个彩色状态覆盖五维事实；
- 列表列：Space、形态、面积、当前 Project、底价、当前合同、预计释放日、占有、现场限制、可租；树节点聚合可租/即将释放/现场受限数量；
- **只读租控图视图**：楼 × 层色块矩阵，点格直达 Space 详情锚区；色块主维度 = 派生供给主状态（可租 / 在租 / 即将释放 / 受限 / 待评估），不是单一现场可运营四值；图内零编辑、零新事实表，纯派生；五维明细与现场可运营四值在 Space 详情查看；
- 行内上下文入口允许“录入合同”“锁定”“报告物业问题”“查看限制”；`LockSpace` 短锁在行内 Drawer 就近承载并复用 §5.10 唯一提交器，其余命令跳转到 §5.10 的规范执行工作区；
- Space 视图、工作台和物业交付视图必须走同一 `EffectivePartyScope` 和同一派生公式；任一处集合不一致即验收失败；
- 不做线索、带看、佣金、房间租控图编辑或合同下钻图编辑；只读租控图按上条交付。

**产权证**：证照原件、资产关系、权利人关系、有效期和三类数据质量 warning：证照信息不完整、权利人与资产当前产权方不一致、证载面积/用途与台账面积/实际用途偏差；warning 指向具体字段或关系，不使用笼统“产权有问题”。

**确权清单（跟进留痕，非任务）**：资产 › 产权证下提供 Space 级待确权清单与权证缺失/不一致汇总，动作 = 进入产权证或 Space 详情；允许追加联系记录、承诺补齐日期等跟进事实（沿用 §2.1 跟进事实先例），**不建立领取/责任人/期限/完成/转派语义**，源事实修复后条目自然消失。

### 5.4 合同

合同工作台以“授权校验 → 录入确认 → 生成账单 → 履约变更/续租/终止”为主线：

- 创建终端合同前显式选择 `direct_ownership` / `sublease` / `agency_leasing`，展示权威来源、覆盖 Space × 期间和签约主体；来源缺口、冲突或主体不匹配时不得定稿；
- 合同详情固定展示不可变授权快照和当前派生授权缺陷；原来源后续变化不改写签约时快照；
- 支持计费规则模板与“复制上一份同类合同”，复制只预填候选，仍逐字段确认，不绕过人工决定；
- 上传盖章扫描件及对应授权证据；
- 系统校验成交单价不低于 Asset/Space 已设 `floor_price`；低于未过期底价需 `lease:price_exception` + 原因 + 审计；
- **续租定价参考卡**：续租/商业变更工作区展示同业态在租单价分布、本空间历史单价、当前底价三线对比；数据源为 §8.3 空间级计费行，只读参考，不替代底价校验或人工确认；
- 原件、候选字段、Party、Space 和授权关系同屏逐字段确认；
- 账单预览全程常驻右栏，随字段/关系选择实时 dry-run 刷新；
- `RecordAgreement` 在一个事务内创建合同身份、授权快照、首版条款快照、证据链接、Space 覆盖、初始账单、审计和必要事件；
- 合同后续动作明确分为：`AgreementCorrection` 修数据录入错误；`AmendAgreement` 记录商业条件变化；续租按法律文书选择创建 `renewed_from_id` 后继 Agreement 或作为补充协议 amendment；
- 返回合同、账单和投影水位，不留下“合同已生效但授权快照或账单缺失”的半状态。

确认采用两步向导，原件常驻左 35%，账单预览常驻右栏，步骤间自由往返；中栏“待处理优先 + 已采用折叠”，不批量采纳：

```text
┌─────────────┬────────────────────────────────┬────────────────────┐
│ 原件 35%     │ ▸ 待处理 3（低置信2/冲突1）─展开  │ 账单预览（全程常驻）  │
│ 全程可缩放   │ ▸ 必填缺失 1 ─展开              │ 月│金额│到期日│数量   │
│             │ ▸ 已采用 12 项 ──折叠（可展开     │ 随任一字段/关系选择   │
│             │   逐项回看，非批量采纳）          │ 实时刷新（dry-run）  │
│             │ ▸ 步骤二·关系：Party/空间或资产选择器 │ 定稿前最后一眼对着钱  │
│             │ 未清零禁止提交（徽章常驻）         │                    │
└─────────────┴────────────────────────────────┴────────────────────┘
```

- 字段动作仅为采用候选、人工修正、显式留空、手工补齐；候选永不自动选中；Party/空间/Asset 候选先按实时范围过滤；
- 折叠仅改变视觉密度，不改变逐字段确认与来源快照纪律；
- 会话绑定操作者、目标、附件哈希、候选版本和 TTL；提交时重新鉴权和校验对象状态，陈旧候选返回 409；
- 解析失败或超时可以切换完全手工录入；不能在确认动作内创建 Party 或 Asset。

### 5.5 收付

收付工作台以账单和流水关系为中心。页内只有**一级 tab**，三个方向/状态平铺——**收款、付款、待核销**；租金、押金、服务费一律是**类型筛选**，不是 tab。每个 tab 渲染自己的一套口径数字条，切换 tab 即整组切换口径，类型筛选只改变当前列表与动作；不再嵌套账单内 tab，也不设“默认不展开”的次级 tab 组。低频危险动作收入行/多选 `⋯` 菜单，右栏改为选中行阅读区：


- 三个一级 tab 平铺渲染；代理结算岗默认直落“收款”tab 且类型筛选预置为“服务费”，收付登记岗默认直落“收款”tab，与 §5.9 完全一致；押金应收/登记/核销落“收款”tab 的类型=“押金”筛选态，不存在“默认不展开”的次级 tab 组；
- 口径数字条只渲染当前 tab 一套预定义文案与口径卡，页面标题、范围摘要随 tab 与类型筛选同步更新；不允许 tab 套 tab；
- 行内输入即时回显“本行核销后欠款”；合计条吸附表格底缘随表格滚动，不钉视口底部，输入、校验、提交同一视觉半径；
- 合计条实时校验“核销合计 ≤ 流水金额”，提交即 `RecordAndAllocatePayment`；幂等键由 §6.3 客户端生成；
- “更正流水”“作废流水”“替换分摊”“扩展/收窄锚点”只出现在行/多选 `⋯` 菜单；登记、追加核销不放该菜单；
- 服务费操作面唯一：收付 › 收款 tab 的“服务费”类型筛选态内含生成应收/来源核对/核销动作；不采用只读卡片 + 第二页面双轨；全站服务费操作入口命中数 = 1（§13.6 同步）；
- 主表同时展示账期月份、到期日、应收/应付、有效分摊、未收/未付、账龄分桶（30/60/90/180 天）和派生状态；跟进记录增加“承诺还款日”，派生“承诺到期未还”例外；
- 展开行展示流水、分摊、发生日期、凭证和更正链；待核销标签显示未分完的余额及可继续核销入口；
- 资金命令成功后直接显示强一致结果；工作台数据尚未追平时显示水位，不诱导重复登记；
- 不提供直接编辑 `paid_amount`、`payment_status` 或“逾期状态”；
- 逾期查询与实收登记是闭环，但页面文案不得伪装成催收系统。

收款采用“**先登记、后核销**”的日常路径。本工作域同时覆盖收款、付款和待核销；按 §3.4 推荐裁决词，一级入口为“收付”，域内对“欠费（应收未收）”和“欠付（应付未付）”分开呈现。

- `RecordPayment` 只登记流水，允许暂不核销；命令接受一个**非空范围锚点集合**（`payment_flow_scopes` 中的项目或往来方，按流水类型约束）。UI 默认选中一个锚点，但登记时允许操作者显式多选；每个锚点及其冻结目标都必须逐条鉴权，缺一则整体拒绝。不设 `payment:register_merged` 专项权限。`ExtendPaymentScope` 只用于登记后的事后扩展，`CorrectPaymentScope` 只用于无活动分摊锚点的收窄/撤销。**活动锚点不变量**：active 流水活动锚点数恒 ≥ 1；`CorrectPaymentScope` 拒绝移除最后活动锚点，误登无分摊流水走 `VoidPayment`。
- `payment_flow_root_id` 跨 `CorrectPayment` 后继保持稳定；活动分摊集合仍是当前有效分摊的全量快照。对 `deposit` 流水，快照每次切换都按同一 flow root × 押金应收计算新旧有效押金分摊差额，并追加 signed `deposit_holding_adjustment`，不得把分摊集合版本 ID 当作押金持有身份；
- 每笔流水必填 `funds_beneficiary`（`operator`/`property_owner`），由流水类型 × 三种授权模式矩阵推导、只读展示由用户确认；`direct_ownership` 与 `agency_leasing` 的终端租金行强制标签“产权方到账”（代理模式另标“代登记”），`sublease` 终端租金归运营方，且同一流水只允许一个资金归属方；
- `RecordAndAllocatePayment` 登记并核销，**核销合计 ≤ 流水金额**即可，差额自动显示为“待核销余额”；后续追加核销使用 `AllocateOpenPayment`，不得复用“替换”命令。
- 活动分摊集合是**当前有效分摊的全量快照**，不是增量日志；待核销余额只按活动集合计算，历史集合只用于审计链和重建，绝不参与当前余额。
- 范围锚点是授权和可见性依据，**不是金额容器**。流水的整笔金额和待核销余额只向“其**非空**活动锚点集合全部落在当前用户有效范围内”的用户展示和开放核销；只命中部分锚点的用户仅能看到自己范围内已授权的分摊明细，不能看到流水总额、待核销余额、无权锚点或无权目标，也不能从明细反推总额。
- 待核销清单按上述规则过滤；单锚点流水按锚点授权展示；合并收款流水只有具备全部锚点权限的用户能在待核销清单中看到整笔余额。
- 部分付款、预付款、多付款都先成为真实流水事实，再通过后续追加分摊核销到对应账期，不做假分摊；
- 未核销流水不是“无主流水”：非空范围锚点集合在登记时确定；后续核销到集合外目标必须先执行 `ExtendPaymentScope`，该命令重新鉴权新旧全部锚点和目标并写入审计；误登或已无分摊的锚点通过 `CorrectPaymentScope` 收窄/撤销，但不得移除最后活动锚点；无分摊的误登流水整体作废走 `VoidPayment`；
- 待核销余额是派生值，不可手填；后续可以继续核销、作废/更正，或按“作废 + 重新登记”的显式流程拆分为多笔流水；本期不提供一键拆流水命令；未核销停留时长进入工作台“待处理”提示，但不生成任务；
- 流水的对方 Party 名称按对方自身数据范围鉴权：查看者对对方无范围时显示“范围外往来方”，不返回名称、编码或稳定 ID；
- 现存无目标流水迁移后进入待核销工作清单，不再一律进拒绝桶；迁移时必须按对方/既有分摊/来源记录回填锚点，无法确定锚点的进入迁移拒绝桶。

### 5.6 往来方

- 档案统一入口，导航末位，不称“业务入口”；按来源角色筛选：产权方、上游出租方、委托方、终端承租方、运营方、资金归属方、实际付款/收款方、物业服务方；不得再用“承租户/业主方/运营方/供应商”四个扁平标签覆盖不同法律与现金关系；详情亦可从合同/流水详情 2 跳内到达；
- 每个角色均由具体来源事实派生，并在详情中显示来源对象与有效期；不允许手工勾选业务角色；

| 来源角色 | 权威来源 | 有效期/快照规则 |
|---|---|---|
| 产权方 | `property_leasing_authority_revisions` 中 `source_type=ownership` 的 `rights_holder_party_id` | 按修订有效期派生；历史合同显示授权快照，不追随当前产权方 |
| 上游出租方 | 上游 Agreement 的 `lessor_party_id` + `agreement_authority_links` | 按上游 Agreement 与授权 link 有效期；不得从当前 Asset owner 猜测 |
| 委托方 | 委托协议的 `principal_party_id` + `agreement_authority_links` | 按委托协议有效期；终止后只保留历史角色 |
| 终端承租方 | 终端 Agreement 的 `lessee_party_id` | 按 Agreement 法律期间；续租后继独立形成新来源 |
| 运营方 | `project_operator_assignments.operator_party_id`；历史合同使用 `ContractGroup.operator_party_id` 快照 | 当前角色按 `as_of` 派生，历史事实不随 Project 运营方变化回写 |
| 资金归属方 | `PaymentFlow.funds_beneficiary` 按签约时冻结的授权快照解析：`operator` 取 `ContractGroup.operator_party_id`，`property_owner` 在 `direct_ownership` 取权利主体、在 `agency_leasing` 取委托方 | 每笔流水冻结唯一 Party；不得用当前 owner 投影或实际收付方替代 |
| 实际付款/收款方 | `PaymentFlow.counterparty_party_id` + 流水方向 | 按有效流水事实派生；作废流水退出当前角色但保留历史 |
| 物业服务方 | 外包工单的 `PropertyWorkOrder.provider_party_id` | 外包时必填并冻结；内部处理时为空，不因 assignee 所属组织猜测供应商 |

- 单位详情聚合合同/授权来源、Space/Asset、账单、现金、欠费、物业工单和跟进历史，但每块继续按对象范围独立鉴权；
- **欠费全景（按往来方聚合）**：往来方详情提供跨合同总欠费、账龄结构、跟进时间线与函件证据的只读汇总；不建催缴工单，不改变账单/流水权威事实，金额逐项下钻到账单与流水，并沿用全通道范围鉴权；
- 历史签约数按合同 ID 去重，`all` 范围合法，不受分析单视角约束。

### 5.7 组织与权限（设置中心）

围绕“为什么可见/不可见”和“变更影响谁”设计；本域位于设置中心。具备任一管理能力的用户，设置中心渲染为导航末位一级入口；其他用户保留头像菜单入口。

- 用户范围诊断展示显式绑定、组织继承来源、下一时间边界和结构化问题；
- Organization 代表 Party、组织移动、用户调动、用户绑定和 Party 启停全部先预览后提交；
- 提交携带范围变更预览 token（与已删除的 alert/return_to token 无关）、原因、幂等键并重新鉴权；
- 批量敏感变更全成全败；
- 字典/系统设置并入数据工具，操作日志/数据策略包并入审计日志或组织与权限；本域不混排机器配置；
- 无范围或配置失效显示阻断式错误和稳定原因码，不显示“暂无数据”；
- `perm_admin` 维持“不可读取业务数据”的强隔离：可查看用户范围诊断的结构化原因码、脱敏标签和命中规则摘要，不返回业务对象名称、编码、金额、附件或可关联的稳定 ID；范围诊断中的节点 ID 仅向具备对应范围管理权限者返回。
- 只有业务负责人确认存在持续、可审计的日常排障岗位，且上述脱敏诊断不足以完成其职责时，才启动对象级权限诊断设计；触发后必须重新补齐岗位责任、最小响应字段、禁止扫描/搜索/导出/聚合、逐次原因与审计、禁止与 `perm_admin` 或业务角色组合，以及 SSOT/API/RBAC/反向测试。触发前不预留能力码、端点或前端入口。

### 5.8 物业

物业是第六业务入口，负责“现场事实与处置”，不是资产详情中的只读卡片，也不是完整物业 ERP/IWMS。

- **页内工作面**：单页只设“现场任务 / 巡查计划 / 现场档案”三个 tab；详情一律走子路由，不在页内重建第三层菜单；


- **问题工单**：用户可从 Space、巡查发现、交还检查或独立报告创建问题；主状态为 `open → assigned → in_progress → pending_acceptance → closed`，另有 `cancelled`；`RejectPropertyWork` 从 `pending_acceptance` 追加驳回事实并回到 `in_progress` 新处理轮次，`ReopenPropertyWork` 只允许 `closed → reopened → in_progress`，原处理和 `PropertyWorkAcceptance` 验收事实不覆盖；`closed` 是工单生命周期状态，accepted 是验收事实结果，不混作状态词；外包工单必须显式冻结 `provider_party_id`，内部处理为空；
- **巡查**：B4.3 拥有通用/周期巡查计划和执行事实；计划必须经创建、启用、暂停、退役；系统按计划 × 周期 × Space 幂等生成 `InspectionRun`，现场人员开始/取消/提交，提交即完成例行执行，不生成 `InspectionReview`；错误只追加 `InspectionSupplement`，不覆盖原执行；
- **交还/交付检查**：B4.4 拥有 `possession_return` / `handover` 两类专用 `InspectionRun` 及其复核、占有交还和交付事实，不复用 B4.3 周期计划。先经 `CreateDeliveryInspectionRun` 冻结 Agreement、Space、purpose、agreement version 和模板版本，再开始/提交/复核；`RecordSpacePossessionReturn`/`RecordSpaceHandover` 必须引用最新 accepted `InspectionReview`，且 review 的 Space、Agreement、purpose 和版本与命令一致；rejected review 只能通过原子创建的 successor run 重新检查，不能原地翻转；
- **交付与限制**：展示一个 Space 的多来源活动限制、实际交还和新租户交付。`restriction_type × blocking_level` 决定是否阻断营销展示、签约、续租、入住交付或继续占用；不同来源限制可并存，只能按来源身份逐条解除；
- **责任与证据**：每张工单必须有责任人、期限和处理记录；提交验收必须带结果与证据；验收/驳回记录验收人、时间、理由和版本；取消与重开必须有理由；
- **移动 Web**：B4.5 提供 390px 宽度可用的现场列表、拍照上传、处理提交和验收界面；离线同步、原生 App 和外部门户不在本期；
- **指标**：只派生工单逾期数、待验收数、重开率、平均闭环时长、巡查按期完成率、现场受限 Space 数；不得以关闭预警或手填 KPI 改写事实。

### 5.9 岗位默认入口与导航可见性

六个一级入口（五个任务型业务入口 + 往来方档案库）按权限动态裁剪；设置中心仅管理类岗位可见：

| 岗位 | 每日首要判断 | 默认落地页 | 默认账期 |

| 决策层 / 高管 | 整体盘面、盘活成效和趋势如何 | 工作台（组合驾驶舱视图） | 当前账期 |
| 运营负责人 | 哪些项目、模式和账期需要干预 | 工作台（待处理视图） | 当前账期 |

| 合同运营岗 | 授权是否覆盖、条款能否形成正确账单 | 合同（合同台账；录入经顶栏“＋录入合同”进入） | 无默认，按待处理线索进入 |

- 代理结算岗直落收付“收款”tab 且类型筛选预置“服务费”；该筛选态必须同屏可见，不设折叠或次级 tab 组；

- 没有权限的一级入口直接隐藏，不出现“点了才 403”；
- 用户被深链带入无权对象时，页面显示稳定原因码和联系入口，不泄露对象是否存在；
- 业务用户登录后 30 秒内应能从默认页判断“今天要做什么”；
- 物业权限按 Space、创建时冻结 Project/operator、工单责任和验收职责共同解析；当前 Space 列表用查询时 assignment，历史物业记录用冻结上下文，不能用当前 Project 反向改写历史可见性。

## 6. 前端目标架构

### 6.1 目录和边界

```text
frontend/src/
  app/                 # 路由、会话、范围阻断、全局错误边界
  features/
    workbench/         # 工作台：单页角色化（待处理/组合驾驶舱）；导出记录在设置中心
    assets/            # 资产：空间、台账（页面标题“资产台账”）、项目总览、产权证
    contracts/         # 合同：授权、合同台账、录入、纠错、商业变更、续租
    payments/          # 收付：收款 / 付款 / 待核销；类型=租金/押金/服务费
    parties/           # 往来方档案与来源角色
    property/          # 物业：问题工单、巡查、现场限制、交还与交付
    access/            # 设置中心：Organization、User、范围预览提交、数据工具、审计日志
  shared/
    api/                # transport、错误和命令回执协议
    navigation/         # 类型化上下文 URL
    ui/                 # 设计系统原语，不含业务规则
```

feature 不能直接导入其他 feature 的内部 store、service 或页面组件。跨域只通过公开 query/command client、稳定 ID 和共享 UI 原语连接。

### 6.2 数据状态

- React Query 管理服务器读模型和强读结果；
- React Hook Form 管理命令输入和预览确认；
- URL 管理可分享上下文与列表状态；
- Auth Context 管理会话；
- Zustand 只保存无服务器真相的 UI 偏好；
- 不用 `useState + useEffect` 拼装服务器数据；
- 不在前端计算金额、权限、逾期、服务费或历史归属。

### 6.3 命令体验

统一命令客户端负责：

- 为每次新的业务意图生成并持久化 `idempotency_key`；页面刷新且载荷未变化时复用原键，载荷变化必须生成新键，避免把“改后重试”误判为同键异载荷；
- 传递 `expected_version`、preview token 和原因；
- 区分字段校验、业务冲突、预览陈旧、范围失效和投影延迟；
- 网络超时后用原幂等键查询命令回执查询端点，不盲目创建新请求；
- 成功页展示对象 ID、版本、生成/跳过数量、风险引用和投影状态；若请求携带 `alert` 例外键来源，提供“返回来源”主按钮并消费白名单 `return_to`；
- 命令完成前禁止重复主按钮，但不以按钮禁用替代服务端幂等。

### 6.4 查询策略

每个工作台消费一个带口径的页面查询；必要的次级详情按用户选择延迟加载。响应统一包含：

```text
items/data
scope_summary
metrics_version
as_of
is_stale
suppressed_fields[]
```

`is_stale` 超过预算时页面明确标记并提供刷新，不把旧预警当成新任务。权限撤销永远在服务端查询入口实时生效，不能等待缓存刷新。

## 7. 后端目标架构

### 7.1 形态选择：模块化单体 + 命令内核，而不是先做全量领域重塑

| 形态 | 结论 |
|---|---|
| 现有横向分层继续全局使用 | 拒绝：资金与范围变更路径自行 commit/rollback，无法统一幂等和审计 |
| 命令式模块化单体 + 全量 CQRS | 拒绝：v1 方案过度，未证明需要为每个页面建投影 |
| **命令式模块化单体 + 按需读模型** | **采用**：高后果写入走命令内核；台账/详情默认规范写模型强读；只有工作台按实测需要建读模型 |
| 全量事件溯源 | 拒绝：审计收益不足以承担事件版本、重放和双时态复杂度 |
| 微服务 | 当前拒绝：合同、账期、分摊和服务费高频强一致；未来只按量化需要拆 OCR/通知/搜索 |
| GraphQL | 拒绝：单一管理后台查询稳定，不能用字段图掩盖授权和投影设计 |
| 薄 BFF | 可用：只做页面字段裁剪和聚合，不计算金额、权限或状态 |

### 7.2 现状资产处置：保留、增量硬化，不全面重命名

### 7.3 命令内核与事务所有权

命令内核只覆盖高后果命令；低后果字典和简单主数据可保留 CRUD，但受 §7.6 负面清单约束。

统一命令执行器负责：

1. 解析不可变 `AuthorizationContext`；
2. 查找幂等回执；命中时只进入回放分支，不执行副作用；
3. 回放分支按回执保存的目标引用和安全分类，用当前角色、deny、范围版本重新鉴权；通过后返回当前允许暴露的首次结果，撤权或目标已不可见则返回 403/404，不泄露旧载荷；
4. 未命中回执时开启数据库事务；
5. 让命令处理器按统一顺序锁资源；
6. 事务内重新校验最新范围版本和对象状态；
7. 执行业务修改；
8. 追加审计和必要业务事件；
9. 写入命令回执；
10. 提交；
11. 返回强一致命令结果。

幂等唯一键为 `(actor_id, command_type, idempotency_key)`：

- 同键同规范化摘要不重复执行；在当前权限重新授权回执目标后，返回首次结果；
- 同键异载荷返回 409 `IDEMPOTENCY_KEY_REUSED`；
- 规范化摘要使用固定字段顺序的 canonical JSON + SHA-256，算法、字段集合和版本写入命令契约；数值必须按 Decimal 字符串规范化，数组按业务语义排序；
- 命令回执提供专用查询端点（按 actor + command_type + idempotency_key），查询永不执行副作用；查询端点必须执行与回放分支相同的当前角色/deny/范围版本重鉴权和结果裁剪，撤权或目标不可见返回 403/404；
- 并发同键插入触发唯一约束冲突时，按“命中已有回执”进入回放分支处理，不得返回 500 或重复执行；
- 回执持久化目标引用、安全分类和可裁剪结果，撤权后重放返回 403/404；
- 业务修改、回执和审计同事务；
- 失败回滚后允许原键安全重试。

领域模块可以 `flush`，不得自行 `commit/rollback`。OCR、消息发送、搜索索引和对象存储复制不得发生在持锁事务内。

### 7.4 出租授权深模块

Agreement Authority 是聚焦的深模块，不建泛化 `Right` 聚合。其公共服务只有 `ResolveAgreementAuthority`、`ValidateAgreementAuthority`、`FreezeAgreementAuthoritySnapshot` 和缺陷继续经营处置 `ResolveAgreementAuthorityDefect`；缺陷终止不另建服务，统一进入 `TerminateAgreement`：

- 输入为目标 Agreement、签约主体、Space 集合、合同期间和授权模式；输出为唯一来源选择、覆盖证明和可冻结快照，不直接提交事务；
- `direct_ownership` 读取有效产权/经营权修订；`sublease` 读取上游 Agreement 的承租权、可转租许可与覆盖；`agency_leasing` 读取委托协议、代理许可与覆盖；
- 校验 Space × 期间无缺口、权限动作允许、来源不冲突、签约主体与来源身份一致；
- `RecordAgreement` 在同一事务、锁定来源修订后重新校验并冻结快照；
- 来源终止、到期或法律范围修正派生 defect；替代来源或法律确认继续经营由 `ResolveAgreementAuthorityDefect` 追加决定和证据，原签约快照不可修改；选择终止时必须进入 `TerminateAgreement`，由该事务终止合同、追加 `resolution_type=terminated`、保存终止回执并关闭 defect；
- 未处置 defect 阻断续租、增加 Space 和新承租户交付，但不自动终止现合同或改写既有账单。

| `deposit:offset` / `deposit:return` / `deposit:reverse` | 押金抵扣/退还/录入错误反转 | `admin`、`system_admin`、收付登记岗/财务负责人岗位角色 | 仅能操作本人范围内的押金流水与冻结目标；抵扣必须先于退还；反转必须有未真实发生证据，真实已支付退还不得反转 |
| `project:change_operator` | 项目运营方有效期变更 | `admin`、`system_admin`、运营负责人岗位角色 | 新旧两侧范围均须授权 |
| `lease:price_exception` | 低于底价签约例外 | `admin`、`system_admin`、运营负责人/合同负责人岗位角色 | 必须填写原因并审计 |
| `ledger_voucher:read` | 收付凭证下载 | 按现行 RBAC 契约 | 下载独立于查看，另记审计 |

角色清单以最终 RBAC SSOT 为准，但能力码、授予边界和禁止组合关系按本表写入。对象级权限诊断不在本表预留；只有 §5.7 的岗位证据触发条件成立后，才能通过后续设计与 SSOT 修订新增。

所有命令必须在设计和测试中声明锁顺序、错误码、审计字段、事件和可重试性；仅把 CRUD 放进 `commands/` 目录不算命令架构。

### 7.6 低后果 CRUD 负面清单

允许轻量 CRUD 的对象：字典、枚举、模板、低后果备注、UI 偏好，以及尚未接入命令内核的简单主数据维护。

以下写路径不得以 CRUD/PATCH 暴露：

- 直接写 `paid_amount`、`payment_status`、逾期或风险关闭、空间状态/可租集合；
- 原地覆盖项目运营方、Space—Project assignment、合同授权快照/缺陷处置、合同定稿条款/商业变更/续租关系、服务费来源、流水分摊/范围锚点、资产产权方与底价；
- 招商锁定、行政/合规维度、实际占有、交还、交付、现场限制、巡查执行、工单处理/验收/重开走通用 PATCH；
- 合同终止、待核销流水追加分摊、扩展/收窄锚点、资产产权方变更走通用 PATCH；正常 Agreement 不提供任何作废命令或 PATCH；
- 替换共享证据而不对全部受影响合同逐条授权；
- 合同根身份（模式、项目、产权方、运营方）通过通用更正改变；
- 解析候选自动绑定或创建 Party/空间/Asset；
- 审计、回执、范围版本和派生状态的人工写入。

### 7.7 锁顺序与数据库最后防线

建议资源类型顺序：

```text
ScopeConfig -> Organization/UserPartyBinding/Role
-> Project/Asset/Space/SpaceTopology/AssetSpaceAssignment/SpaceProjectAssignment
-> PropertyLeasingAuthorityRevision/AgreementAuthoritySnapshot/ContractGroup/Contract
-> InspectionPlan/InspectionRun/PropertyWorkOrder/SpaceOperationalRestriction/SpacePossession/SpaceHandover
-> OperationalPaymentFlow/PaymentFlowScope
-> ContractLedgerEntry/ServiceFeeLedger/DepositReceivable
-> PaymentAllocationSet/ObligationWriteOff/SpaceLock/ContractSpaceLink
```

同类型按稳定 ID 升序锁定。长编辑对象使用 `expected_version` 乐观锁；分摊、更正、服务费来源修订、范围锚点扩展和范围提交使用行锁。

有效期唯一性和单活动版本必须落到数据库：

- 项目运营方同一时点一条：`project_operator_assignments` 对 Project + 有效期使用 PostgreSQL GiST 排斥约束；
- `spaces` 的父子关系不得成环；类型化父子、多父、非根孤儿、重复稳定叶子和面积守恒由命令校验，递归触发器/延迟约束或等价数据库最后防线阻断非法拓扑；仅叶子 Space 可进入合同覆盖与可租集合；
- `asset_space_assignments` 的 `primary_accounting` 关系按叶子 Space + 有效期使用 GiST 排斥约束；`space_project_assignments` 按 Space + 有效期使用 GiST 排斥约束；两者均采用半开区间并禁止空/倒置区间；
- `property_leasing_authority_revisions` 是产权/经营权唯一可写事实且只追加；每个 `source_root_id` 修订保存完整权利快照并唯一指向直接 `supersedes_id`，禁止自环/跨链环。权威 `as_of` 解析在链上选择最新已生效且未到期修订；预登记未来修订的替换/取消必须追加 superseding 完整快照，不能更新/删除旧修订或只 patch 部分 Space。覆盖叶子 Space 与有效期、允许动作和证据版本不可空；`ChangeAssetOwner`/`RecordOperatingAuthorityRevision` 以预期链头锁 source root，并发分叉只允许一个成功；来源变化在同一事务重算受影响 defect。`Asset.owner_party_id/projected_from_revision_id/next_transition_at` 仅为展示投影：立即生效时刷新，未来边界由唯一耐久到期任务幂等刷新，周期修复扫描补偿漏跑；任何权限、签约、沿革和显示回退都从权威修订读取，漂移告警且不影响权威结果；
- `agreement_authority_snapshots` 对目标 Agreement 的每个 Space × 合同期间必须无缺口；同一目标、Space、期间、选定来源唯一；快照与其 `source_fact_revision_id` 不可更新；
- `contract_space_links` 在行内保存 `agreement_revision_id`、`coverage_lane=terminal_occupancy|authority_source` 与 `enforcement_state=enforced|historical|closed`；每个 Agreement revision 必须提交覆盖其法律期间与全部叶子 Space 的**完整、相邻可拼合、内部无重叠分段集合**，不存在未声明空洞。纠错/amendment 在一个可延迟约束事务中把旧 revision 全部行切为 `historical`，再插入相同 lane 的新 revision 完整分段集合；生效日前仍承诺的原范围和生效日后修订范围分别成为新 revision 的 `enforced` 分段。终止同样历史化旧 revision，并以终止生效点切分：`[covered_from, termination_at)` 保持 `enforced`（自然在边界后失效），`[termination_at, original_covered_to)` 为 `closed`；终止点等于起止边界时不插入空区间。历史行永不删除。只有终端租约写 `terminal_occupancy`，上游租约/委托协议写 `authority_source`；lane 从 Agreement 类型确定且不可由客户端任意传入。数据库使用可延迟的部分排斥约束 `EXCLUDE USING gist (space_id WITH =, daterange(covered_from, covered_to, '[)') WITH &&) WHERE (coverage_lane = 'terminal_occupancy' AND enforcement_state = 'enforced')`，仅阻断终端占用重叠，允许授权来源与终端租约合法重叠；谓词不依赖 join Agreement 状态，普通部分唯一索引不能替代区间不重叠约束；
- 续租链每份 Agreement 至多一个直接前序和一个直接后继，`renewed_from_id` 唯一、非自指且全链无环；前后继 Space 期间不得重叠，允许存在业务签字的空档但不自动填补；并发为同一前序续租只有一个成功；
- `space_locks` 同一 Space 同一时点一条活动锁定；`expected_party_id` 可空、到期日非空；锁定不能与他方合同交付并存；
- `space_operational_restrictions` 按 `(source_type, source_id, restriction_type)` 保证活动来源身份唯一；同一 Space 允许多个不同来源限制，解除只关闭指定来源；
- 周期巡查 `inspection_runs` 按 `(plan_id, scheduled_period, space_id)` 唯一，重复生成返回同一批结果；例行执行提交即完成，不创建 review。交还/交付专用检查按 `(purpose, agreement_id, space_id, agreement_version)` 建唯一 chain root；初始 `CreateDeliveryInspectionRun` 只创建该 root 与首个 run，重复调用返回当前链。每个 run 的 `predecessor_run_id` 最多一个 successor，两路后继均通过同一**内部后继创建内核**（校验 predecessor 状态、原子插入 successor 并共享 `predecessor_run_id` 唯一约束；过期路径另冻结新模板版本，rejected 路径记录拒绝原因）创建：rejected review 由 `ReviewInspectionRun` 在同一复核事务调用；accepted review 过政策有效期后，由 `ReinspectDeliveryRun` 在确认尚无交还/交付事实的事务中调用。两路竞争同一 predecessor 时仅一个成功；不新增面向用户的“合并 successor”命令，也不把 rejected review 与 successor 拆成两个事务；提交后正文/附件只追加 supplement；
- `inspection_reviews` 仅允许引用 `purpose in (possession_return, handover)` 的 submitted run，每次只追加；accepted/rejected 终态不可原地翻转。`RecordSpacePossessionReturn`/`RecordSpaceHandover` 以外键和命令校验强制引用用途、Agreement、Space、agreement_version 一致且仍在政策有效期内的最新 accepted review；过期 accepted review 只能经 `ReinspectDeliveryRun` 进入新检查，不能重开或翻转旧 review；
- critical finding 提交采用单事务原子门：同一 `SubmitInspectionRun` 同时写入 finding、证据链接、`PropertyWorkOrder`、以 `(source_type='inspection_finding', source_id=finding_id, restriction_type)` 唯一的活动限制、审计和回执；任一步故障全部回滚，重试返回同一结果；
- `property_work_orders`、`inspection_runs`、`space_possession_returns`、`space_handover_records` 均用 `expected_version` 保护迁移；处理轮次和验收只追加；同一合同—Space 的活动占有/交付事实不得矛盾；外包工单 `provider_party_id` 必填，内部工单必须为空；
- 每笔活动流水同一时点一个活动分摊集合：`flow_id` 上的部分唯一索引 `WHERE active`；活动集合是当前有效分摊的**全量快照**，历史集合不参与余额计算；更正链共享唯一 `payment_flow_root_id`；
- 每条账期义务同一时点一个活动版本：`contract_ledger_entry_revisions` 的 `entry_id + active` 部分唯一约束；历史版本只读；
- 流水范围锚点以 `(flow_id, anchor_type, anchor_id)` 为稳定键，追加/作废版本，不原地改历史；同一锚点键同一时点只有一个活动版本；active 流水至少保留一个活动锚点，`CorrectPaymentScope`/迁移路径不得产生零锚点 active 流水（命令校验 + 迁移校验，数据库侧以触发器或等价延迟约束兜底，失败测试见 §13.3-4）；
- `service_fee_receivables.source_identity=(agency_agreement_root_id, service_fee_settlement_cycle_root_id)` 全局唯一；settlement-cycle 日期边界、来源义务集合/账期桶、产权方和活动分摊属于 `calculation_fingerprint`，变化只形成 mismatch/新修订，不新建 receivable root。`service_fee_receivable_revisions` 按 root + `active` 部分唯一，历史修订只读；生成/核对先锁 receivable root、settlement-cycle root 与来源义务；不同幂等键并发生成同一稳定身份只有一个成功，核对并发只有一个活动切换成功；
- `deposit_holding_lots` 对 `(payment_flow_root_id, deposit_receivable_id)` 唯一且身份不可变；每次 deposit 活动分摊集合切换或 `CorrectPayment` 后继生效时，以 `(lot_id, source_allocation_set_id)` 唯一追加 signed `deposit_holding_adjustment`，金额等于该 root 对该押金应收的新旧有效分摊差额，禁止把全量快照重复累计。`recognized_amount=SUM(adjustments)` 必须 ≥0；`deposit_dispositions` 只追加，`offset` 必须引用欠费义务，`return` 必须引用同事务创建且 Party/币种一致的 `deposit_return` 流水。被 disposition 引用的流水禁止通用 `VoidPayment`/`CorrectPayment`。录入错误只允许 `ReverseDepositDisposition` 追加对原 disposition 唯一的 reversal：offset 原子恢复义务；return 仅在证据证明外部资金未真实付出时原子失效专用退还流水；真实已支付的退还不允许用数据更正伪造反转。有效 disposition 按原额减唯一 reversal 计算，命令按 flow root → lot → dispositions 固定锁序逐分校验 `SUM(active offset + active return) <= recognized_amount`，数据库以延迟约束触发器或等价最后防线阻断冲减穿透；已有 holding adjustment 的 deposit 流水不可 `VoidPayment`，更正不得改变 Party/币种/资金归属方或把 recognized amount 降到有效 dispositions 以下；
- `settlement_history_status` 只允许由支付/分摊/迁移流程写入，禁止普通编辑 UPDATE；`uncertain` 账期禁止自动重建；
- `funds_beneficiary` 枚举与流水类型 × 模式矩阵由 check 和命令校验双重兜底；同一流水只允许一个资金归属方；
- `floor_price` 可空且非负（check 只兜底 `>= 0`）、金额方向、枚举、编号、外键和外部单号条件唯一由 check/unique/FK 兜底，不能只依赖应用校验；“取消底价”只能通过 `SetAssetFloorPrice` 置空表达，不接受 0；`floor_price_valid_until`/评估依据随底价一起受命令管理；
- `space_locks`、`space_administrative_availability_revisions`、`space_compliance_status_revisions` 和 `obligation_write_offs` 由对应命令维护，普通 UPDATE 禁止；行政与合规修订各自只追加且同一 Space 同一时点最多一个活动版本；活动锁定同一 Space 唯一；同一账期活动核销事实唯一，且 MVP 要求 `write_off_amount` 等于核销时点当前未核销余额（命令校验 + 事务内对账，禁止部分核销与撤销）；
- `floor_price_basis_type` 枚举仅允许 `appraisal_report`/`filing_record`/`other`；设置正数底价时 `floor_price_basis_type` 与 `floor_price_basis_ref` 必填，置空底价时二者随之为空；`floor_price_valid_until` 不早于命令生效日。

累计金额字段的防御：`paid_amount`/`payment_status` 仅保留为派生缓存，除命令内核在分摊/流水事务内同步重算外，任何业务代码不得 UPDATE；每条分摊变更在同一事务内重算并对账，迁移期保留逐分对账任务，任何不一致进入告警并阻断后续资金命令。

### 7.8 选择性 CQRS：按需，不预设

性能预算在 `PRODUCT.md` 既有 P95 承诺（列表/详情 ≤800ms，统计和搜索 ≤2s）基础上，新增本方案承诺：工作台/分析/搜索 P95 ≤ 2s、P99 ≤ 5s，列表/详情 P95 ≤ 800ms。只有真实数据量下突破预算且索引/查询优化不足时，才为该工作面建立专用读模型；本方案不把候选名称、数量或预建投影列为第一版约束。

- 台账、合同详情、流水详情、物业工单详情默认使用规范写模型强读；
- 每个投影必须声明：来源事件、主键和去重、范围字段、口径版本、水位、最大延迟、重建命令、差异对账和失败队列；
- 命令返回强一致结果；工作台查询超时返回稳定的 `PROJECTION_NOT_READY` 和当前水位，不暗示命令失败；
- 读模型可从规范写模型重建，不反向成为资金或权限事实源；
- 不引入签名的 `projection_token`，除非出现必须跨服务传递读取授权的真实需求；
- outbox/inbox 只在需要把领域事件异步投递给通知、搜索或读模型消费者时引入；没有消费者就不建基础设施。

- `ServiceFeeReceivableGenerated`、`ServiceFeeSourceMismatchDetected`、`ServiceFeeSourceReconciled`；
- `AssetOwnerChanged`、`SpaceTopologyChanged`、`AssetSpaceAssigned`、`SpaceProjectAssigned`、`ProjectOperatorChanged`、`ScopeConfigurationChanged`、`ExtractionConfirmed`；
- `SpaceLocked`、`SpaceAdministrativeAvailabilityChanged`、`SpaceComplianceStatusRecorded`、`SpaceOperationalRestricted`、`SpaceOperationalRestrictionReleased`、`SpacePossessionReturned`、`SpaceHandedOver`；
- `InspectionPlanCreated`、`InspectionPlanActivated`、`InspectionPlanPaused`、`InspectionPlanRetired`、`InspectionRunGenerated`、`DeliveryInspectionRunCreated`、`DeliveryInspectionReinspectionCreated`、`InspectionRunStarted`、`InspectionRunCancelled`、`InspectionRunSubmitted`、`DeliveryInspectionReviewed`、`DeliveryInspectionRejectedSuccessorCreated`、`InspectionSupplementAppended`；
- `PropertyIssueReported`、`PropertyWorkAssigned`、`PropertyWorkStarted`、`PropertyWorkSubmitted`、`PropertyWorkAccepted`、`PropertyWorkRejected`、`PropertyWorkReopened`、`PropertyWorkCancelled`；
- `ObligationWrittenOff`；`DepositHoldingLotCreated`/`DepositHoldingAdjusted`/`DepositOffsetApplied`/`DepositReturned`/`DepositDispositionReversed`。

事件是集成事实，不是系统状态的唯一来源。若引入 outbox，按聚合版本有序发布；消费者以 `(consumer_name, event_id)` 建 inbox；持续失败进入可观测死信，重放必须幂等且可对账。

业务审计与 domain event 分离。审计记录：稳定 actor、命令与幂等 ID、原因、目标版本、前后摘要、权限和范围来源摘要、附件 SHA-256、trace 和结果。审计只追加，可做哈希链和定期外部锚定；在未具备可信时间戳、签名和独立保全前，产品只能宣称“可追溯”和“可检测篡改”，不得宣称法律不可抵赖。

文件规则：

- 合同盖章件、跨项目共享协议扫描件和收付凭证使用不可变 blob + 证据版本链，链接表达业务归属；产权证附件沿用轻量规则并做最小加固（替换/重登时旧件转历史保留、只读不可删，不建完整证据版本链，v3.9）；资产附件维持现行通用轻量规则；
- 通用 `Attachment` 生命周期按 `owner_type` 分列：`contract`/`payment_flow`/`obligation_write_off` 为证据链（坏账核销依据与授权证据不可变、替换只追加），`property_certificate`/`asset` 为轻量附件；domain-model §4.22 不得再用一条通用规则覆盖合同与核销证据；
- 任何元数据、预览、下载或审计请求都必须携带拥有对象上下文，并通过该对象上已授权的证据链接解析；不提供裸文档 ID 读取入口；
- 内容去重只在存储层内部进行；上传或链接响应不得暴露是否命中无权 blob、全局链接数、兄弟对象数量或不可见文档 ID；
- 不可变证据优先直接引用已校验暂存 blob，只变更数据库分类，不搬文件；
- 若必须复制晋升，使用 outbox 重试，晋升成功前不清理暂存；
- 数据库失败留下的未关联 blob 由 TTL 清理；任何存在业务链接的不可变证据 blob 永不作为孤儿清理；
- 预览跟随对象读取权限，下载有独立外流权限和审计；响应不返回存储路径。

## 8. 端到端工作流

### 8.1 建立合同、冻结授权并生成账单

1. 选择目标叶子 Space、合同期间和授权模式 `direct_ownership` / `sublease` / `agency_leasing`；
2. Agreement Authority 解析候选来源：产权/经营权事实修订、上游合同或委托协议；
3. 显式选择唯一来源，系统校验目标 Space × 期间无缺口、许可动作允许、来源不冲突、签约 Party 与来源身份一致；
4. 校验所选 Space 无活动终端租约覆盖，活动招商锁按本方/空挂自动解除、他方拒绝 `SPACE_LOCKED_BY_OTHER`；
5. 上传盖章扫描件和授权证据，原件、候选字段、Party、Space 与授权关系同屏逐项确认；
6. 校验成交单价与未过期底价，例外走 `lease:price_exception`；
7. 预览不可变授权快照、条款快照、计费规则和账单；
8. 执行 `RecordAgreement`，事务内按固定顺序锁来源修订、Space/锁定、合同编号和义务目标，重新鉴权并复验授权；
9. 同一事务创建合同、授权快照、首版条款、证据链接、合同—Space 覆盖、初始账单、审计和回执；
10. 返回合同、账单和查询水位，不留下“合同已生效但授权或账单缺失”的半状态。

### 8.2 逐字段扫描确认

- 字段动作仅为采用候选、人工修正、显式留空、手工补齐；
- 低置信、与现值冲突和必填字段必须逐项处理；
- Party/空间/Asset 候选先按实时范围过滤，只返回稳定编码和必要识别信息；
- 候选永不自动选中；
- 会话绑定操作者、目标、附件哈希、候选版本和 TTL；
- 提交时重新鉴权和校验对象状态，陈旧候选返回 409；
- 会话消费失败恢复依赖命令回执，不重复建档。

### 8.3 生成和预览账单

- 每个账期必须恰好命中一条计费规则；
- 更正必须携带 `correction_effective_month`；生效月之前（含已冻结历史）的账单不得被普通更正重建，生效月及之后按 §8.6 规则处理；
- 显示账单月份、服务期间、到期日、金额、方向和冻结归属来源；
- 条款重叠、无法解释的计费空档、缺金额、跨服务费比例区间，或任一授权模式未唯一命中其权威来源时阻断；
- 免租期、递增率、装修期、押付方式四项为存量租约标准条款，必须在 §13.1 语义门确认可表达；缺任何一项，结构化导入对应行不得激活；
- 多资产合同金额保持合同级，不做系统臆造的资产分摊；**合同明示按空间列计费行的，条款快照支持录入"空间级计费行"（v3.9 补）——只录合同载明值，用于空间级租金水平分析与定价参考，不参与核销约束、不虚构未载明金额**；
- 用户确认的是条款和结果预览，不是手工逐条造账单。

### 8.4 登记并分摊收付流水

1. 选择流水类型、发生日期、金额、实际收付方、外部来源单号（如有）、备注和可选凭证；系统按流水类型 × 模式推导 `funds_beneficiary` 并只读展示，用户确认；只登记不核销且项目为混合模式时，必须显式选择模式以完成推导；
2. 选择非空范围锚点集合（项目或往来方，按流水类型约束）；UI 默认单锚点，但登记时允许显式多选。服务端逐条鉴权全部锚点，缺一则整体拒绝；登记后新增范围才使用 `ExtendPaymentScope`；
3. 选择要核销的账单；可按租户、合同、项目筛选；每个冻结目标必须落在登记锚点集合内并逐条鉴权；
4. 系统实时计算“本次核销合计 ≤ 流水金额”，差额显示为“待核销余额”；也允许先只登记流水、后核销；
5. 只登记不核销时，提交 `RecordPayment`；登记并核销提交 `RecordAndAllocatePayment`；后续追加核销提交 `AllocateOpenPayment`，均携带幂等键；
6. 服务端按 §5.5 的锚点集合规则鉴权流水可见性，对每个目标按冻结归属逐条鉴权，按稳定 ID 顺序锁定全部目标，事务内创建流水、锚点版本和首个活动分摊集合；
7. 返回各账期新实收/实付、流水待核销余额和派生状态；
8. 前端先展示命令结果，再等待工作台数据追平。

流水类型 × 允许锚点矩阵：

| 流水类型 | 允许的项目锚点 | 允许的往来方锚点 |
|---|---|---|
| `terminal_rent_receipt` | 项目 | 终端租户 Party |
| `upstream_cost_payment` | 项目 | 上游出租方/成本对手方 Party |
| `service_fee_receipt` | 项目 | 产权方 Party |
| `deposit` | 项目 | 承租户 Party |
| `deposit_return` | 项目 | 承租户 Party |

矩阵落入数据库 check 与 API 校验；未命中即 422，不进入命令执行。同一锚点内多合同/多账单核销不属于合并收款；跨范围登记使用同一非空锚点集合并逐条鉴权，登记后的范围变化才使用 `ExtendPaymentScope`/`CorrectPaymentScope`，无专项权限仪式。

资金归属方矩阵（`funds_beneficiary`）：

| 流水类型 | 授权模式 | `funds_beneficiary` | 冻结 Party 解析 |
|---|---|---|---|
| `terminal_rent_receipt` | 产权方直租 `direct_ownership` | `property_owner` | 当前合同授权快照中的产权/经营权 `rights_holder_party_id` |
| `terminal_rent_receipt` | 承租转租 `sublease` | `operator` | `ContractGroup.operator_party_id` |
| `terminal_rent_receipt` | 委托运营 `agency_leasing` | `property_owner` | 当前合同授权快照中的委托方 `principal_party_id`（运营方代登记） |
| `upstream_cost_payment` | `sublease` | `operator` | `ContractGroup.operator_party_id` |
| `service_fee_receipt` | `agency_leasing` | `operator` | `ContractGroup.operator_party_id` |
| `deposit` | 三种模式 | `operator` | `ContractGroup.operator_party_id`；押金由运营方持有，不随终端租金归属变化 |
| `deposit_return` | 三种模式 | `operator` | `ContractGroup.operator_party_id`，并必须与原 holding lot 冻结的资金归属 Party 一致 |

未列出的流水类型 × 授权模式组合非法，不能用“任意模式”绕过来源语义。同一笔流水只允许一个 `funds_beneficiary`；跨资金归属方的目标不得合并到同一流水，且任何解析都不得读取当前 `Asset.owner_party_id` 投影。

约束：

- `terminal_rent_receipt` 只能核销终端租户租金义务，`upstream_cost_payment` 只能核销上游成本义务，`service_fee_receipt` 只能核销服务费应收；`deposit` 只能核销押金应收；`deposit_return` 为押金退还流出，不参与普通核销；金额方向必须与流水一致；
- 核销合计**大于**流水金额时失败且零写入；小于等于流水金额是合法状态；
- 跨租户/合同/项目合并收款时，操作者必须对每个锚点和每个冻结目标都有权限，缺一个整体拒绝，并逐条列出无权目标而不是模糊失败；普通用户不得以部分锚点权限查看整笔余额或核销其他锚点目标；
- 只登记流水必须带范围锚点；active 流水活动锚点数恒 ≥ 1；待核销清单按 §5.5 的锚点集合规则过滤；把未核销流水核销到锚点外目标必须先执行 `ExtendPaymentScope`，重新鉴权新旧全部锚点和目标并审计；
- 流水具备银行流水号、支付平台交易号或外部系统单号时，按来源系统和来源引用建立条件唯一约束；缺少权威外部引用时，服务端按对方、金额、日期和类型返回疑似重复提示，只有具备重复登记权限并填写原因才可继续，且必须审计；
- 方向不一致、资金归属方不一致、重复幂等键异载荷或并发冲突必须明确失败，不做最后写覆盖。

### 8.5 流水作废和更正

- 作废保留原流水和原分摊集合，令其退出有效汇总；只允许作废从未核销、没有 holding adjustment 且未被 deposit disposition 引用的普通流水（误录纠正），不允许借作废清理已核销流水或押金持有/处置审计链；
- 被 `deposit_disposition(return)` 引用的专用 `deposit_return` 流水稳定拒绝通用 `VoidPayment`/`CorrectPayment`；已真实发生的外部退还只能作为真实资金事实保留，不能伪装成数据更正。只有证据证明外部资金从未付出时，才可从原 disposition 详情执行 `ReverseDepositDisposition`；
- 本期不提供一键“拆流水”命令；需要拆分为多笔时，按“作废原流水（如从未核销/持有）或更正后重新登记多笔”的显式流程处理，每笔独立携带原因和幂等键；
- 更正在同一事务中终结原流水、创建共享同一 `payment_flow_root_id` 的唯一后继流水及首个活动分摊集合（未核销流水更正允许分摊集合为空）；新流水允许保留待核销余额；deposit 更正同时按 root × 押金应收计算差额并追加 holding adjustment，已有 disposition 后不得改变 Party/币种/资金归属方，也不得把 recognized holding 降穿有效 disposition；
- `AllocateOpenPayment` 对未核销余额追加新分摊，生成新活动分摊集合并保留旧集合；`ReplacePaymentAllocations` 用于替换既有分摊，不删除或覆盖旧明细，写入 `supersedes_id`、原因、操作者和版本；
- `CorrectPaymentScope` 仅允许在目标锚点不存在活动分摊、且移除后活动锚点数仍 ≥ 1 时收窄/撤销该锚点；移除最后活动锚点整体拒绝，误登且无分摊的流水应走 `VoidPayment`；目标锚点仍有活动分摊时必须先调整分摊；
- 原凭证仍属于原流水，新流水凭证另行上传；
- 原因必填，前后金额、日期、目标和受影响账期在提交前预览；
- 两次并发更正或分摊替换只有一次成功，第二次返回明确冲突。

### 8.6 合同纠错、商业变更与续租

**`AgreementCorrection`：只修数据录入错误。** 从当前合同创建纠错草稿，并排展示法律原件、旧值、新值和义务影响。普通字段纠错追加版本，不改变商业事实；仅 `settlement_history_status=never_settled` 的未来账单可由 `FinalizeAgreementCorrection` 替换重建，`has_settlement_history/uncertain` 必须保留并走显式 `CorrectObligation` 版本链。期间或 Space 确属原始法律文书录入错误时，只有“受保护法律原件纠错”路径可处理：追加 Agreement correction、重新解析并冻结授权快照、原子地把旧 revision 覆盖全转 `historical`，并为新 revision 插入覆盖全部叶子 Space × 法律期间的完整 `enforced` 分段集合，再重跑底价/限制/义务影响；任一授权、全集闭合或排斥冲突则整体拒绝，不允许强行覆盖。普通 `RecordAgreement` 定稿后已经生成覆盖与账单，不存在 Agreement 作废命令；结构化导入暂存误录只拒绝导入行，不创建 Agreement。若差异来自事后协商而非原始录入错误，必须走 amendment/renewal。

**`AmendAgreement`：记录商业条件变化。** 补充协议、租金调整、期间调整、增减 Space 等经营变化必须上传法律文书，填写生效日，重新验证授权、锁定、底价、Space 覆盖、现场限制和受影响义务；旧 revision 覆盖全转 `historical`，新 revision 保存生效日前原承诺段与生效日后修订段组成的完整权威覆盖集合，未来义务按 amendment 版本确定性生成。增加 Space 或延长期间时必须重新解析授权，未处置 `agreement_authority_defect` 时拒绝。

**续租/展期按法律文书裁决。** 新主合同只执行 `RenewAgreement`：创建唯一直接 `renewed_from_id` 后继 Agreement，并重新校验当前授权、锁定、Space 覆盖、现场限制和定价；法律文书明确是原合同补充协议时，在提交前路由到 `AmendAgreement`，`RenewAgreement` 本身不兼做 amendment。每份 Agreement 至多一个直接前序和一个直接后继，链禁止自环和任意环；前后继合同期间不得重叠。允许法律文书明确形成真实空档，系统按实际日期保存并在空档期不生成义务、不宣称连续占用；不得自动补齐日期。并发为同一前序创建后继时只有一个成功。

共同重验矩阵：`AmendAgreement`、`RenewAgreement` 和受保护法律原件纠错均在同一事务按顺序重验授权来源、未处置 defect、招商锁、合同—Space 区间排斥约束、底价、`restriction_type × blocking_level`、未来义务和当前有效分摊下限；旧条款、授权快照、覆盖版本、账单版本、原因、证据和操作者完整保留。模式、签约法律主体或授权模式根本变化通常通过终止旧 Agreement 并新签表达，不得伪装为纠错。

### 8.7 服务费生成与来源核对

- 按租金账期、项目、产权方、委托协议聚合代理直租有效实收（`currency=CNY` 常量）；
- `source_identity` 只由 `agency_agreement_root_id + service_fee_settlement_cycle_root_id` 组成；settlement cycle 是委托协议结算计划中的稳定根，日期边界可版本化但 root 不变。来源义务集合、账期桶、产权方和活动分摊都不是 root identity；
- `calculation_fingerprint` 由 settlement-cycle 当前日期边界、不可变来源义务 root 集合、活动分摊集合及版本/金额、当前产权方来源修订、委托协议修订、比例和舍入规则生成，用于检测所有来源计算变化；
- 首次生成按稳定 settlement-cycle root 固化 `source_identity`、计算指纹、比例、基数和冻结归属；同一 root 不得插入第二个应收身份；来源租金账期、来源义务/活动分摊或产权方变化只改变 `calculation_fingerprint` 并进入 mismatch/新修订，不新建 root；
- 指纹变化只派生 mismatch，不静默覆盖；
- `ReconcileServiceFeeSource` 要求唯一来源、原因、期望来源身份/指纹和锁；它追加修订并切换活动修订，不改写旧修订；
- 新修订应收低于已登记服务费有效分摊时拒绝，先更正服务费流水；
- 服务费未收不称“逾期”，不生成逾期通知；
- **版本链骨架**：`service_fee_receivable_revisions`/`ReconcileServiceFeeSource` 与 `contract_ledger_entry_revisions`/`CorrectObligation` 复用追加版本、活动切换和单活动版本唯一约束骨架；两者保留独立命令、来源身份、计算指纹、审计和错误码，不合并领域语义。

### 8.8 Space 经营归属调整和共享证据

Space 的 Project 归属只通过 `Preview/CommitSpaceProjectAssignment` 调整：

- 锁定目标 Space、当前/未来 `space_project_assignments`、相关 Asset 映射和受影响的活动/未来合同、开放工单、限制、巡查与交付；
- 使用半开有效期版本终止旧 assignment 并追加新 assignment，不原地改写历史；区间重叠由 GiST 排斥约束拒绝；
- 预览列出新旧 Project/operator 可见性、跨生效边界对象和授权来源影响；存在活动对象时要求同时拥有新旧范围、填写原因并显式确认，但不回写其冻结归属；
- `Asset` 不保存 `project_id` 或等价当前 Project 关系；Project 侧 Asset/Space 索引只从 `asset_space_assignments → space_project_assignments` 按 `as_of` 派生；
- 当前索引和未来 assignment 从业务生效日变化，旧合同、账期、物业记录和交付事实继续使用各自冻结的 Project/operator。

跨项目委托协议共享的是不可变扫描件内容，不是跨项目合同或事项：

- 每个项目有独立协议记录和账期，合同号按 `(project_id, contract_number)` 复合唯一，同号兄弟记录不联动更正；
- 替换共享证据必须逐条授权全部受影响合同且全成全败；
- 无全量权限时可显式解除本合同链接并上传新文档；
- 响应不得暴露无权兄弟合同、项目数量或文件元数据。

### 8.9 项目运营方变更

- 项目运营方变更只通过 `Preview/CommitProjectOperatorChange`，创建新的 `project_operator_assignments` 有效期版本，不原地覆盖历史；
- 变更前预览列出受影响项目、生效合同和未来账期；既有 `ContractGroup.operator_party_id`、历史台账冻结归属不回写；
- 跨生效边界的活动合同默认阻断原地变更，必须先终止旧合同/协议并在新运营方下建立新合同/协议；允许无活动合同的未来时段切换；
- 既有合同的可见性按合同固化的 `operator_party_id` 解析，而不是按项目当前运营方实时 join；原运营方用户仍能看到并处理旧合同，新运营方用户自生效日起看到新合同；
- 新合同的 `operator_party_id` 取自签约时点项目运营方的有效版本，签约后不随项目运营方再变更而改写。

四类对象在运营方切换日前后的可见性固定如下，`PartyScopeResolver` 必须按对象类型执行，不得统一按项目当前运营方过滤：

| 对象 | 切换日之前 | 切换日及之后 | 数据依据 |
|---|---|---|---|
| Project | 原运营方可见；新运营方不可见 | 新运营方可见；原运营方仅可进入“历史项目”只读视图 | `project_operator_assignments` 有效期 |
| Asset/Space | 产权方按 `property_leasing_authority_revisions(as_of)` 查看覆盖资产；运营方只可见经 `asset_space_assignments → space_project_assignments → project_operator_assignments(as_of)` 命中其范围的 Space 片段，不得读取跨 Project 的完整 Asset 聚合 | 切换后新运营方只见生效日起命中其 Project 的 Space 片段；原运营方仅保留其历史 `as_of` 视图 | 三段有效期关系 + 权威产权修订；`Asset.owner_party_id` 展示投影不参与解析，不存在 Asset 当前 Project 字段 |
| Contract | 始终按合同创建时固化的 `operator_party_id` 授权，不随切换改变 | 同左；跨边界活动合同必须先终止再新签 | `ContractGroup.operator_party_id` |
| Ledger | 始终按冻结的 `attributed_operator_party_id` 授权，不随切换改变 | 同左 | 台账冻结归属 |

- 原运营方用户在切换后保留“合同”“收付”中旧合同的直接工作入口，以及只读历史项目工作区；不允许继续创建归属新运营方的新合同或新账期；
- 历史项目/Space 片段视图按查询 `as_of` 匹配 `space_project_assignments` 与 `project_operator_assignments` 鉴权，查询范围不得越过用户当时的有效主体绑定边界；
- `PartyScopeResolver` 对 Project 及 Project 侧 Asset/Space 查询增加 `as_of` 解析，并在 Space 粒度先裁剪再聚合；一个 Asset 跨多个 Project 时，数量、面积、金额、关系和附件不得从无权 Space 片段泄漏。Contract/Ledger 继续使用对象自带冻结归属，不叠加当前 Project 运营方过滤。

### 8.10 合同终止、实际交还、整改与重新可租

- `TerminateAgreement` 追加终止 revision、结束法律承诺并停止未来账单；同一事务把旧 revision 覆盖全转 `historical`，再按终止生效点为新 revision 写入完整分段：终止前原范围为 `enforced`、终止起至原结束为 `closed`，不生成空区间；已有结算历史、授权快照、证据和旧覆盖保留；
- 正常 Agreement 没有 void 命令。结构化导入先持久化 `AgreementImportRow(staged)`；`ValidateAgreementImportRow` 在人工绑定和盖章件/关键条款核对通过后追加证据并转 `validated`，不创建 Agreement。状态只允许 `staged → validated → activated` 或 `staged/validated → rejected`；`RejectAgreementImportRow` 只追加拒绝原因/证据和审计，不创建 Agreement；`activated` 由逐份 `RecordAgreement(import_row_id)` 同事务切换且唯一引用已创建 Agreement，并与携带 `import_row_id` 的 `AgreementRecorded` 及 `AgreementImportRowActivated` 同事务发出，激活失败保持 validated 可重试，已 activated/rejected 不可回退；
- 合同终止不代表承租人已经交还，Space 的实际占有维度保持不变；
- 现场完成交还检查后执行 `RecordSpacePossessionReturn`；若发现损坏或清理事项，创建物业问题/工单并按来源施加 `SpaceOperationalRestriction`；
- 工单处理完成后必须经过 `AcceptPropertyWork`，再逐来源执行 `ReleaseSpaceOperationalRestriction`；物业验收不能关闭行政停用或权属合规冻结；
- 只有 §2.1 可租公式全部为真，Space 才由查询派生为可租；没有任何“释放为空置可租”的写命令；
- 新租户进入前执行 I2：授权复核、现场检查、阻断限制校验和 `RecordSpaceHandover`。


### 8.11 招商锁定、行政/合规标记与现场限制

- `LockSpace` 只对可租或明确即将释放 Space 开放；短期锁定必填结构化原因、意向 Party（可空并保留备注名）和到期日。超标准期限、续锁或高价值 Space 才要求附件或升级权限；短锁 UI 采用 Space 行内 Drawer，复用唯一提交器，不复制表单/校验/提交逻辑；
- 锁定到期只终结锁事实，不写 Space 状态；签约时本方/空挂锁自动解除，他方锁返回 `SPACE_LOCKED_BY_OTHER`；签约事务解除本方/空挂锁时，同事务生成业务回执“已转化为合同 XXX”，提交后向锁定人发通知，该回执进入工作台“我的锁定”清单；
- `SetSpaceAdministrativeAvailability` 只追加行政启用/停用修订，不得改写权属合规、合同占有或现场限制；每次变更携带业务生效日和原因；
- `RecordSpaceComplianceStatus` 只追加正常/待确权/合规冻结修订，必须引用权属或合规来源并按政策携带证据，不得改写行政或现场事实；
- `RestrictSpaceOperation` 专门维护现场可运营维度。多个来源限制可并存，营销展示、签约、续租、入住交付、继续占用的阻断级别由政策矩阵决定；
- `ReleaseSpaceOperationalRestriction` 只解除指定来源，必须验证来源问题已接受或有单独批准；不得因另一个工单关闭而清除全部限制；
- 工作台、资产 Space 视图和物业交付视图从同一五维事实与限制集合派生，不保存“可租/在租/临期”可编辑状态。

### 8.12 物业巡查、交还/交付检查与工单闭环

**B4.3 通用巡查流程**：`CreateInspectionPlan → ActivateInspectionPlan → GenerateInspectionRuns`。生成命令以计划 + 周期 + Space 为幂等身份；重复调度不得产生第二个执行。现场人员 `StartInspectionRun` 后可记录多个 finding，`SubmitInspectionRun` 校验检查项与证据后即完成例行执行，不创建 `InspectionReview`。提交后正文/证据不可覆盖，错误或补证只经 `AppendInspectionSupplement` 追加。计划可暂停、恢复或退役，不回收历史执行；“恢复”复用 `ActivateInspectionPlan`（paused→active），不新增 Resume 命令。

**B4.4 交还/交付检查流程**：`CreateDeliveryInspectionRun` 幂等创建 `possession_return` 或 `handover` 专用 chain root 与首个执行，冻结 Agreement、Space、purpose、agreement version、模板版本与 Project/operator，不依赖周期计划。执行开始/提交后必须由具备独立复核能力的人员 `ReviewInspectionRun`；accepted/rejected review 都只追加且不可翻转。rejected review 由 `ReviewInspectionRun` 在同一事务调用内部后继创建内核，创建引用原执行的唯一 successor；accepted review 若在交还/交付前超过政策有效期，必须显式 `ReinspectDeliveryRun`，该命令验证尚无交还/交付事实后调用同一内部后继创建内核，为原 run 创建唯一 successor 并冻结新模板版本。两路 successor 共享 predecessor 唯一约束与冻结/插入逻辑，不合并为一条面向用户命令；新执行重新开始现场检查；对象或 Agreement version 已变化则原 chain 失效，重新以新 identity 创建 chain。补充证据仍只追加。`RecordSpacePossessionReturn`/`RecordSpaceHandover` 只能引用当前 Agreement × Space × purpose × version 的最新、未过期 accepted review；rejected、过期或对象/版本不匹配时返回稳定错误且零写入。

**critical finding 原子联动**：政策矩阵认定 finding 为 critical 时，`SubmitInspectionRun` 在一个事务内写 finding、不可变证据链接、`PropertyWorkOrder`、以该 finding 为唯一来源的 `SpaceOperationalRestriction`、审计和命令回执；限制级别由政策矩阵确定，不由前端传任意值。工单/限制唯一冲突进入幂等回放，不得留下“有 finding 无工单”或“有工单无限制”的半状态。非 critical finding 可独立存在，由授权用户后续显式 `ReportPropertyIssue`/`RestrictSpaceOperation`。

**问题工单流程**：`ReportPropertyIssue → AssignPropertyWork → StartPropertyWork → SubmitPropertyWork → AcceptPropertyWork/RejectPropertyWork`。驳回后进入新处理轮次；已接受事项因复发或验收错误可 `ReopenPropertyWork`，原接受记录保留。外包工单在报告/分派时冻结 `provider_party_id`，内部工单为空。每次迁移携带 `expected_version`、幂等键、原因/证据（按动作要求），事务内重鉴权并按固定顺序锁定 Space、来源巡查/交还、工单、限制。

**限制联动**：除 critical finding 原子门外，问题或巡查发现达到其他政策阈值时显式执行 `RestrictSpaceOperation`，而不是由工单状态隐式改 Space。工单接受后也不自动清除所有限制；只能针对该来源执行 `ReleaseSpaceOperationalRestriction`。取消工单不等于问题不存在，取消必须记录独立原因和后续处置。

### 8.13 I1/I2 跨域集成

- **I1 退租到重新可租**：合同域 `TerminateAgreement` → B4.4 创建/提交 `possession_return` 检查 → accepted review → `RecordSpacePossessionReturn` → 必要时问题/工单/现场限制 → 验收 → 逐来源解除限制 → Space 查询重新计算可租；I1 只编排前置和回执，不复制检查、交还、工单或限制事实。
- **I2 新合同到入住交付**：合同授权重验 → Space 当前合同/锁定/行政/合规/现场前置校验 → B4.4 创建/提交 `handover` 检查 → accepted review → `RecordSpaceHandover`；存在未处置授权缺陷、rejected/过期 review 或阻断入住限制时拒绝。I2 不复制授权快照、检查或交付事实。
- B4.4 独占交还/交付专用检查、复核和事实命令；B4.3 只拥有通用/周期巡查；I1/I2 只拥有跨域编排。事务边界仍在单库命令内核，跨步骤长流程以稳定回执和状态查询恢复，不引入 Saga。

### 8.14 坏账核销

- `WriteOffObligation` 以账单义务为对象，**MVP 仅支持全额核销**：`write_off_amount` 必须等于该账单当前未核销余额；不可逆、不提供撤销，同一账单活动核销唯一（部分唯一索引兜底）；要求原因、核销依据、授权证据和审计，同一事务写入 `obligation_write_offs` 并更新派生口径；
- 核销后该账单退出欠费/逾期/账龄口径，进入“坏账”单列统计；原账单、流水、分摊和历史链均不删除；已核销账单拒绝后续追加核销；
- `WriteOffObligation` 必须拒绝仍有有效押金余额可抵扣的账单；先执行 `DepositOffset`，系统证据证明余额为零后才允许核销；
- 坏账核销不是“催缴工单”，不生成任务、不改变合同，只做账务处置。

### 8.15 押金最小工作流

1. 合同定稿时按押金条款生成押金应收（不虚构金额，来源为合同条款）；
2. 首次把 `deposit` 流水分摊到押金应收时，为 `payment_flow_root_id × deposit_receivable_id` 创建唯一 `deposit_holding_lot`；同一事务按该 root 的新旧有效押金分摊差额追加首笔正数 `deposit_holding_adjustment`；
3. 后续 `AllocateOpenPayment`、`ReplacePaymentAllocations` 或 `CorrectPayment` 切换全量分摊快照时，不新建第二个 lot，也不累计整份快照；只对相同 lot 追加 signed adjustment。冲减后 `recognized_amount` 不得低于 0 或已有有效 dispositions；已有 holding adjustment 的流水不能 `VoidPayment`；
4. 退租结算按欠费账单优先级执行 `DepositOffset`：锁定可用 holding lot 后追加 `deposit_disposition(offset)` 并引用目标欠费义务；不创建原押金流水的新分摊集合，也不改写其历史分摊；
5. 抵扣后仍有余额时执行 `DepositReturn`：同一事务登记 `deposit_return` 流水并追加引用该流水的 `deposit_disposition(return)`；退还不减少原押金流水的待核销余额；
6. 每个 lot 的 `recognized_amount = SUM(signed adjustments)`，有效 offset + return 合计不得超过该金额；部分抵扣、分次退还、更正和并发处置都按 flow root → lot → dispositions 固定锁序逐分校验，并由数据库最后防线守恒；`total_deposit` 和可用押金只从 recognized holding 减 dispositions 派生；
7. `WriteOffObligation` 在仍有有效押金余额可抵扣时拒绝；必须先完成 `DepositOffset` 并由系统事实证明可抵扣余额为零；
8. `ReverseDepositDisposition` 只纠正有证据证明未真实发生的录入错误：按 flow root → lot → 原 disposition → 义务/专用退还流水固定顺序加锁，要求原因、不可变证据、原 disposition 未有 reversal，且只允许全额反转；offset 反转在同一事务追加唯一 reversal 并恢复原义务未核销余额，return 反转仅在证明外部资金未付出时追加唯一 reversal 并令该 disposition 专用 `deposit_return` 流水退出有效汇总；原 disposition、流水和证据均保留。真实已支付退还、部分反转、第二次反转、通用 `VoidPayment`/`CorrectPayment` 或任一步失败都必须零写入；
9. 命令复用统一幂等、授权、锁序、审计和回执内核；`deposit_return` 复用现金流水事实，押金持有与处置不复用支付分摊表达。

## 9. 权限与防泄漏

### 9.1 请求上下文

每个请求只生成一个不可变 `AuthorizationContext`：

- actor 与有效角色；
- allow/deny 结果；
- EffectivePartyScope 及来源；
- owner/manager Party 集合；
- `scope_version`、`next_transition_at` 与项目/资产解析使用的 `as_of`；
- 当前请求能力和 trace。

写命令在事务内锁定资源后按最新范围版本再校验。范围缓存不得越过 `next_transition_at`，且数据库范围版本必须使撤权在下一请求立即生效。

角色分配也必须是显式命令并按角色类别实施授予边界：`perm_admin` 可以配置权限、策略和范围，但只有 `admin/system_admin` 可以授予业务角色；任何用户不得利用角色管理给自己或他人授予超出自身授予边界的角色。命令端必须执行这一不变量并记录审计，不能依赖前端隐藏按钮。

对象级权限诊断只保留 §5.7 的岗位证据触发器。触发前，`perm_admin` 诊断视图仅返回脱敏标签、稳定原因码和命中规则摘要；系统不提供可读取业务对象名称/编码的诊断能力、端点或入口。

### 9.2 全通道矩阵

必须用 owner-only、manager-only、双视角、无范围、失效范围、`perm_admin`、admin 七类用户覆盖：

- 列表项目和 total count；
- 详情与关系侧栏；
- 工作台（待处理/组合驾驶舱）、资产项目总览、Space 可租/即将释放、合同授权快照/缺陷、物业问题工单/巡查/交付与限制；
- 搜索与自动补全；
- 通知正文和跳转；
- 导出任务创建、完成和下载；
- 待核销流水清单、范围锚点、整笔金额/余额和后续核销；
- 流水对方 Party 名称、全局搜索和自动补全；
- 命令审计时间线、锚点变更、授权解析/缺陷处置、Space assignment/锁定/行政合规、物业工单/巡查/限制/交还/交付、坏账、押金和附件审计元数据；
- 命令回执查询与回放；
- 附件元数据、预览、下载和审计；
- 异步任务和失败修复入口。

未授权的不只是行，还包括数量、名称、稳定 ID、聚合金额、兄弟项目数量和附件存在性。补充规则：

- 物业当前列表按查询时点 `space_project_assignments` 授权；历史工单、巡查、限制、交还和交付按创建时冻结 Project/operator 及 Space 范围授权，不得因当前 assignment 改写历史可见性；
- 物业列表/count、搜索、自动补全、通知、附件、导出、审计、命令回执和移动 Web 必须全部执行相同对象范围裁剪；无权 Space 的存在性、工单数、图片和责任人均不得泄漏；
- 合同授权来源和 defect 只向同时有合同与来源对象必要范围的用户展示；无权来源以稳定原因码抑制，不返回来源 ID、Party 或兄弟 Agreement；
- 流水对方 Party 名称按对方自身数据范围鉴权；范围外统一显示“范围外往来方”，不得返回名称、编码、稳定 ID 或数量；
- 命令审计时间线按查看者对目标对象和流水活动锚点集合的权限裁剪；部分锚点用户不得读到含其他锚点或金额的审计摘要；
- 命令回执查询端点与回放执行相同重鉴权和裁剪；撤权后返回 403/404。

### 9.3 导出与异步任务

创建导出时鉴权，文件交付和每次下载时再次鉴权；用户中途撤权后不能继续下载旧任务结果。导出记录 `as_of`、口径版本、账期范围、经营视角、范围摘要和数据水位，保证结果可解释。导出记录、下载重鉴权与口径水印统一在设置中心 › 数据工具，组合驾驶舱不内嵌“导出记录”抽屉；各业务列表保留“导出”按钮，下载时重新鉴权。

## 10. 批量语义矩阵

| 类型 | 语义 |
|---|---|
| 用户/组织主体范围批量变更 | 单事务全成全败 |
| 一笔流水分摊多个账期 | 单事务全成全败 |
| 共享证据链接替换 | 对全部受影响合同逐条授权后全成全败 |
| Space 经营归属变更 | 单 Space assignment 影响预览后原子提交，不做列表逐项成功 |
| 资产/Party 导入 | 持久 job + 行级结果，可只重试失败项 |
| 资产批量提交/确认 | 逐项状态结果，幂等成功 |
| 附件多选上传 | 文件级结果，不自动解析 |
| 合同/产权证解析确认 | 单件逐字段，不提供批量 |
| 存量合同结构化导入 | 持久化 `AgreementImportRow(staged)`：行级校验 + 盖章扫描件绑定 + 每行人工绑定/核对关键字段；`ValidateAgreementImportRow` 追加核对证据并转 `validated`，抽样人工核对；状态 `staged → validated → activated` 或 `staged/validated → rejected`，拒绝走 `RejectAgreementImportRow`，激活逐份调用 `RecordAgreement(import_row_id)`，字段来源 `manual` |
| 合同纠错、商业变更、续租、授权缺陷处置 | 单合同命令；预览影响后原子提交，不提供批量 |
| 招商锁定、行政/合规标记、实际交还与入住交付 | 单 Space/合同命令，不提供批量 |
| 物业问题报告/分派 | 批量导入可持久 job + 行级结果；正式分派仍逐工单版本化 |
| 物业工单处理、提交、验收、驳回、重开、取消 | 单工单命令，不提供“批量完成/批量验收” |
| 巡查执行生成 | 按计划 × 周期幂等批量生成，全批次记录回执；重复生成不增行 |
| 通用/周期巡查现场提交 | 单次执行命令；finding 可多条但提交原子化，提交即完成且不进入 review |
| 交还/交付检查复核与重检 | 单 delivery run/chain 命令；review 只追加，rejected/过期 accepted 各按唯一 successor 约束推进，不提供批量复核 |
| Space 现场限制 | 可对同一来源批量提出预览，但提交按来源 × Space 逐条结果；不得“一键清除全部限制” |
| 坏账核销 | 单账期命令 + 证据 + 授权，不提供批量；MVP 仅全额 |
| 押金抵扣/退还 | 单押金流水 × 多欠费账单可单事务分摊；退还单流水，不提供批量 |

禁止用一条“所有批量逐项成功”或“所有批量全部回滚”覆盖不同业务后果。

存量合同结构化导入不是批量解析确认：每行先成为可审计的 `AgreementImportRow`，不允许自动绑定 Party/空间/Asset，不允许绕过盖章扫描件，不允许未经人工核对直接激活；拒绝只终结导入行，正常 Agreement 不存在 void 入口；抽样比例与失败行处理进入 §13.5 验收。

## 11. 实施路线：先硬化、再切片，不做全局大切换

### 11.1 原则

- 不长期兼容旧 CRUD、旧页面或旧路由；
- 不建立两个可写事实源；
- 不在应用层同步双写旧表和新表；0→1 阶段不建影子双轨（见开工前事实核查门）；
- 保留稳定业务 ID 是历史正确性，不是兼容包袱；
- 金额逐分对账，不使用容差；
- 权限差异零容忍；
- 无法分类的数据进入拒绝桶，不能猜测迁移；
- 每个切片可独立回滚；金额核心切片在首笔新写后进入前向修复，不应用层反向同步。

### 11.2 阶段 A：产品可信度收口（可与语义冻结并行）

先修用户已经撞到的错误路径和死路：

1. 登录错误反馈，401 不再进入硬刷新跳转链；
2. 产权证关联资产 `page_size` 与后端上限对齐，消除 422 兜底 UUID 路径；
3. 组织树告警清零；
4. 项目详情空态补齐；
5. PDF 导出占位改为真实 PDF 或明确暂缓并从入口隐藏；
6. 死路由、孤儿页面、旧服务和未挂载模块清理；
7. 导航随对应纵向切片逐域换名：某域新切片完成、旧页面关闭的同一发布里切换该域入口名与路由；未完成域保留旧入口名与旧页面一致。仅“工作台”可在阶段 A 提前（所指不变）。

退出条件：用户视角审计主路径 error=0；正式路由探针无 404/未挂载入口；已知 P1/P2 全清。

### 11.3 B0：证据签字与 ADR 细化时间盒

开工前先完成事实核查 G0：确认是否有真实生产写入、必须保留的数据、旧土地物业系统数据采用迁入/归档/放弃哪种策略，以及选迁入时源数据是否可迁。0→1 且无真实数据时直接写新结构并删除旧入口；有真实数据时只对需保留事实迁移对账，不建长期影子双轨。

最终评审已经裁定的产品不变量不得在 B0 重开：本期建设最小押金域；支付登记命令接受非空锚点集合、UI 默认单锚点并允许登记时显式多选；服务费修订复用追加版本骨架但保留独立领域语义；采用独立 Space、三种出租授权模式、后继 Agreement/补充协议两种法律路径和物业 B4 闭环。B0 只核验证据、固化政策矩阵并细化 ADR 实现约束：

| 组 | 五日内必须签字的证据包/ADR 细节 | 依赖切片 |
|---|---|---|
| B0-A 既有域 | 押金条款/流水/余额源数据抽样与会计边界；支付锚点允许类型、登记多选权限与可见性矩阵；服务费版本链共享骨架的约束名、锁序、迁移与对账细节 | A2/A3 |
| B0-B 新领域 | Space 拓扑与 Asset/Project assignment 源数据抽样、面积守恒和调配政策；产权/经营权来源证据及三模式授权矩阵；物业限制级别、自处理自验收和 critical finding 原子联动政策；**accepted delivery review 政策有效期常数**；续租法律文书样本、前后继间隔政策 | A1/A2/B4/I1/I2 |

B0-A 与 B0-B 从启动日起各五个工作日内完成证据签字和 ADR 细化，五日不是编码、迁移或完整交付估算。只有客观第三方证据未到位时，相应组可批准一次最多五个工作日的补证延期，并同时记录缺失证据、责任人、受影响切片和新截止日；延期不得改变上述产品不变量。到期未签进入 `blocked` 并升级产品负责人，只冻结依赖该证据的切片，其他无依赖工作继续。

实施顺序唯一为：`B0 证据/政策签字 → v3.13 定向设计终审 → §15 SSOT 同步 → B1/A/B/I 实现`。B0 未签字不能宣称终审通过；终审未通过不能先改 SSOT 或业务代码。

### 11.4 双工作流与集成顺序

**B1 共享地基**：统一命令执行器、幂等回执、事务内重鉴权、固定锁序、审计/事件、附件证据协议、全通道权限测试、独立 Space 与有效期 Project assignment。权限硬化是所有切片横切门，不再占用 B4 编号。

**Workflow A：商业链**

- **A1 授权**：Agreement Authority 解析/校验/快照、三种来源模式、Space × 期间覆盖与 defect 处置；
- **A2 合同与义务**：锁定—签约交接、录入纠错、商业变更、续租、终止、账单和服务费义务；
- **A3 现金与清偿**：流水锚点、活动分摊集合、押金现金、服务费现金、坏账和逐分对账。

**Workflow B：物业 Epic B4**

- **B4.1 问题闭环**：问题 → 分派 → 处理 → 提交验收 → 接受/驳回 → 重开；
- **B4.2 现场限制**：多来源限制、阻断级别、逐来源解除；
- **B4.3 巡查**：通用/周期计划生命周期、计划 × 周期 × Space 幂等生成、现场执行、发现和补充证据；例行提交即完成且不进入复核；
- **B4.4 交还与交付**：`possession_return`/`handover` 专用检查、rejected successor、过期 accepted review 的 `ReinspectDeliveryRun`、未过期 accepted review 硬前置、实际占有与交付事实命令；
- **B4.5 现场体验与加固**：390px 移动 Web、指标、通知、附件和全通道权限。

**Integration**

- **I1**：合同终止 → B4.4 交还检查/accepted review/实际交还 → 整改/限制 → 验收 → 可租；
- **I2**：新合同 → 授权复核 → B4.4 交付检查/accepted review/交付。

A 与 B 可并行开发；编号表达依赖和可验收增量，不是瀑布顺序。B4.3 只拥有通用/周期巡查，B4.4 独占交还/交付专用检查及事实命令，I1/I2 只编排跨域前置与回执，不复制事实或命令。**B1 完成后立即建立跨 A1–A3 骨架集成测试**：Space/授权 → 合同/义务 → 现金/核销最小商业链的端到端测试工件，随片点亮并持续运行；它不是新切片，不产生第二套“完成”口径。

### 11.5 交付层级与发布依赖

- **物业域最小可用增量**：B4.1 问题 → 处理 → 验收/重开完整跑通；只能称“物业问题闭环可用”，不能称产品完成；
- **产品最小商业链**：Space/授权 → 合同/义务 → 现金/核销；必须通过 A1–A3，并由 B1 后的跨 A1–A3 骨架集成测试持续证明；
- **本期最终产品签收**：商业链与 B4.1–B4.5 均完成，并通过 I1/I2 端到端联通和岗位现场验收。

物业部署单向依赖稳定 `space_id`；Space、合同和收付可先发布，物业不反向阻塞商业链。物业限制投影上线前，Space 的现场可运营维度只能显示“待评估”，不得假定可租；B4.2 上线并完成初始化后，才按活动限制派生。

每个切片同时交付页面、命令/API、模型/迁移、数据库约束、能力码、失败测试、空/加载/错误/无权限四态和旧入口退出清单。完成一片即删除该片旧写路径，不长期双轨。

### 11.6 对账与回滚

- 金额切片逐分核对对象、冻结归属、活动分摊和 owner/manager/all 行集合；
- Space/授权切片核对拓扑、Project assignment、来源修订、覆盖期间和合同—Space 唯一性；
- 物业切片核对原系统巡查计划/任务/处理记录到新事实的映射；无法证明责任人、期限、证据或验收的旧记录只归档，不伪造成已完成工单；
- 发布前声明首笔新写、停止流量、快照恢复、RPO/RTO 和前向修复；金额切片首笔新写后不做应用层反向同步；
- 前端和读查询可回滚；新增事实表在未接管写入前可重建；迁移无法分类的数据进入拒绝桶，不按名称猜关系。

### 11.7 本期边界

保留催缴联系记录与承诺还款日，但不建催缴工单或催收成功率 KPI。房间租控图编辑、企业微信/支付/财务/BI/地图集成等仍在 §12 排除。物业闭环按 B4 实施，不再归入“后续再说”。

### 11.8 回滚边界

- 前端和读查询切片可回滚；
- 新增事实表在未接管写入前可清空重建；
- 金额命令切片接收首笔新写后越过不可回滚点，只采用前向修复或恢复到明确 RPO 的整库快照，不做应用层反向同步；
- 每阶段预先声明 RPO/RTO、首笔新写的判定、停止流量步骤和不可回滚点。

## 13. 验收门与建议测试

### 13.1 语义门

- 四条事实轴、五个任务型业务入口与往来方档案库在 PRD、领域模型、API、路由与本文中唯一；Space、Asset、Project 不得继续复用为同一身份；
- 三种授权模式、签约 Party—来源关系、Space × 期间无缺口覆盖、不可变授权快照、缺陷派生与处置在 SSOT 中唯一；`property_leasing_authority_revisions` 是产权/经营权唯一可写事实，`Asset.owner_party_id` 只是不参与授权和资金归属解析的当前投影；
- `AgreementCorrection`、`AmendAgreement`、后继合同续租与补充协议展期语义分离；每条路径的授权重验、历史保护和义务影响明确；
- Space 五个正交维度、招商锁和多来源现场限制分别有权威事实；“可租”和“即将释放”按 §2.1 两套公式唯一，临期合同不得计入可租；
- 合同终止、实际交还、物业整改/验收、重新可租与新租户交付是独立事实和命令；目标态不存在 `ReleaseSpace` 或手改“空置可租”；
- Party 八类来源角色都有明确事实依据，资金归属方与实际收付方不得混同；
- 物业工单是窄承诺对象，预警仍不是任务；工单责任人、期限、证据、接受/驳回/重开状态机在 SSOT 中唯一；例行巡查提交即完成且无 review，交还/交付专用检查才允许复核与 rejected successor；
- `restriction_type × blocking_level` 对营销、签约、续租、入住交付和继续占用的阻断策略有唯一矩阵；同一 Space 多来源限制可并存；
- 活动分摊集合、active 流水锚点 ≥1、服务费来源身份/单活动修订、带本地 `enforcement_state` 的合同—Space 覆盖、底价、坏账，以及 holding lot/disposition 押金守恒继续遵守唯一口径；
- 每个不变量同时有数据库约束或等价最后防线、事务内命令校验和失败测试。

### 13.2 安全门

- 七类既有权限用户加物业现场人员/负责人/交付负责人，覆盖列表/count/详情/搜索/通知/导出/附件/审计/回执/移动 Web；
- owner O1 能看项目 P 的一项资产时，不能因此看到 O2 的合同名、金额、风险数或附件；
- 撤权后下一请求立即拒绝，不能等待投影或缓存 TTL；原幂等键回放也必须重新鉴权，不返回旧结果载荷；
- `perm_admin` 给自己或他人授予业务角色必须在命令端拒绝并审计；`perm_admin` 默认诊断不返回业务对象名称/编码/金额/附件；未满足 §5.7 岗位证据触发条件时，不得实现对象级诊断能力、端点或入口；
- 共享扫描件替换不泄露无权兄弟项目；重复内容上传也不暴露无权 blob 是否存在；
- 项目运营方切换前后，Project、Project 侧 Asset/Space 片段、Contract、Ledger 四类对象按 §8.9 矩阵授权；原运营方在切换日后仍能访问旧合同和旧台账，但不得创建新运营方合同；新运营方不得经当前 Asset 聚合或历史项目视图看到切换前及其他 Project 的 Space、合同金额和台账；
- Space 当前视图与工作台按查询时 assignment 和同一五维公式授权/派生；历史物业记录按冻结 Project/operator 授权；任一处可租/即将释放集合不一致即失败；
- 无权用户不得从物业 count、责任人自动补全、通知摘要、图片附件、导出或审计获知 Space/工单存在性；
- 合同授权来源对无来源范围的用户最小化抑制，不能泄漏来源 Party、上游合同或兄弟 Space；
- 待核销流水清单（含 `deposit` 押金流水）只向拥有全部**非空**活动锚点范围权限的用户展示流水金额和待核销余额；部分锚点用户只能看到自己范围内的已授权分摊明细，不能反推整笔金额；无权锚点的名称、ID、金额和数量均不可见；零活动锚点的 active 流水为非法状态，迁移/命令必须拒绝；
- 流水对方 Party 超出查看者范围时只显示“范围外往来方”，全局搜索和自动补全不得返回其名称、编码、ID 或数量；
- 命令审计时间线按目标对象和活动锚点集合裁剪；部分锚点用户读取审计不得获得范围外锚点、金额或对象信息；空间锁定/停用/待确权与坏账核销审计同样按对象范围裁剪；
- 命令回执查询端点执行与回放相同的重鉴权和裁剪；撤权后返回 403/404。

- 每切片发布后逐分对账通过；旧系统不存在的新能力按 §13.3 对应命令/并发/越权门通过；目标读查询在写切换前已验收；

- 旧路径删除清单有唯一退出条件，不允许双轨无限期存在。

**5 条自动化 smoke（脚本执行，每次发布必跑）**：

1. 导航 30 秒预算内抵达“登记收款”“可租”“即将释放”和“物业工单”，断言六入口存在且按工作台/资产/合同/收付/物业/往来方排序；
2. 完成一笔款核销 3 张账单 <90 秒，URL 保持项目/合同/账期上下文；
3. 合同录入 dry-run：切换授权模式/Space/租金时授权与账单预览 2 秒内刷新，不产生写入；
4. 390px 视口完成工单开始、拍照、提交验收，控件无重叠和横向滚动；
5. 合同终止后显示仍待交还；完成交还并留有现场限制时仍不可租；验收并解除最后一个阻断限制后才进入可租。

**人工计时与脚本分开记录**：中位合同录入 <8 分钟属于现场计时 checklist（人工），不在自动化 smoke 中断言；解析排队时间单独列示，不计入人工录入时长。

**保留的界面断言**：

- 菜单深度 ≤2 级 + 1 级子路由；六个一级入口齐全且按工作台/资产/合同/收付/物业/往来方排序；工作台/合同/收付/物业/往来方均为零子节点，物业单页只有“现场任务 / 巡查计划 / 现场档案”三个页内 tab，工单与巡查详情只走子路由；资产子节点按序 = 空间/台账/项目总览/产权证；收付页只有“收款 / 付款 / 待核销”三个一级 tab，租金/押金/服务费均为类型筛选，不渲染“服务费”一级 tab 或次级 tab 组；
- §5.10 规范执行工作区矩阵全覆盖：一个命令只能有一个提交工作区，但可有多个携带上下文入口；
- Space 默认“可租”，并可切到“即将释放”；两者集合不重叠，现场“待评估”不进入可租；
- 资产 › 空间包含只读租控图视图：色块主维度 = 供给主状态（可租/在租/即将释放/受限/待评估），无编辑入口，点格进入 Space 详情锚区；
